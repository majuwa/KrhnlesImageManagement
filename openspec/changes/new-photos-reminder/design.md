# Design

## Context

See proposal.md (Why) for motivation and `specs/new-photos-reminder/spec.md` for the behavior contract. Relevant current state:

- **Non-credential preferences** (`wifi_only`, `auto_date_folders`, `blur_sensitivity`, `verify_by_download`) are plain keys in the credentials DataStore, written only through `CredentialStore` (`NoCredentialDataStoreAccessRegressionTest`). The credential snapshot de-duplicates on `(serverUrl, baseFolder, credentials_version)` before decrypting, so extra keys never touch the Keystore. `CredentialStore.clear()` calls `prefs.clear()` (resets every such key) and the file is excluded from backup / device transfer.
- **Logout** is `SettingsViewModel.logout()`: `clearLogged(...)` steps (verified uploads → credentials → uploaded markers), each in its own `runCatching` that rethrows `CancellationException`.
- **Uploaded markers**: `UploadedPhotosStore.uploadedPhotoIds: Flow<Set<Long>>` (media ids, video ids carry `Photo.VIDEO_ID_FLAG`, built only via `mediaItemId()`).
- **Upload history**: `UploadHistoryStore.entries` (`timestampMillis`, `photoCount` = batch size, `failedCount`), written by `UploadWorker.recordHistory()` at the end of each run, not cleared on logout, user-clearable.
- **Media**: `MediaRepository` queries `MediaStore.Images` / `MediaStore.Video` (full rows, no limit) for the grid. Access rules live in `ui/photogrid/MediaAccess.kt` (`MediaAccess.of(context)`: `images` / `video` / `userSelected`, `hasAccess`, `isPartial`).
- **Album downloads (`download-album-photos`, implemented, CLAUDE.md rule 11)**: `DownloadWorker` inserts saved photos through `LocalMediaWriter` into `MediaStore.Images` under `"Pictures/$DOWNLOAD_ROOT_FOLDER/<album>/"` (`DOWNLOAD_ROOT_FOLDER = "KroehnSync"` in `download/DownloadNames.kt`), owned by this package. They never touch `UploadedPhotosStore` / `VerifiedUploadsStore` and stay visible under "show only new photos" — without an exclusion every saved photo would be counted as "new".
- **Notifications**: `UploadWorker` owns channel `upload_channel` (LOW), ids 1001 (foreground) / 1002 (results, tagged by queue file); the download worker owns `download_channel` (LOW), ids 1004 (progress) / 1005 (results). Both check `POST_NOTIFICATIONS` before `notify`; none sets a content intent today. Id 1003 is free and reserved for this change. The photo grid already requests `POST_NOTIFICATIONS` whenever it is composed without it. `minSdk` is 35 (`targetSdk` 37), so the runtime permission, `QUERY_ARG_*` bundles and `OWNER_PACKAGE_NAME` are always available.
- **WorkManager cancel guard**: `NoUploadWorkCancelOutsideCancelPathRegressionTest` forbids `cancelWorkById` / `cancelAllWorkByTag` / `cancelUniqueWork` / `cancelAllWork` in every main source except `worker/UploadCancellation.kt` (plus two narrow, user-confirmed download allowances), and `ExistingWorkPolicy.REPLACE` everywhere. A plain `cancelUniqueWork` in a reminder file would fail it.
- **Entry**: `MainActivity` (standard launch mode, exported for the launcher / share filters, no `onNewIntent` handling yet) decides once in `onCreate` between `ShareRoute` and `KrhnlesApp`; a share instance runs in the sharing app's task (usually) and `openApp()` starts the app with `FLAG_ACTIVITY_NEW_TASK`. `KrhnlesApp` resolves the start route once (`StartupViewModel`, may be onboarding) and hosts the `NavHost`; tabs navigate with `popUpTo(ROUTE_PHOTOS) { saveState = true }` + `restoreState`, Settings / Upload history are pushed above `ROUTE_PHOTOS`, the album screens live in the Albums subtree. The grid's `PhotoGridViewModel` is scoped to `ROUTE_PHOTOS` and only has `toggleShowOnlyNewPhotos()`; the top-bar toggle is hidden while a selection is active.
- **Application start**: `KrhnlesApplication.onCreate` already starts `recoverCancelledUploads(…, WorkManager.getInstance(…), …)` once per process in `appScope` (guarded by an `AtomicBoolean`).

## Goals / Non-Goals

**Goals:**
- One unique periodic job per install that is always consistent with the stored setting (toggle, interval change, logout, app start, self-cancel).
- A counting step that is a pure function over rows + markers + baseline, so the logic is unit-testable without MediaStore.
- A launch request that is applied exactly once and goes through navigation, never through a second activity or a global singleton.

**Non-Goals:**
- No automatic upload, no network check of what is on the server, no server-side comparison.
- No dismissal of a shown reminder when the user starts an upload (it is auto-cancelled on tap and replaced by the next reminder).
- No per-album / per-folder reminders, no custom time of day, no exact scheduling (WorkManager timing is inexact by design).
- No change to the existing launch-time `POST_NOTIFICATIONS` request of the photo grid.

## Decisions

### D1. Storage: four plain keys in the credentials DataStore via `CredentialStore`
Keys: `new_photos_reminder_enabled` (Boolean), `new_photos_reminder_interval` (enum name, read type-safely via `asMap()[KEY] as? String`, fallback `Weekly`, like `blur_sensitivity`), `new_photos_reminder_since` (epoch ms, written together with `enabled = true` in one edit when the reminder is turned on), `new_photos_reminder_last_shown` (epoch ms, removed in that same edit). Exposed on `CredentialRepository` as `newPhotosReminder: Flow<NewPhotosReminderSettings>` (data class: enabled, interval, sinceMillis, lastShownMillis), `saveNewPhotosReminder(enabled, interval)` and `markNewPhotosReminderShown(atMillis)`. Plain `edit`s, no `credentials_version` bump.
- *Why:* the request asks to follow Wi-Fi only / blur sensitivity; this gives logout reset (`prefs.clear()`) and backup exclusion for free and keeps all DataStore access inside `CredentialStore`.
- *Alternative:* `app_preferences` (onboarding / media-permission flags) — rejected: it is not cleared on logout, so a separate reset path would be needed.
- *Alternative:* a separate reminder DataStore — rejected: another backup-rules entry and another logout step for four values.

### D2. `ReminderInterval` enum in `model/`
`Weekly(7)`, `EveryTwoWeeks(14)`, `Monthly(30)` days, `fromStored(String?)` with fallback `Weekly`. "Monthly" is a fixed 30-day period (PeriodicWorkRequest has no calendar months).

### D3. Scheduling through a `NewPhotosReminderScheduling` interface
`reminder/NewPhotosReminderScheduler.kt` wraps `WorkManager`:
- `schedule(interval)` → `enqueueUniquePeriodicWork(NEW_PHOTOS_REMINDER_WORK_NAME, ExistingPeriodicWorkPolicy.UPDATE, request)`; request = `PeriodicWorkRequestBuilder<NewPhotosReminderWorker>(interval.days, DAYS)`, `setInitialDelay(interval.days, DAYS)`, constraint `setRequiresBatteryNotLow(true)`, no network constraint, tag `new_photos_reminder`.
- From Settings: turning on → `UPDATE` (WorkManager deletes a `CANCELLED` spec and enqueues anew, so the first run is one interval after enabling), interval change → `UPDATE` (keeps the existing work id and its enqueue time, replaces the period; a running instance finishes with the old spec). Turning off / logout → `cancel()` = cancel the unique work + cancel the reminder notification.
- `reconcile(settings)` on app start → enabled: `UPDATE` (per the `ExistingPeriodicWorkPolicy.UPDATE` KDoc it preserves the enqueue time, so it never resets the timing of an existing schedule, yet repairs a period that drifted because a Settings schedule call failed after the write; enqueues when absent); disabled: `cancel()` (no-op if absent). `KEEP` is not used: it would keep a stale period forever.
- Only `UPDATE` is used for the reminder; never `ExistingPeriodicWorkPolicy.CANCEL_AND_REENQUEUE` / `REPLACE` (they stop a running instance and reset the timing).
- **Cancelling is the one exception to the upload cancel guard.** The unique work is removed by exactly one call, `workManager.cancelUniqueWork(NEW_PHOTOS_REMINDER_WORK_NAME)`, inside `NewPhotosReminderScheduler.cancel()` in `reminder/NewPhotosReminderScheduler.kt`; the worker's self-cancel (D6) and logout go through that method. `NoUploadWorkCancelOutsideCancelPathRegressionTest` gets a third narrow allowance in the style of the download ones: in that file only `cancelUniqueWork(NEW_PHOTOS_REMINDER_WORK_NAME)` (no other cancel API, no other argument), and the file joins the "allowed files never reference upload work" check (`photo_upload`, `UploadWorker`, `uploadWorkRequest`). This is sound for the guard's purpose: the name `new_photos_reminder` is never used by upload work, so no upload ever sees `STOP_REASON_CANCELLED_BY_APP` from it. Because it widens a guard that the CLAUDE.md upload rule calls "the only code that cancels work", the allowance was confirmed by the user (as the download allowances were) and CLAUDE.md rule 4 is reworded accordingly.
- Every call is wrapped (`runCatching`, rethrow `CancellationException`, `IllegalStateException` from an uninitialised WorkManager logged by type); `await()` the `Operation` with a timeout (CLAUDE.md: bounded waits).
- *Why an interface:* `SettingsViewModel` gets it as a default constructor parameter (`@JvmOverloads`, `ViewModelFactoryRegressionTest`), tests pass a recording fake; Robolectric tests of the real scheduler use `WorkManagerTestInitHelper`.
- *Alternative:* schedule from the worker side only (self-rescheduling one-time work) — rejected: periodic work is what WorkManager persists across reboot / update without extra receivers.

### D4. Ordering of a Settings change
`SettingsViewModel.setNewPhotosReminder(enabled, interval)`: persist first (`saveNewPhotosReminder`), then schedule / cancel; a failed write is logged by type and changes nothing else (the switch shows the stored value, like `setVerifyByDownload`). A failed schedule leaves the stored value; app-start `reconcile()` and the worker's self-cancel (D6) repair any drift. Calls are serialized by one `Mutex` acquired with a timeout (CLAUDE.md: locks with a timeout; a timed-out acquisition logs and drops the call): without it a quick on → off → on would run two coroutines whose `UPDATE` / cancel can reach WorkManager in the wrong order and leave the work cancelled while the setting is on. Inside the lock the step applies the value it just stored. Logout adds a `clearLogged("reminder") { reminderScheduler.cancel() }` step before the credential clear; the credential clear resets the keys.

### D5. Reconcile on app start
`MainActivity.onCreate` (non-share path, `savedInstanceState == null`) calls `KrhnlesApplication.newPhotosReminderScheduler.reconcileInBackground()`, which runs in `appScope`: reads `newPhotosReminder.first()` under `withTimeoutOrNull(3 s)` (`runCatching`, rethrow cancellation); null / failure → do nothing.
- *Why not `Application.onCreate`:* it would also run whenever WorkManager wakes the process (every upload, download and reminder run) and in share launches, re-reading the setting each time for nothing; and every Robolectric test that instantiates `KrhnlesApplication` would hit the reminder path (`recoverCancelledUploads` already touches WorkManager there, wrapped in `runCatching`, so this is a cost, not a blocker). Opening the app is the moment drift matters. The share path is skipped because it runs in another app's task and must stay minimal.
- After a force-stop the OS drops the app's jobs; WorkManager reschedules them on the next process start (its `ForceStopRunnable`), so no reminder appears until the app is opened again — documented in the README, no extra code.

### D6. `NewPhotosReminderWorker` (CoroutineWorker, `reminder/`)
Internal constructor with injectable `CredentialRepository`-like settings source, `UploadedPhotosRepositoryContract`, `UploadHistoryRepository`, `NewMediaQuery`, `ReminderNotifier`, clock and permission checker; public `(Context, WorkerParameters)` constructor for WorkManager. Steps (each store read `withTimeoutOrNull(3 s)` + `runCatching`, rethrow cancellation):
1. Settings unreadable → `Result.success()` (nothing posted, nothing cancelled). Disabled → `scheduler.cancel()` (D3, the only allowed cancel) as the **last** step, then `Result.success()` (cancelling its own unique work stops this coroutine, so nothing may follow it).
2. `ReminderNotifier.canPost()` false (permission, `areNotificationsEnabled()`, channel importance `NONE`; a channel that does not exist yet counts as allowed, it is created right before posting) → success, no query.
3. `queryableKinds(access: MediaAccess)` (pure, reusing `MediaAccess.of(context)` from `ui/photogrid/MediaAccess.kt`, never a second permission list): Image iff `images || userSelected`, Video iff `video || userSelected` (with partial access MediaStore returns only the selected items); `!access.hasAccess` → success, no query. `ACCESS_MEDIA_LOCATION` is irrelevant.
4. Baseline = max(`sinceMillis`, newest history `timestampMillis` with `photoCount > failedCount`). History unreadable → `sinceMillis` only. `lastShownMillis` read too.
5. Markers unreadable / timeout → success without posting (an empty set would over-count).
6. Query (D7), then pure `countNewMedia(rows, uploadedIds, baselineMillis, lastShownMillis)` → `NewMediaCount(total, hasNewSinceLastReminder, isLowerBound, sinceLastUpload)`.
7. `total > 0 && hasNewSinceLastReminder` → re-read the setting (still enabled, same `sinceMillis`) → post (D8) → `markNewPhotosReminderShown(now)`.
Always `Result.success()` (a missed reminder needs no retry; periodic work continues anyway). No network, no `WebDavConfig`, no Keystore.

### D7. Bounded media query (`reminder/NewMediaQuery.kt`)
Per kind: `contentResolver.query(collection, arrayOf(_ID, DATE_ADDED), Bundle, CancellationSignal)` with the selection built by a pure `reminderSelection(baselineSeconds, ownPackage, excludedPathPrefixes)` → (`QUERY_ARG_SQL_SELECTION`, `QUERY_ARG_SQL_SELECTION_ARGS`):
`date_added > ? AND is_pending = 0 AND is_trashed = 0 AND (owner_package_name IS NULL OR owner_package_name != ?) AND (relative_path IS NULL OR relative_path NOT LIKE ?)` (one `relative_path` clause per prefix, argument `<prefix>%`). The `IS NULL` branches are required: in SQL `NULL != x` and `NULL NOT LIKE x` are NULL, which would silently drop every row without an owner or a path. `is_pending = 0 AND is_trashed = 0` duplicate MediaStore's default `MATCH_EXCLUDE` on purpose, so the rule is visible in the selection and testable (no `QUERY_ARG_MATCH_*` is set). Rows with a null `date_added` are not counted. `QUERY_ARG_LIMIT` = `MAX_REMINDER_SCAN_ROWS` (50,000) + 1; `QUERY_ARG_SQL_SORT_ORDER` `date_added DESC`. `DATE_ADDED` is in seconds; the baseline is converted with floor division and `>` keeps second-granularity semantics. Ids go through `mediaItemId(rawId, kind)` (raw ids `>= 2^62` skipped).
- The blocking query (incl. reading the cursor into a list of `(id, dateAddedSeconds)` and closing it) runs through the existing `abandonableCall()` (`util/AbandonableCall.kt`: `CancellationSignal`, `REMINDER_QUERY_TIMEOUT_MS` = 30 s, detached, `Dispatchers.IO`), not a bare `withTimeoutOrNull` around a blocking call, which could not return before the provider does. The block maps `android.os.OperationCanceledException` (a cancelled signal; not a coroutine `CancellationException`) to the timeout result and a `SecurityException` to zero rows for that kind. A timeout aborts the run (no post, no `last_shown` write).
- *Why not reuse `MediaRepository.loadPhotos()`:* it reads the full library with names, sizes and durations and has no limit; the reminder needs ids and `DATE_ADDED` of recent rows only.
- *Why `DATE_ADDED`:* "new on the device" is when it entered MediaStore; `DATE_TAKEN` would miss photos received from others and is null for many files.
- *Why the owner and path filters:* photos saved by `download-album-photos` are owned by our package while it is installed; after an uninstall / reinstall MediaProvider orphans them (owner null), so the path prefix `DOWNLOAD_RELATIVE_ROOT` = `"Pictures/$DOWNLOAD_ROOT_FOLDER/"` also excludes them. That constant is extracted into `download/DownloadNames.kt` and used by `DownloadWorker` (replacing its inline `"Pictures/$DOWNLOAD_ROOT_FOLDER/…"`) and by the reminder, so the two can never drift. `LIKE` is ASCII case-insensitive and the prefix contains no `%` / `_`, so no `ESCAPE` is needed.
- *Consequence (documented, intended):* saved photos stay visible under "show only new photos" (rule 11) but are not counted, and the filter shows every unmarked item while the count only covers items after the baseline, so the reminder's number can be lower than what the filtered grid shows.
- *Testing:* Robolectric has no MediaProvider. `FakeMediaStoreProvider` gets a Bundle-query path for the two collection uris that loads the configured rows into an in-memory SQLite table with the MediaStore column names and runs the recorded selection, args, sort and limit through `SQLiteQueryBuilder` — the real SQL is evaluated (incl. the NULL cases), no hand-written parser. Existing 5-argument queries and item-uri queries keep their current behaviour.

### D8. Notification (`reminder/ReminderNotifier.kt`)
Channel `new_photos_reminder_channel` ("Reminders", `IMPORTANCE_DEFAULT`, created before posting), id `NEW_PHOTOS_REMINDER_NOTIFICATION_ID = 1003` (never the upload ids 1001 / 1002 or the download ids 1004 / 1005), no tag, so a new reminder replaces the old one. Small icon = the existing notification glyph. Title `R.string.reminder_notification_title`; text `R.plurals.reminder_new_media_since_upload` / `R.plurals.reminder_new_media` (no upload since enabling) / `R.plurals.reminder_new_media_more_than` (lower bound), via `resources.getQuantityString`. `setAutoCancel(true)`. Content intent: `PendingIntent.getActivity(context, REQUEST_CODE_SHOW_NEW_MEDIA, Intent(context, MainActivity::class.java).setAction(ACTION_SHOW_NEW_MEDIA).addFlags(FLAG_ACTIVITY_NEW_TASK or FLAG_ACTIVITY_CLEAR_TOP or FLAG_ACTIVITY_SINGLE_TOP), FLAG_IMMUTABLE or FLAG_UPDATE_CURRENT)`; `ACTION_SHOW_NEW_MEDIA` is namespaced (`"$packageName.action.SHOW_NEW_MEDIA"` as a constant, not built from a runtime package name). `notify` only after the `POST_NOTIFICATIONS` check in the same function (lint `MissingPermission` satisfied without suppression). `CLEAR_TOP` finishes activities above `MainActivity` in the app task, e.g. a system permission dialog or the trash confirmation the grid launched; they return `RESULT_CANCELED` / a denial, which those flows already handle as a dismissal (accepted).

### D9. Launch request → navigation
- Pure `launchRequestOf(intent): AppLaunchRequest?` (`ui/navigation/LaunchRequest.kt`): `ShowNewMedia` iff `intent.action == ACTION_SHOW_NEW_MEDIA`; extras and data are never read. `isShareIntent` is checked first, unchanged.
- `LaunchRequestViewModel` (plain `ViewModel`, no-arg constructor, activity-scoped via `by viewModels()`): `pending: StateFlow<AppLaunchRequest?>`, `offer(request)`, `consume()`. `MainActivity` offers in `onCreate` only when `savedInstanceState == null` (process-death / rotation recreation never re-applies the original intent) and in an `addOnNewIntentListener` (CLEAR_TOP + SINGLE_TOP delivers taps to the running instance).
- A share-mode instance never offers and never registers the listener: if a tap reaches it (a sharing app that started the share with `FLAG_ACTIVITY_NEW_TASK` puts it into the app's task), the share screen stays and the request is dropped (documented edge case; the share finishes within seconds and the reminder is shown again only when something new arrives).
- `KrhnlesApp(onStartUpload, launchRequests, onLaunchRequestConsumed)`; inside `KrhnlesNavigation`, a `LaunchedEffect(pending)`: if the start route is onboarding → `consume()` (dropped). Otherwise it leaves the current screen through a pure `NavController.openPhotosForLaunchRequest()` (next to `completeOnboarding`, never the graph start, per CLAUDE.md 3a):
  - back stack contains `ROUTE_ALBUMS` → the Photos-tab navigation without `restoreState` (`popUpTo(ROUTE_PHOTOS) { saveState = true }`, `launchSingleTop`; verified: with `restoreState = true` Navigation restores the just-saved Albums subtree on top of the grid again). The Albums subtree is *saved*, not destroyed, so a running album photo deletion (which blocks Back, CLAUDE.md rule 8) keeps running in its retained `AlbumDetailViewModel` and its `photoDeletionOutcome` is shown when the user returns through the Albums tab — a plain pop would clear that ViewModel and cancel the deletion half-way;
  - otherwise (Settings / Upload history above the grid, or the grid itself) → `popBackStack(ROUTE_PHOTOS, inclusive = false)` without saving, like Back: saving Settings would retain a `SettingsViewModel` under a key that is never restored.
  The `ROUTE_PHOTOS` composable observes the same pending request and, when it is `ShowNewMedia`, calls `PhotoGridViewModel.showOnlyNewPhotos()` (sets `true`, recomputes from `allPhotosByDate`, removes now-hidden ids from `selectedPhotoIds` so no invisible item stays selected — the top-bar toggle is never offered during a selection, but the reminder can arrive during one; idempotent) and then `consume()`. Because consumption happens only in the grid destination, the filter is never lost when navigation and composition race.
- *Alternative:* a nav argument on `ROUTE_PHOTOS` / a `navDeepLink` — rejected: changes the route pattern used by `popUpTo(ROUTE_PHOTOS)` and the bottom bar, and a deep link URI would be re-applied by the NavController on recreation.
- *Alternative:* an intent extra boolean — rejected: the action alone is sufficient and an exported activity should not interpret extras.
- *Security note:* `MainActivity` is exported, so any app can send `ACTION_SHOW_NEW_MEDIA`; the only effect is opening the grid with a filter on — no data is read from the intent.

### D10. Settings UI
In the logged-in section next to Wi-Fi only: one `toggleable(role = Role.Switch)` row; when on, three `selectable(role = Role.RadioButton)` rows inside `selectableGroup()`. Turning on with `POST_NOTIFICATIONS` missing launches `RequestPermission` through `rememberLauncherForActivityResult` (testable with a fake `ActivityResultRegistry`, like `PhotoGridPermissionTest`). `canPostReminders` is computed in the screen through the same pure rule as `ReminderNotifier.canPost()` (`NotificationManagerCompat.areNotificationsEnabled()` + permission + channel importance != `NONE`, a missing channel counts as allowed) on `ON_RESUME` and after the permission result; when the reminder is on and it is false, a hint with "Open notification settings" (`Settings.ACTION_APP_NOTIFICATION_SETTINGS` + `EXTRA_APP_PACKAGE`) is shown. Strings via resources; callbacks use `LocalResources.current`.

## Risks / Trade-offs

- [WorkManager periodic timing is inexact (Doze, battery-not-low)] → acceptable for a weekly nudge; documented in README.
- [A clock change backwards puts the baseline in the future, so nothing is counted until time catches up] → accepted; turning the reminder off and on resets it.
- [Restored / copied old photos get a new `DATE_ADDED` and count as new] → intended: they are not backed up from this device.
- [Clearing the upload history moves the baseline back to the enable time, so more items count] → accepted; markers still exclude uploaded items.
- [Partial access counts only selected items, typically 0] → spec'd; README explains that reminders need full photo access.
- [Worker writes `last_shown` while logout clears the DataStore] → the worker re-reads `enabled` + `sinceMillis` right before posting; a stray `last_shown` key with `enabled` unset is harmless and removed by the next enable.
- [The worker read "disabled", the user turns the reminder on, then the worker's self-cancel removes the fresh schedule] → narrow window; the next app start's `reconcile()` restores it. Accepted.
- [Logout's credential clear fails after the reminder was cancelled] → the stored value stays on and the next app start re-schedules it; consistent with "the stored setting wins".
- [Upload history uses the end time of a run, and shared-photo uploads also write history] → items added while a long run was in progress, or before a share upload, fall before the baseline and are not counted. Accepted: "since your last upload" is literal; the filtered grid still shows them.
- [App standby bucket "rare" / "restricted", force-stop] → runs can be deferred by a day or more, or (force-stop) until the app is opened; acceptable for a weekly nudge, documented in README.
- [Large libraries: 50,000-row cap per kind] → only ids and dates are read; above the cap the text says "more than".
- [Reminder channel `IMPORTANCE_DEFAULT` may make a sound] → user can change it per channel; the upload channel stays LOW.

## Migration Plan

No data migration: absent keys mean "off / Weekly". Existing installs see the new switch off. The WorkManager database lives in `noBackupFilesDir` (WorkManager ≥ 2.6), so a restored device has neither the setting nor the work; if a work spec ever survived without the setting, the self-cancel (D6) removes it. Rollback: removing the feature leaves unused keys in the credentials DataStore (cleared on next logout) and a periodic work entry whose worker class no longer exists; a rollback must therefore keep the allowed `cancelUniqueWork(NEW_PHOTOS_REMINDER_WORK_NAME)` call (and its guard allowance) on app start.
