## Context

Observed: `minSdk` is 35 (so the Android 13 criterion is not applicable) and `targetSdk` is moving to 37; Android 14+ partial media access always applies. `MediaRepository.loadPhotos()` queries only `MediaStore.Images`. `Photo` has `id`, `uri`, `mimeType`, `size`. The grid permission check uses `READ_MEDIA_IMAGES` or `READ_MEDIA_VISUAL_USER_SELECTED`. `UploadWorker` opens a `content://` stream and `WebDavClient.uploadFile` sends it through a streaming `InputStreamRequestBody` with a blocking `client.newCall(request).execute()` (`WebDavClient.kt`), no known length, `writeTimeout` 120 s per write, no `callTimeout`. The worker runs as a `dataSync` foreground service. `UploadedPhotosStore` and the queue file key photos by a single `Long` id. Album listings keep only `image/*` entries (`AlbumsRepository.isImage`), so the album screens and the duplicate / blur reviews never see videos.

## Decisions

1. **Permissions.** Manifest adds `READ_MEDIA_VIDEO`. The grid requests images, video and `READ_MEDIA_VISUAL_USER_SELECTED` in one `RequestMultiplePermissions` call. Access exists if any is granted (as today). "Video missing" means `READ_MEDIA_IMAGES` granted AND `READ_MEDIA_VIDEO` not granted, which only occurs for users upgrading from an images-only version. That case is requested at most once (persisted flag in the app preferences, otherwise per session); it is never auto-requested for partial-access (`USER_SELECTED`) users. Partial-access users instead see a non-blocking banner "Select more photos and videos" that re-launches the picker request. The banner action opens the app settings only after a permanent denial: a denied result where `shouldShowRequestPermissionRationale` is false *and* the system offered a rationale before (persisted `video_rationale_shown` flag, set after a denial with rationale). A false value without an earlier rationale means the dialog was dismissed; the banner keeps asking. Every permission result that keeps access reloads the media, so a widened grant (images-only to + video, partial to full) shows the new items at once. Full denial keeps `PermissionDeniedContent`. A `SecurityException` from the video query yields an empty video list, never an error for the images.
2. **Id collisions.** `MediaStore.Images` and `MediaStore.Video` ids overlap. Videos use `Photo.id = videoId or VIDEO_ID_FLAG` with `VIDEO_ID_FLAG = 1L shl 62`; image ids are unchanged. The value is positive (the queue treats `>= 0` as markable, `-1` as "no id"), fits the `Long` string-set in `UploadedPhotosStore` and the queue JSON, and needs no migration. A raw `_ID >= 2^62` is rejected / skipped by the helper (it would collide with the flag). The real content URI stays in `Photo.uri`.
3. **Video detection.** `Photo` gets `mediaKind: MediaKind { Image, Video }`, set by the query that produced the row; `Photo.isVideo = mediaKind == Video`. It is not derived from the mime type, because `MIME_TYPE` can be null. Videos with a null / blank mime type use the fallback `video/*` as content type; images keep their current fallback. The retry file stores `id` and `mimeType` only, so a retried video keeps `video/*` and is recognised by the flagged id.
4. **Query and ordering.** A second query on `MediaStore.Video.Media.EXTERNAL_CONTENT_URI` reads `_ID, DISPLAY_NAME, DATE_TAKEN, SIZE, MIME_TYPE, DURATION`. Both lists are merged and sorted by raw `DATE_TAKEN` descending before grouping by day. Undated videos (null / 0) map to `Photo.UNKNOWN_DATE` and group under "Unknown date" like images; no `DATE_MODIFIED` fallback (out of scope). Auto date folders therefore put undated videos in the same 1970/01/01 folder as undated images. `Photo` gains `durationMs: Long? = null`; unknown / zero duration shows no badge.
5. **Thumbnails.** Add `io.coil-kt.coil3:coil-video` (same version as Coil). Its service-loader registration would decode every `video/*` source, also a remote thumbnail answer, with `MediaMetadataRetriever`. The app image loader therefore sets `serviceLoaderEnabled(false)` and registers its authenticated OkHttp fetcher and `LocalVideoFrameDecoderFactory` explicitly; the wrapper delegates to `VideoFrameDecoder.Factory()` only for sources with Coil's `ContentMetadata` of a `content://` URI (network and disk-cache sources are refused). `VideoDecoderRegistrationTest` pins the single registration and the refusal of remote sources. The tile keeps `AsyncImage(photo.uri)`. `ContentResolver.loadThumbnail` as a custom fetcher was rejected for minimal scope. Compose tests keep providing `LocalAsyncImagePreviewHandler` + `LocalInspectionMode`. Frame extraction is slower than image decoding, so scroll performance is checked manually on a device with many videos.
6. **Tile, header and accessibility.** The tile stays one `toggleable(role = Role.Checkbox)` node. A play icon overlay and a duration badge (`m:ss` / `h:mm:ss`) are decorative (`contentDescription = null`). The description becomes "Video N of M, <duration>, taken on <date>" (and the unknown-date variant; without duration segment when duration is unknown or zero). File names are never used. The day header count covers all media of the day (photos and videos); wording is neutral ("N items") through a new `item_count` plural, and the header action labels become "Select all items of this day" / "Deselect all items of this day".
7. **Neutral wording.** User-facing strings that now also cover videos change to neutral wording: upload-queued toast, upload notification title / success / partial / failure plurals, uploading channel description, the select-all labels and the selected count. Strings that stay photo-specific: share-target texts (share is image-only), album / review / viewer texts, onboarding copy (describes the product, kept). Listed explicitly in the tasks.
8. **Upload.** The single `PUT` stays; chunked upload v2 is an explicit follow-up. Changes in `WebDavClient.uploadFile`:
   - Use the existing `executeCancellable(call)` pattern (shared from `AlbumsRepository.kt`, made `internal` or moved) instead of the blocking `execute()`, so cancelling the worker cancels the transfer.
   - `InputStreamRequestBody.isOneShot() = true` (the stream cannot be replayed; OkHttp must not retransmit it) and `contentLength()` returns the known size when available. The worker passes the length from `contentResolver.openAssetFileDescriptor(uri, "r").length`, computed inside the stream's `use` block; `AssetFileDescriptor.UNKNOWN_LENGTH` (-1) or any failure falls back to chunked transfer (`contentLength() = -1`). Staged share copies use only their own file size, never the entry URI. The descriptor is closed.
   - A per-upload `noRedirectClient.newBuilder().readTimeout(5 min)` copy (shares pool, dispatcher and the origin-restricted auth interceptor) because the server may take long to finalise a large PUT after the last byte. It never follows redirects: OkHttp turns a 301 / 302 / 303 `PUT` into a body-less `GET` whose 2xx would be a false success, so every 3xx fails the item (this also avoids OkHttp keeping `Authorization` on a same-host, same-port https to http redirect); no `callTimeout` (CLAUDE.md rule 7), so large uploads never fail on an overall limit; no in-memory buffering.
   - HTTP 413 maps to a typed "file too large for the server" result and 507 to "server storage full" (new string resources, user-facing, via the existing typed error mapping; `WebDavHttpException(code)`, branch on code, no message parsing). Other failures keep today's behaviour.
   Videos use the same auto date folders, occasion folder, retry file and `isAllowedPhotoUri` check (`content://media/external/video/...`).
9. **Foreground service limits.** With target SDK 37, `dataSync` foreground services have a shared budget (about 6 hours per 24 hours); after exhaustion, and in background-start restrictions, `setForeground()` throws `ForegroundServiceStartNotAllowedException`. Today `doWork` would fail and leave the queue file with no retry file and no notification. Fix: catch the `setForeground` failure (initial call and progress updates) and return `Result.retry()`, keeping the queue file so WorkManager re-runs the work later (explicit exponential back-off on every upload work request). A refused update after the last entry counts as completion. Progress is persisted per entry: after each successful upload the queue file is rewritten atomically (temp file + rename) with an `"uploaded": true` marker and the photo is marked uploaded at once; a re-run skips marked entries, and result, history and notification count the whole batch including earlier runs. Files without markers (older queue and retry files) upload every entry. To end endless loops, once `runAttemptCount + 1` reaches 5 a refused foreground service stops the run with the failure notification and a retry file for the entries not uploaded yet. Only the entry interrupted mid-transfer is sent again (the PUT overwrites; Nextcloud may create an extra file version). No resume of partial files.
10. **Duplicate / blur reviews and albums.** `AlbumsRepository.isImage` drops non-image entries, so no code change; a regression test pins that a video entry is not listed or scanned. Uploaded videos therefore do not appear in the Albums screens (documented in the README).
11. **Share target.** The manifest filters and the image allow-list of `ShareIntentParser` stay as they are.
12. **Filter.** A Photos / Videos filter is deferred; not part of this change.

## Risks / Trade-offs

- A large video interrupted mid-transfer re-uploads from its start after a stop (budget exhaustion, process death, network loss); finished entries are not sent again. The attempt cap counts all runs, including Wi-Fi-only back-offs. Nextcloud chunked upload v2 is a follow-up.
- A single PUT of multi-GB files depends on server / proxy limits (413, 507 are reported distinctly).
- Thumbnail extraction is slower than for images; checked manually for scroll performance.
- The id flag couples grid state to the id scheme; kept in one helper with unit tests.
- Play policy: `READ_MEDIA_VIDEO` needs a Photo and Video Permissions declaration; noted in the README.

## Open Questions

None. Decided: no size-warning dialog, no filter, single PUT with Content-Length when known.
