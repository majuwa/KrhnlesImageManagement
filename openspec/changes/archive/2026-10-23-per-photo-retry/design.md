# Design

## Context

The retry path already exists. `UploadWorker.executeUpload` collects failed indices, `writeRetryQueueFile` stores `{folderName, photos[{id, uri, mimeType, displayName}]}` as `filesDir/retry_queue_<uuid>.json` (same format as `upload_queue_*.json`), and the completion notification carries a "Retry Failed (%d)" action broadcast to `RetryUploadReceiver`, which enqueues an `UploadWorker` tagged `photo_upload`. Photo lists live in files because WorkManager `Data` is limited to 10 KB. `WebDavClient.uploadFile` is a plain `PUT`, which overwrites, so retrying a photo that actually reached the server creates no duplicate.

## Goals / Non-Goals

**Goals:** meet issue #19 robustly with the least change; keep the queue-file format and the `KEY_QUEUE_FILE` input contract.

**Non-Goals:** no persistent failure store, retry badge or history-screen retry; no automatic retries (apart from the WorkManager backoff while Wi-Fi-only is on and the network is metered); no pruning of old retry files; no handling of two photos sharing a display name.

## Decisions

1. **Queue file stays the failure record.** Unchanged.
2. **Per-photo read failures are failures.** A narrow try around `openInputStream` catches `SecurityException`, `FileNotFoundException`, `IllegalArgumentException` (log the class name only); the photo counts as failed and stays in the retry file. `CancellationException` is never caught. The `continue` that skipped `setProgress` / `setForeground` is replaced by control flow that updates progress on success and failure.
3. **Wi-Fi-only everywhere.** `uploadConstraints(wifiOnly)` (`worker/UploadConstraints.kt`) builds the `Constraints`; `readWifiOnly(flow, timeoutMs = 3000)` returns `flow.first()` bounded by `withTimeoutOrNull` inside `runCatching` (cancellation rethrown); timeout / failure -> `true` (unmetered; fail towards not using mobile data). Upload enqueueing moves out of the activity into the process-scoped `UploadEnqueuer(appContext, credentialRepository, appScope)` (`upload/UploadEnqueuer.kt`; `KrhnlesApplication.appScope` is exposed and owns `uploadEnqueuer`). Its non-suspend `enqueue(batches)` launches in `appScope`: bounded `readWifiOnly`, queue files written on `Dispatchers.IO`, `workManager.enqueue(...).await()` per batch, then the toast on Main via the application context. Destroying the activity (rotation, dismissed share dialog) therefore cannot lose an upload, and the activity does no `lifecycleScope` work (the `stateIn(initialValue = false)` race stays removed). Both the main flow and the share target call it; the share path calls `finish()` synchronously afterwards. `ShareReceiverScreen` fires `onConfirm` at most once (a `submitted` flag disables the button), so a double tap cannot enqueue twice. `RetryUploadReceiver.onReceive` calls `goAsync()`, creates a fresh `CoroutineScope(SupervisorJob() + Dispatchers.IO)` per broadcast and delegates to `internal suspend fun handleRetry(context, intent, wifiOnly: Flow<Boolean>, timeoutMs)`; `pendingResult.finish()` runs in `finally`, as does cancelling the scope. `handleRetry` awaits `enqueueUniqueWork(...).await()` so the request is persisted before `finish()`. The work is unique per retry file (`enqueueUniqueWork(retryFileName, ExistingWorkPolicy.KEEP, ...)`): at most one retry runs per retry file at a time; a second tap before the first retry finished is a no-op, a tap after it finished finds no file. Alternative (copy the constraint into the queue file) rejected: it would ignore a later setting change. A setting switched on *after* enqueue is honoured by the worker itself: `doWork()` reads `readWifiOnly` and, if on while `ConnectivityManager.isActiveNetworkMetered` is true, returns `Result.retry()` (WorkManager backoff, queue file untouched) before touching the server. Chosen over re-enqueueing with new constraints because it is a few lines and cannot lose or duplicate work.
4. **Receiver order and validation.** `handleRetry` cancels the notification (id from extras) first, then validates the path: file name matches `retry_queue_[0-9a-f-]+\.json`, canonical parent equals canonical `filesDir`, file exists. Otherwise nothing is enqueued. The worker applies the same check to `KEY_QUEUE_FILE` (also accepting `upload_queue_<millis>_<uuid>.json`). Missing or malformed queue file in the worker -> `Result.failure()`; a malformed file is deleted.
5. **Notification identity.** The foreground / progress notification keeps id 1001. All result notifications use the fixed `RESULT_NOTIFICATION_ID` (1002) with the input queue file name as notification *tag* (`notify(tag, id, ...)`), so batches never collide (no hashing) and never equal 1001. `EXTRA_NOTIFICATION_ID` and `EXTRA_NOTIFICATION_TAG` are passed to the receiver, which calls `cancel(tag, id)`. The retry `PendingIntent` keeps request code 2001 but its intent has a unique data URI `retry://<retryFileName>`, which makes `PendingIntent` identity unique per retry file.
6. **Typed folder-creation error.** `WebDavClient.createDirectory` throws `WebDavHttpException(code)` for non-2xx. The worker maps failures with the upload-specific `FolderCreationError` (`worker/FolderCreationError.kt`): `InvalidFolderName` (the worker validates the folder path before any request: no `.` / `..` / empty segment / backslash), `FolderNotAvailable` (HTTP 403 / 404 / 409: "not found or no permission"), `NotConfigured`, `Connection(AlbumsError)` (certificate, host, unreachable, timeout, 401) which reuses the album wording, and `Generic`; each resolves to a `upload_error_*` string inside `notification_create_folder_failed`. Album-specific wording ("server address is not a valid URL", "album not found") is no longer shown for upload folder problems. The raw `error` message is removed from the failure `Data`; an unconfigured server now also shows a notification. The occasion dialogs (`ui/share/OccasionDialog`, used by the photo grid and the share target) reject `.` / `..` / names containing `/` or `\` with an inline error (`isValidOccasionName`).
7. **Test seam.** `UploadWorker` gets an internal primary constructor `(context, params, credentialRepository: CredentialRepository, clientFactory: (WebDavConfig) -> WebDavClient)` and a public `(context, params)` constructor for WorkManager that supplies `CredentialStore` and `::WebDavClient`. Tests use `TestListenableWorkerBuilder.setWorkerFactory` with `FakeCredentialRepository` and MockWebServer; they call `doWork()` directly because the work-testing scheduler runs workers on its own executor and would hide the `Result`. The internal constructor also takes the `isActiveNetworkMetered` check. `handleRetry` is tested with fake flows, `UploadEnqueuer` with an injected scope / dispatchers and a delegating `CredentialRepository`.
8. **Share URI policy (hardening).** The share target accepts only `content://` URIs of other apps (`isAllowedPhotoUri`: scheme `content`, authority not `<applicationId>` or `<applicationId>.*`, userinfo stripped); `file://` is rejected so a share cannot make the app read its private files. `UploadWorker.openPhoto` repeats the check (defence in depth): a rejected URI counts as a failed photo. Logs contain exception class names only.
9. **Documented limitation.** Share-target URI grants end when `MainActivity` finishes, so retries realistically only succeed for MediaStore URIs; others fail again, bounded and user-driven. Each retry writes its own history entry (photo count = retried photos).

## Risks / Trade-offs

- [Unreadable shared photos fail forever] -> remain retryable; accepted.
- [`goAsync` window ~10 s] -> 3 s timeout leaves headroom.
- [Enqueue runs in the application scope] -> survives activity destruction; only process death during the <=3 s read loses it (bounded, accepted).
- [Wi-Fi-only switched on after enqueue, on mobile data] -> `Result.retry()` with WorkManager backoff (up to hours) until an unmetered network is active.
