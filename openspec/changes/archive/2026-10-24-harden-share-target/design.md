## Context

Observed: manifest already has `SEND` / `SEND_MULTIPLE` `image/*` filters on exported `MainActivity` (standard launch mode, runs in the sender's task). `parseSharedPhotos()` reads `EXTRA_STREAM`, filters with `isAllowedPhotoUri`, queries metadata synchronously from `onCreate`, falls back to mime `image/*`, and sets `id = index` (`ShareIntentParser.kt:45`), which `markAsUploaded` would treat as a MediaStore id. `ShareReceiverScreen` -> `uploadEnqueuer.enqueue(Occasion)` -> `finish()`. Worker re-checks `isAllowedPhotoUri`, treats `SecurityException` as a failed photo, and deletes the queue file at `UploadWorker.kt:95,109,125`. WorkManager may re-run a worker, which re-uploads all entries.

Gaps: (1) the grant is revoked when the receiving activity is finished/destroyed and is not persistable, so the worker can read nothing after `finish()`; (2) no mime check, count/size bounds; (3) main-thread provider IO, state lost/repeated on rotation; (4) no not-configured handling; (5) wrong `id` for shared entries.

## Goals / Non-Goals

**Goals:** reliable upload of shared photos; safe, bounded handling of untrusted input; the four acceptance criteria. **Non-goals:** new filters, video, ClipData fallback (the platform copies `EXTRA_STREAM` into ClipData and senders set `EXTRA_STREAM`), separate activity, per-photo/date folders, persistent grants, FileProvider.

## Decisions

1. **Stage copies before finishing.** After confirm, `ShareViewModel` (public `(Application)` constructor for the default factory, guarded by `ViewModelFactoryRegressionTest`; internal test constructor with dispatcher, clock, staging dir, enqueuer) copies each URI via `openAssetFileDescriptor(uri, "r", CancellationSignal)` on `Dispatchers.IO` into `noBackupFilesDir/share_staging/<uuid>`, then enqueues, then emits a one-shot `finish`. A Job + latch ignores confirm while running/after done; rotation keeps the ViewModel. Rejected: keeping the activity alive until upload ends (breaks rule 4); copying at receipt (wastes work on cancel).
   - Progress: determinate "Preparing x of n" (format string) with a Cancel button.
   - Cancel/Back during the copy cancels the job and publishes `Cancelled` at once (never joins it); a `finally` deletes partial and already staged files of this batch and nothing is enqueued. `onCleared()` performs the same cleanup (task swiped).
   - Provider calls are not interruptible and a provider may ignore cancellation, so every provider call of a share (metadata `getType` + `query(…, signal)`, open + copy) runs as `abandonableCall()`: detached on IO, awaited under a per-item timeout (metadata 10 s → item dropped; open + copy 2 min → skipped as unreadable). Timeout or cancellation cancels the `CancellationSignal` (aborts the provider's open; its cancel listener closes the source stream so a blocked read returns) and returns immediately. A result that never reached the caller (abandoned, or raced by a cancellation) goes to `onAbandoned`, which deletes a complete staged file; the ViewModel records a returned staged name without a suspension point. So no staged file is orphaned and Cancel never waits for a stuck provider (it keeps one IO thread until it returns; accepted).
   - Preparing (config + metadata read) shows an indeterminate progress with Cancel.
   - Enqueue failure after a complete copy deletes the batch's staged files and shows the failure toast.
2. **Bounds.** 100 photos, 100 MiB per file, 1 GiB per share, enforced on bytes copied (counting stream). Items whose reported `OpenableColumns.SIZE` exceeds the cap are pre-skipped. Before copying, check usable space (`StorageManager.getAllocatableBytes` where available, else `usableSpace`, minus a safety margin) and cap the whole `share_staging` folder at 2 GiB (existing staged bytes count). On `IOException` / ENOSPC stop the share, clean up the batch and show one `share_copy_failed` message. Skips carry a reason: unreadable / too large (`share_copy_skipped`, plural with the MB cap) and over the per-share cap (`share_over_share_limit`, plural with the MB cap; also pre-skipped by reported `SIZE`). If every item was skipped the share ends with `NothingCopied` (`share_nothing_copied`), not the storage message. The budgets are per share and computed when its copy starts; concurrent shares (separate tasks) do not share them and can together exceed the folder cap by up to one share (accepted).
3. **Names.** Staged name is a UUID. Remote file name: provider name if a single valid segment (reuse the `WebDavClient` rule) without Unicode Cf characters (bidi controls U+202A–202E / U+2066–2069, U+200E / U+200F, zero-width characters), line / paragraph separators or unpaired surrogates, else a generated `shared_<timestamp>_<short uuid>.<ext>`. The name must end with an extension of the validated type, otherwise that type's extension is appended (`evil.svg` validated as PNG → `evil.svg.png`). Names are de-duplicated within a share; a plain PUT overwrites a same-named file already in the folder (known behaviour, unchanged). Sanitising is for reliability (invalid, colliding or disguised names), not a security boundary; traversal is already blocked by `WebDavClient`.
4. **Queue format and ids.** `UploadQueue` entries get optional `staged` (must match the UUID pattern, canonical parent equals `noBackupFilesDir/share_staging`, accepted only together with `id = -1`; otherwise the entry is rejected). Shared entries are written with `id = -1`; the worker never calls `markAsUploaded` for them. A staged entry keeps its `uri` string, but the worker reads only the staged file and never falls back to `uri` when it is missing (the photo fails); staged entries never touch `contentResolver`. `toRetryJson` copies `staged`. Old queue files parse unchanged. `isAllowedPhotoUri` unchanged for URI entries. CLAUDE.md rule 4 gets the staged exception.
5. **Cleanup.** No deletion per successful upload (a WorkManager re-run re-uploads all entries, so the staged files must survive until the queue is final). One helper deletes a queue file's staged files, except those referenced by a newly written retry file, and is used at every `queueFile.delete()` site (`UploadWorker.kt:95,109,125`) and by the worker's NotConfigured path. Sweep: runs on `Dispatchers.IO` off the confirm path; deletes staged files older than 7 days (injectable clock/dir) that are not referenced by an `upload_queue_*` file; a file referenced by retry files is deleted together with them only if every such retry file is itself older than 7 days by its own mtime (`handleRetry` refreshes it on each tap, so the window restarts) and has no unfinished unique retry work (`getWorkInfosForUniqueWork(retryWorkName)`, bounded 5 s; unknown counts as unfinished) — retry window 7 days, documented in README. The sweep fails closed: if a queue file is unreadable or vanishes during the scan it deletes nothing (or lists twice and compares).
6. **Parsing.** `parseSharedPhotos` is a pure extraction of `EXTRA_STREAM` (single/list) into `SharedItems(uris, truncated, rejected)`, catching any `RuntimeException` while reading the extra (incl. `BadParcelableException` / `ClassCastException`; types only logged). Order: `isAllowedPhotoUri`, dedupe, cap 100. Provider `query()` and `getType` run on IO (see 1) and catch `SecurityException`, `IllegalArgumentException`, `IllegalStateException`, `OperationCanceledException`. Type: a concrete provider type decides alone; if it is null, `application/octet-stream` or a wildcard, the `DISPLAY_NAME` extension decides via `MimeTypeMap` (a known non-image extension drops); without a known extension a concrete `intent.type` (never `image/*`). The result must be allow-listed raster: JPEG, PNG, GIF, WebP, HEIC, HEIF, AVIF, BMP, DNG (aliases `image/jpg`, `image/pjpeg`, `image/x-ms-bmp`, `image/dng` normalized); SVG and all other types are dropped. `id = -1`, `dateTaken` today.
7. **Not configured / nothing usable.** `ShareViewModel` reads one `webDavConfig.first()` under a 3 s `withTimeoutOrNull`, defaulting to configured on timeout (the worker reports failures). Not configured -> Toast (or dialog) with a "set up server" message; if an "open app" action is kept it starts `MainActivity` with `FLAG_ACTIVITY_NEW_TASK`. No usable photo -> Toast `share_no_photos` and `finish()`, no app launch. No extra intent flag.
8. **Manifest.** Keep `exported=true`; no new permissions; standard launch mode; no `onNewIntent`.
9. **Strings** (plurals for counts): `share_not_configured_*`, `share_no_photos`, `share_skipped_photos`, `share_too_many_photos`, `share_copy_failed`, `share_preparing` (x of n).

## Risks / Trade-offs

- Confused deputy: the exported activity reads shared URIs with the app's own identity, so a sender can make it read a URI only this app can read (e.g. MediaStore with the app's media permission). Accepted: the photo only goes to the user's own server after the user confirmed the count and an occasion; own authorities and `file://` stay rejected.

- Copying delays dismissal -> progress, cancel, bounds, space check.
- Staged files live until the queue is final or 7 days -> sweep.
- Process death during copy loses only that share; partial files are removed by the next sweep (age rule).
