## Context

- `KrhnlesApp.kt` uses a fixed `startDestination = ROUTE_PHOTOS`; the bottom bar shows only on `photos` / `albums`. `MainActivity` renders `ShareReceiverScreen` instead of `KrhnlesApp` for share intents.
- `CredentialStore` owns the credentials DataStore (excluded from backup) with `isConfigured`, `webDavConfig` and `credentialState` flows. There is no app-level preferences store.
- CLAUDE.md: ViewModels never reference each other; one-shot flow reads use `first()`; guards must be released; locks/waits have timeouts.
- Verified (Context7): Preferences DataStore reads throw `IOException` (`CorruptionException` for a corrupt file) which must be caught; `navigate(route) { popUpTo(x) { inclusive = true } }` removes x; the NavHost start destination is fixed when the graph is created.

## Goals / Non-Goals

**Goals:** one-time, skippable two-page introduction; safe for existing users (including corrupted-credential upgrade users); no flash of a wrong destination; share intents unaffected.
**Non-Goals:** extracting or reusing Settings / grid composables, a permission step, in-flow login, base-folder or connection-test steps, a "replay onboarding" entry, localisation beyond `values/` (only that locale exists).

## Decisions

1. **Persistence.** `OnboardingRepository { val completed: Flow<Boolean>; suspend fun markCompleted() }` in `data/Repositories.kt`. `OnboardingStore` implements it on its own DataStore `app_preferences` (key `onboarding_completed`, boolean). Public constructor takes a `Context` (production DataStore delegate with a `ReplaceFileCorruptionHandler` that resets a corrupt file); an `internal` constructor takes a `DataStore<Preferences>` so tests can use `PreferenceDataStoreFactory.create` with a temp file. `completed` is `data.catch { if (it is IOException) emit(emptyPreferences()) else throw it }.map { it[KEY] ?: false }` so a read failure means "unset". Rejected: deriving purely from "not configured" (re-shows after logout), reusing the credentials DataStore (mixed concerns, deliberate backup exclusion).
2. **Who is an "existing user".** `isExistingUser = config.isValid (isConfigured) || config.url.isNotBlank() || credentialState != Missing`. Rationale: a user upgrading with a stored URL but credentials that no longer decrypt (`Corrupted`) or a half-saved setup is not a first-time user and Settings already explains the credential problem; showing onboarding would be wrong. Cost: a user who typed a URL and never finished login is also treated as existing and never sees onboarding; acceptable. Pure functions `isExistingUser(...)` and `resolveStartDestination(completed, existingUser)` (`Onboarding` iff `!completed && !existingUser`, else `Photos`) in `ui/onboarding/StartDestination.kt`, covered by a truth-table test.
3. **Start decision.** `StartupViewModel` (`AndroidViewModel`, `@JvmOverloads` constructor with defaults `OnboardingStore(application)`, `CredentialStore(application)`, timeout 3 s) exposes `StateFlow<StartDestination?>` (`null` = resolving). It reads `completed` and one `combine(webDavConfig, credentialState).first()` snapshot (configured = `config.isValid`; one Keystore decrypt pass, consistent values) inside `withTimeoutOrNull`; timeout or any non-cancellation failure resolves to `Photos` (never wrongly onboarding, never blocking the app). Resolution runs only once per ViewModel. If `!completed && existingUser` it silently calls `markCompleted()` (failure ignored, logged by class name only).
4. **Gating and splash.** `KrhnlesApp` keeps the resolved route in `rememberSaveable`; a restored value is used immediately without waiting for the ViewModel. While neither exists, a full-size box with the theme background is shown instead of the `NavHost`. Splash decision (honest): the platform splash disappears on the first frame and we add no dependency (`androidx.core.splashscreen`) and no `OnPreDrawListener` hack; so there can be a brief neutral, theme-colored frame (typically 1-2 frames; at most the 3 s timeout if the store hangs) but never the wrong destination. The share path never composes `KrhnlesApp`, so share intents on a first launch behave as before and neither read nor set the flag.
5. **Route and back stack.** Tab navigation uses `popUpTo(ROUTE_PHOTOS)`, never the graph start destination (the start may be onboarding, which is not on the back stack after leaving it). `ROUTE_ONBOARDING = "onboarding"`; bottom bar already only on `photos` / `albums`. `OnboardingViewModel` (`AndroidViewModel`, non-null `SavedStateHandle`: public `(application, savedStateHandle)` constructor for the default `SavedStateViewModelFactory` plus an internal `(application, savedStateHandle, repository)` constructor for tests; guarded by a constructor-existence test and a recreation test) holds `page` (0 or 1, in `SavedStateHandle`), `isFinishing` and a one-shot `exit: OnboardingExit?` (`Photos` for Skip, `Settings` for the CTA). `finish(exit)` ignores re-entry while a `Job` is active, persists inside `withTimeoutOrNull(3 s)` (rethrow `CancellationException`; a persist failure or timeout still exits, logged by class name only), sets `exit` only after persisting and then sets a never-reset `done` latch (`finish()` stays ignored after `consumeExit()`, `isFinishing` stays true so the buttons stay disabled); on cancellation the guard is released in `finally`. The screen consumes `exit` once and the host runs `NavController.completeOnboarding(exit)`:
   - Photos: `navigate(photos) { popUpTo(onboarding) { inclusive = true } }`.
   - Settings: the same, then `navigate(settings)`. Back stack ends `photos`, `settings`, so Back from Settings lands on Photos. (`photos` replaces onboarding even when it was the start destination.)
6. **Pages and back.** Page 0 Overview: title, description of the purpose, "Next" and "Skip". Page 1 Connect: title, short instruction text (open Settings, log in with Nextcloud or enter WebDAV data), "Connect now" and "Skip". Step text "Step N of 2" is visible. `BackHandler(enabled = page > 0 && !isFinishing)` goes to page 0; on page 0 the handler is disabled so the system exits the app and nothing is persisted (onboarding appears again next launch, intended since neither skipped nor completed). Layout scrolls for large fonts.
7. **Accessibility / strings.** All text in `values/strings.xml` with `onboarding_` prefix (only locale). The page title uses `Modifier.semantics { heading() }` and the page container `paneTitle`, so a page change is announced. Decorative icons have no content description. Tests assert semantics (heading, pane title, enabled/disabled state), not pixel layout.
8. **Backup.** `datastore/app_preferences.preferences_pb` is excluded in `backup_rules.xml` and in both the `cloud-backup` and `device-transfer` sections of `data_extraction_rules.xml`. Without it, a restore with the flag but without credentials (credentials are excluded) would skip onboarding on a device that has no server configured. A regression test parses all three sections.
9. **Security.** No credential handling in onboarding. The store holds only a boolean. Settings is opened through plain navigation.

## Risks / Trade-offs

- [Existing unconfigured user sees onboarding once] -> acceptable, Skip is one tap.
- [Brief neutral frame at start] -> documented in decision 4; bounded by timeout.
- [Process death between persisting the flag and navigating] -> user lands on the photo grid, CTA lost; acceptable.
- [User with only a typed URL treated as existing] -> decision 2, accepted.

## Migration Plan

No data migration. First start after the update: configured / partially configured users get the flag silently; unconfigured users see onboarding once. Rollback: unused DataStore file remains harmless.
