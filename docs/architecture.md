# Architecture

## Overview

Kröhnle's Image Management follows **MVVM + Clean Architecture** using Kotlin and Jetpack Compose.

## Authentication

Two authentication methods are supported:

1. **Nextcloud Login Flow v2** (recommended): Opens the Nextcloud login page in the browser. The app polls for completion and receives an app-specific token. Follows the same pattern as the android-paper-reader reference project.
2. **Manual WebDAV config**: Direct URL, username, and password/app token entry for non-Nextcloud WebDAV servers.

Credentials are stored securely:
- URL and base folder in DataStore Preferences
- Username and password/app token encrypted via Android Keystore (AES-256-GCM) in standard SharedPreferences
- Crypto lives in `CredentialCipher` (format `Base64([ivLen][iv][ciphertext+tag])`), backed by an injectable `CredentialKeyProvider` (`AndroidKeystoreKeyProvider` in production, a software AES key in unit tests because the Keystore is unavailable under Robolectric)
- `CredentialCipher.decrypt()` maps missing values, format violations and every `GeneralSecurityException` / `ProviderException` / `IOException` to `DecryptResult.Missing`, `Success`, or `Failure(reason)` (other runtime exceptions are not caught) where the reason is `KEY_INVALIDATED` (`KeyPermanentlyInvalidatedException` / `UnrecoverableKeyException` / `UnrecoverableEntryException` anywhere in the cause chain) or `UNREADABLE` (malformed data, GCM tag mismatch, lost key, `UnexpectedKeyEntryException` when the alias holds a non-secret-key entry, other Keystore errors)
- Corrupted encrypted values fail closed (treated as not configured, never used for requests) and failures are logged via `Log.w` with field name and exception type only — never ciphertext or plaintext; a persisting failure is logged once per field until its outcome changes
- All credential-derived flows (`credentialState`, `isConfigured`, `webDavConfig`, `username`) derive from one private snapshot flow that decrypts both fields once per DataStore emission and runs `flowOn(ioDispatcher)` (internal constructor parameter, default `Dispatchers.IO`) to keep Keystore work off the main thread
- Because DataStore does not observe the secure SharedPreferences, `save()` and `clear()` bump a `credentials_version` key in the same DataStore edit, forcing an emission even when the server URL is unchanged
- `save()` is ordered for atomicity: encrypt both values → `commit()` them to the secure prefs → DataStore edit (`server_url` + version bump). A failed encryption leaves the previous credentials and URL untouched; failures surface as `CredentialSaveException`, which `SettingsViewModel` turns into `R.string.error_credentials_save_failed` instead of crashing
- Non-credential preferences share this DataStore: `wifiOnly`, `autoDateFoldersEnabled` and `blurSensitivity` (string key `blur_sensitivity`, value = `BlurSensitivity` enum name, plain `edit` without a `credentials_version` bump). `blurSensitivity` is read via `prefs.asMap()[KEY] as? String` so a wrong-typed value falls back to Medium instead of throwing; unknown / blank names also give Medium. Like the whole file it is excluded from backup and device transfer, so the setting is not restored on a new device (issue #20 / #39)
- `CredentialRepository.credentialState` exposes `CredentialState.Missing / Valid / Corrupted(reason)`; `SettingsViewModel` maps it to `SettingsUiState.credentialProblem` and the login screen shows a localized banner explaining why the user must log in again (issue #31 / #50)
- If obtaining the key or initialising the cipher during encryption fails with an error classified as `KEY_INVALIDATED` (same cause-chain predicate as decrypt), `CredentialCipher.encrypt()` deletes the key, regenerates it, and retries once, so re-login after a security-settings change succeeds; other errors propagate without deleting the key

## Navigation & Album State Scoping

`KrhnlesApp.kt` hosts a single `NavHost`. The album flow is split into one ViewModel per responsibility, each scoped to the back-stack entry of the route that owns it (issues #29 / #48):

| Route | ViewModel (scope) | Used by |
|---|---|---|
| `albums` | `AlbumsViewModel` (own entry) | album list, rename / delete album |
| `albums/detail?href={href}` | `AlbumDetailViewModel` (own entry) | detail screen; shared with viewer and reviews |
| `albums/viewer` | — (detail entry's `AlbumDetailViewModel`) | fullscreen viewer |
| `albums/duplicates` | `DuplicatesViewModel` (own entry) + detail's `AlbumDetailViewModel` | duplicate review |
| `albums/blur` | `BlurViewModel` (own entry) + detail's `AlbumDetailViewModel` | blur review |

Sub-routes of an album obtain the detail ViewModel via the private helper `sharedAlbumDetailViewModel()`; `getBackStackEntry()` matches the detail route *pattern* (`ROUTE_ALBUM_DETAIL_PATTERN`):

```kotlin
composable(route) { backStack ->
    val detailVm = sharedAlbumDetailViewModel(navController, backStack)
    // = viewModel(rememberParentEntry(navController, backStack, ROUTE_ALBUM_DETAIL_PATTERN))
}
```

The review ViewModels are created with plain `viewModel()` in their own destination, so leaving a review clears them and cancels a running scan. Reviews get the album's photos, thumbnail URLs and the detail ViewModel's repository as arguments (`findDuplicates(photos, thumbnailUrls, detailVm.repositories)` / `findBlurryPhotos(photos, thumbnailUrls, repositories, sensitivity)`) — ViewModels never hold references to each other, and one album flow uses one `AlbumsRepository` (one OkHttp client) whose lifetime is the detail entry, which always outlives the reviews opened from it.

**Scans** — both reviews run the shared `scanAlbumPhotos()` (`ui/albums/PhotoScan.kt`): repository from the source, then the analyzer (`PhotoAnalyzer`; the blur scorer is created inside the error handling and closed only if created), then per photo resolve URL → download → analyze → `recycle()` in `finally` → `ensureActive()` → progress. A failing photo is skipped; cancellation is rethrown (neither a skipped photo nor an error); any other failure is a `PhotoScanOutcome.Failed(AlbumsError)`. Before every photo the loop asks the source again (`repositories.get()`): if it fails or no longer returns the repository the scan started with (logout, server / account change) the scan stops with `AlbumsError.ConfigurationChanged` / the typed failure, so no further request goes to the old server. Analysis (`PhotoAnalyzer.analyze`) runs on an injectable dispatcher (`analysisDispatcher`, default `Dispatchers.Default`), never on Main. Robolectric Compose UI tests inject `Dispatchers.Unconfined`: `waitUntil {}` does not drain the paused main looper, so a result resumed from a real background pool after the last `waitForIdle()` would hang the scan, timing-dependently (`RobolectricAnalysisDispatcherRegressionTest`). Each review ViewModel tracks its `scanJob`: `cancelScan()` (album became unavailable), `reset…State()` and a new scan cancel it, so two scans never publish concurrently; results are published only after `ensureActive()`. A scan starts only from `Idle` (`findDuplicates` / `findBlurryPhotos`), and Retry calls `retryFindDuplicates` / `retryFindBlurryPhotos`, which only run from `Error` and ignore an empty photo list (never turns an error into "none found"). So recreating the screen (rotation) never restarts a scan, never discards `Found` and never overwrites `Deleting`. `rememberReviewSelection()` pre-fills the selection once per result and keeps the user's choices across recreation (`ReviewSelectionTest`).

**Review ↔ album lifecycle** — the review screens take the album href and use `rememberReviewAlbumReady()` (`ReviewSelection.kt`): it calls `AlbumDetailViewModel.loadAlbum(href)` (no-op if loaded, so a review restored after process death loads its album), starts the scan only once the album `isLoaded` (never reports "none found" for an unloaded / loading / failed album), and on `NotConfigured` / `ConfigurationChanged` calls `cancelScan()` (state back to `Idle`, results dropped; not while `Deleting`, re-evaluated when it ends). `ReviewAlbumGate` shows the album error (Retry → `reload()`) or a progress indicator instead of the scan states.

**Blur sensitivity** — `findBlurryPhotos` / `retryFindBlurryPhotos` take the level as a `Flow<BlurSensitivity>` argument (the `albums/blur` destination passes `CredentialStore.blurSensitivity` to `BlurReviewScreen`; never a collected State value, so `BlurViewModel` stays a plain ViewModel). The scan job reads it once with `first()` after `Scanning` is published, bounded by `withTimeoutOrNull(3 s)` inside `runCatching` (cancellation rethrown); timeout or failure gives Medium. The level is fixed for that scan; a change in Settings applies to the next scan / Retry (no re-filter, no rescan). Photos with `score < threshold` are blurry; the thresholds are unvalidated heuristics (Memories previews and downsampled originals score differently) and are retuned only in `BlurSensitivity`. The Settings slider (`SettingsScreen`, logged-in content) derives its position from the hoisted level, persists in `onValueChange` whenever the rounded level changes (optimistic UI update in `SettingsViewModel.setBlurSensitivity`; the stored-value collector is ignored while a save is pending so a fast drag does not flicker, and a failed save restores the persisted level and shows `error_blur_sensitivity_save_failed`). Logout (`CredentialStore.clear()`) resets the level to Medium like the other preferences. `CredentialStore.snapshot` de-duplicates its DataStore inputs (server URL, base folder, `credentials_version`) before decrypting, so these preference writes never re-emit the credential flows; `credentialDataStore` is `@VisibleForTesting` and only used inside `CredentialStore.kt` (`NoCredentialDataStoreAccessRegressionTest`) and is a single accessibility node (content description = title, state description = level label; the visible texts are hidden from semantics).

**Repositories** — `AlbumsViewModel` and `AlbumDetailViewModel` own an `AlbumsRepositoryProvider` (`data/`, implements `AlbumsRepositorySource`). `get()` returns a `Result` and never throws (except cancellation): no complete credentials → `AlbumsRepositoryUnavailableException(NOT_CONFIGURED)`, a factory `IllegalArgumentException` (invalid URL) → `INVALID_CONFIGURATION`, lock not acquired / config not read within 10 s → `TIMEOUT`. Every `get()` re-reads the config and rebuilds when it differs from the cached one; calls are serialized by a `Mutex` (`withTimeoutOrNull`, CLAUDE.md lock rule) so concurrent callers share one instance; `invalidate()` bumps a generation so a build overlapping it is returned but never cached. `get()` itself picks up configuration changes, so `AlbumsViewModel.loadAlbums()` needs no explicit `invalidate()`. `AlbumDetailViewModel.loadAlbum(href)` is a no-op when the same album is already loaded or loading without error (a recreated screen never reloads, which could resurrect photos during a deletion); `reload()` is the explicit Retry. `AlbumDetailViewModel` additionally observes `webDavConfig` (`distinctUntilChanged().drop(1)`): on logout / server or account change it cancels a running load and deletion, invalidates and clears the album with `AlbumsError.NotConfigured` / `ConfigurationChanged`.

**Errors** — album list, detail and review states hold a typed `AlbumsError` (never exception text). `Throwable.toAlbumsError()` maps provider failures and reuses the connection-test classification (`toConnectionTestResult()`: TLS, DNS, unreachable, timeout, 401/403, 404, other HTTP); `albumsErrorMessage(resources, error)` resolves `R.string.albums_error_*`. The detail screen offers Retry except for `NotConfigured` / `ConfigurationChanged`. Only exception class names are logged.

Album ViewModels keep an `(Application)` constructor for the default factory (`ViewModelFactoryRegressionTest`): `AlbumsViewModel` / `AlbumDetailViewModel` via `@JvmOverloads (Application, credentialRepo, repoFactory)`, while `BlurViewModel` (`@JvmOverloads (blurScorerFactory, analysisDispatcher)`; the sensitivity source is a per-call argument) and `DuplicatesViewModel` (`@JvmOverloads (analysisDispatcher)`) are plain `ViewModel`s with a no-arg constructor (`PlainViewModelFactoryRegressionTest`).

After process death a restored review entry gets a fresh detail ViewModel; the review loads the album itself (`loadAlbum(albumHref)`) and scans once it is loaded.

`rememberParentEntry()` (`ui/navigation/BackStackEntries.kt`) remembers `navController.getBackStackEntry(parentRoute)` keyed on the destination's own `NavBackStackEntry`: the lookup is cached across recompositions and re-resolved whenever the current entry changes, which is the form the navigation-compose `UnrememberedGetBackStackEntry` lint check accepts. Keying on a constant such as the route string is forbidden, and the check must never be silenced (issues #24 / #43).

`NoLintSuppressionRegressionTest` (backed by `LintSuppressionScanner` in the test source set) enforces this in `./gradlew test`: it scans every source set under `app/src` (`.kt`, `.kts`, `.java`) for `@Suppress`/`@SuppressLint`/`@SuppressWarnings` (any use-site target such as `@file:`, qualified or not, single- or multi-line) and `noinspection` comments naming the issue, and fails if `app/build.gradle.kts`, `app/lint*.xml`, any `app/*baseline*.xml` or the root `lint.xml` mention the issue id at all. The module and root directories are passed to unit tests as the system properties `krhnles.moduleDir` / `krhnles.projectDir` (`testOptions.unitTests.all` in `app/build.gradle.kts`); the test falls back to the working directory and fails loudly if `src/main` is not found. The test spells the issue id as a concatenation so the scan of its own source set does not flag its fixtures.

## Onboarding & Start Destination

`KrhnlesApp` asks `StartupViewModel` once for the start route. Onboarding is the start iff `onboarding_completed` is unset **and** the user is not existing (valid config, any stored server URL, or `credentialState != Missing`, so upgrade users with corrupted credentials never see it). Existing users without the flag get it set silently. Resolution has a 3 s timeout; timeouts and failures resolve to `photos`. The resolved route is kept in `rememberSaveable` (a restored value is used without waiting). While unresolved only the theme background is drawn: the platform splash dismisses at the first frame and no splash dependency is added, so a brief neutral frame is possible but a wrong destination never is. The share path (`ShareReceiverScreen`) never composes `KrhnlesApp`, so share intents are unaffected.

The `onboarding` route has two pages (Overview, Connect) with Skip on both. `OnboardingViewModel.finish()` persists the flag (3 s timeout; a timeout or failure still exits), then emits a one-shot `OnboardingExit`; `NavController.completeOnboarding()` navigates to `photos` with `popUpTo(onboarding){inclusive}` and, for "Connect now", then to `settings`, so the stack is `photos`, `settings`. A never-reset `done` latch keeps `finish()` ignored and the buttons disabled after the exit was consumed. Tab navigation uses `popUpTo(photos)`, not the graph start (which may be onboarding). `StartupViewModel` reads `combine(webDavConfig, credentialState).first()` once. Back on page 0 exits the app without persisting. `datastore/app_preferences.preferences_pb` is excluded from cloud backup and device transfer.

## Accessibility (TalkBack)

Issues #30 / #49. Photo grids never announce raw file names.

- **Local grid** (`ui/photogrid/PhotoGridScreen.kt`): `PhotoItem` and `DateHeader` are `Modifier.toggleable(value, role = Role.Checkbox)` followed by a `semantics {}` block that sets `stateDescription` and `onClick(label) { onClick(); true }`. The labelled action is the real callback (never a stub), so `performSemanticsAction(SemanticsActions.OnClick)` fires it exactly once; `toggleable` already merges descendants, so no extra `mergeDescendants`. The image, uploaded badge, selection icon and the header `Checkbox(onCheckedChange = null)` are decorative.
- **Descriptions:** items read "Photo N of M, taken on <date>" (`cd_photo_position_taken_on`) or "..., date unknown"; videos "Video N of M, <duration>, taken on <date>" (`cd_video_position_*`, duration via `durationDescription()` from the `duration_*` plurals, left out when unknown or zero). The play icon and the duration badge are decorative (`contentDescription = null`, badge `clearAndSetSemantics {}`). The uploaded flag is part of the state ("Selected, already uploaded"). The header is described by its merged texts (date + `item_count` plural over all media of the day) and is a `heading()`; its action labels are "Select / Deselect all items of this day".
- **Dates:** formatted once per date with `remember(locale) { ofLocalizedDate(LONG).withLocale(locale) }`, `locale = LocalConfiguration.current.locales[0]`. `MediaRepository.dateTakenOf()` maps a missing `DATE_TAKEN` (null or 0) to `Photo.UNKNOWN_DATE` (`LocalDate.EPOCH`), shown as "Unknown date"; negative values are real pre-1970 dates. The sentinel is checked only via `LocalDate.isKnownDate()` / `Photo.hasKnownDate`. A genuine photo dated local 1970-01-01 also shows as unknown (accepted). `ShareIntentParser` uses today (known). Auto date upload (`resolveAutoDateUploadBatch`) puts unknown-date photos into `1970/01/01` (pinned by `UploadBatchTest`); pre-1970 photos keep their real date folder. The per-date strings are precomputed with `remember(photosByDate.keys, dateFormatter, unknownDateText)`; the decorative header `Checkbox` keeps `minimumInteractiveComponentSize()` so the header height is unchanged.
- **Remote grids and viewer:** `photoPositionDescription(position, total)` (`ui/components/PhotoDescriptions.kt`, "Photo N of M") for album detail, blur / duplicate review and the fullscreen viewer.
- **Tests:** `PhotoGridAccessibilityTest` (Robolectric Compose; `LocalAsyncImagePreviewHandler` + `LocalInspectionMode` keep `AsyncImage` side-effect free) and `NoFilenameContentDescriptionRegressionTest` (regex scan of `ui/**` for `contentDescription = ...displayName`, module dir via `krhnles.moduleDir`). Manual TalkBack verification remains a device check.

## Data Flow

1. **Photo Loading**: `MediaRepository` queries `MediaStore.Images` and `MediaStore.Video` → merged, grouped by date in `PhotoGridViewModel` (see [Videos](#videos-issues-15--34))
2. **Selection**: User taps photos or date headers → selection state in ViewModel
3. **Upload Trigger**: FAB → occasion dialog *or* auto date preview dialog → exactly one `UploadBatch` per selection → `UploadEnqueuer` → one `WorkManager.enqueue(UploadWorker)` call
4. **Upload Execution**: `UploadWorker` reads config from `CredentialStore`, creates the remote folder(s) via `WebDavClient.createDirectories()`, uploads each file via `WebDavClient.uploadFile()` (streamed request body, no full in-memory byte copy), records each successfully uploaded photo ID right after its upload via `UploadedPhotosStore.markAsUploaded()` and persists the entry's `uploaded` marker in the queue file
5. **Progress**: Worker emits progress via `setProgress()` and shows system notifications
6. **History**: Upload outcomes are persisted via `UploadHistoryStore` and shown on the Upload History screen
7. **Album Management**: The Albums flow lists remote directories and can rename an album in place via `WebDavClient.renameDirectory()` using WebDAV `MOVE`, updating UI state without re-fetching the full album list. The MOVE is hardened: `renameDirectory()` awaits the call cancellably (`awaitStatus()`, no `callTimeout`) on a non-redirecting client derived from the shared one, sends the source as collection URL (trailing slash) with `Overwrite: F`, accepts only 201 / 204 and otherwise throws `WebDavHttpException(code)`. `renameDirectory(oldSegments, newSegments)` takes decoded segment lists (never joined strings) and rejects blank segments, `\\` and ISO control characters instead of filtering them. `AlbumsRepository.renameAlbum()` trims and re-validates the name with `isValidOccasionName` (`InvalidAlbumNameException`) and `exceedsAlbumNameLimit` (255 UTF-8 bytes, `AlbumNameTooLongException`), requires the source exactly one level below the base folder without empty / blank segments (`UnsafeHrefException`), and runs in `resultOf {}` (no request on rejection). A 2xx other than 201 / 204 maps to `AlbumsError.RenamePartial` and, like a timeout, reloads the list. The success branch drops another entry with the new href (duplicate grid keys). `AlbumsScreen` consumes the rename outcome only after its snackbar was shown, so a rotation does not lose it. `WebDavClient`'s interceptor adds `Authorization` only for the configured origin (`hasSameOriginAs`). `AlbumsViewModel.renameAlbum()` is a guarded one-shot (`renameJob`, `withTimeoutOrNull(30 s)`, failures become a `RenameOutcome` exposed as one-shot `renameOutcome` / `consumeRenameOutcome()`, busy flag reset in `finally`); a timeout reports `AlbumsError.RenameTimedOut` and reloads the list, and Refresh is ignored while a rename runs. `Throwable.toRenameAlbumError()` maps 412 -> `AlreadyExists`, 404 / 409 -> `AlbumGone`, 400 / 403 -> `RenameRejected`, everything else via `toAlbumsError()`. Pending uploads / retry queues keep the old folder name (known limitation)

### Retry of failed photos (issues #19 / #38)
- **Queue file as failure record**: after a partial upload `UploadWorker` writes `noBackupFilesDir/retry_queue_<uuid>.json` (same format as the input queue, failed photos only: a top-level `folderName`, or for auto date uploads a `folderName` on every entry plus the top-level `label`; each failed photo keeps its own folder, folders are never re-derived) and the completion notification gets a "Retry Failed (N)" action to `RetryUploadReceiver`. Only names `retry_queue_[0-9a-f-]+.json` / `upload_queue_<millis>_<uuid>.json` directly in `noBackupFilesDir` (new files; excluded from cloud backup and device transfer automatically because they contain per-photo capture days; `UploadEnqueuer` writes there too) or in the legacy `filesDir` (files and retry notifications of older versions) are accepted, no other parent (receiver and worker, `isRetryQueueFile` / `isWorkerQueueFile` in `worker/QueueFiles.kt`, canonical-parent check, so subdirectories and traversal are rejected). A missing or malformed queue file in the worker ends with `Result.failure()`; a malformed file is deleted. The format is decided from the content (`parseUploadQueue`, `worker/UploadQueue.kt`), never from a version field; `folderName` / `label` are read strictly with `opt(key)` + `is String` (Android `org.json` `getString` / `optString` would coerce `5` or `null` to strings). See *Upload Path Construction* for the rules.
- **Per-photo read failures**: a narrow try around `openInputStream` (`SecurityException`, `FileNotFoundException`, `IllegalArgumentException`; class name logged only) counts the photo as failed and keeps it in the retry file; progress / foreground updates run for failed photos too. `CancellationException` is never caught.
- **Wi-Fi-only** (`worker/UploadConstraints.kt`): `uploadConstraints(wifiOnly)` builds the constraint for the original upload and the retry; `readWifiOnly(flow)` reads `first()` bounded by `withTimeoutOrNull(3 s)`, timeout / failure -> unmetered. Enqueueing lives in the process-scoped `UploadEnqueuer` (`upload/UploadEnqueuer.kt`, owned by `KrhnlesApplication.uploadEnqueuer`, scope `KrhnlesApplication.appScope`): non-suspend `enqueue(batches)` launches in the application scope, reads the setting with `readWifiOnly`, writes the queue files, awaits `workManager.enqueue(...)` and then shows the toast on Main, so an upload is never lost when the activity is destroyed (rotation, dismissed share dialog). The share path calls it (with an `onFailure` callback that deletes the staged copies) only after copying, then `finish()`es; `ShareViewModel` ignores every confirm after the first. A queue file whose WorkManager enqueue fails is deleted. A setting switched on after enqueue is honoured by `UploadWorker.doWork()`: Wi-Fi-only on and `isActiveNetworkMetered` -> `Result.retry()` (WorkManager backoff, queue file kept). Settings shows the toggle as a single `toggleable(role = Role.Switch)` row (`wifiOnlyRow`, label and hint merged, inner `Switch` non-interactive, 48 dp minimum height). The setting is off by default, reset by `CredentialStore.clear()` (logout) and, living in the credentials DataStore, not restored from backup. `UNMETERED` means unmetered, not Wi-Fi: a metered hotspot waits, an unmetered cellular plan uploads. Work enqueued with the setting on stays constrained after it is switched off until an unmetered network is available or the user retries.
- **Receiver**: `onReceive` uses `goAsync()` with a fresh `CoroutineScope(SupervisorJob() + Dispatchers.IO)` per broadcast, delegates to `internal suspend fun handleRetry(context, intent, wifiOnly: Flow<Boolean>, timeout)` and calls `finish()` in `finally`. `handleRetry` cancels the notification from the extras (tag + id) first, then validates the file, then `enqueueUniqueWork(retryFileName, ExistingWorkPolicy.KEEP, ...).await()` (tag `photo_upload`), so the request is persisted before `finish()`. At most one retry runs per retry file at a time; a later tap after it finished finds no file and does nothing (old retry files are not pruned).
- **Notification ids**: the foreground / progress notification keeps id 1001; every result notification (success, partial, failure, folder-creation failure) uses `UploadWorker.RESULT_NOTIFICATION_ID` (1002) with the input queue file name as notification tag (`notify(tag, id, ...)`; no hash, no collisions). The retry `PendingIntent` has a unique data URI `retry://<retryFileName>` because `PendingIntent` identity ignores extras. The receiver cancels exactly the tag + id carried in the extras.
- **Folder-creation failure**: `WebDavClient.createDirectory` / `createDirectories` return a `Result` whose failure is a `WebDavHttpException(code)`; the worker first validates the folder path (`isValidFolderPath`: no `.` / `..` / empty segment / backslash) and maps failures with `FolderCreationError` (`worker/FolderCreationError.kt`: `InvalidFolderName`, `FolderNotAvailable` for 403 / 404 / 409, `NotConfigured`, `Connection(AlbumsError)`, `Generic`) into `notification_create_folder_failed` with `upload_error_*` reasons (never raw exception text, never album wording). `OccasionDialog` (`ui/share`, used by the photo grid and the share target) rejects `.` / `..` / `/` / `\` names inline (`isValidOccasionName`).
- **Test seam**: `UploadWorker` has an internal constructor `(context, params, CredentialRepository, (WebDavConfig) -> WebDavClient)`; WorkManager uses the public `(context, params)` constructor (`CredentialStore`, `::WebDavClient`). `UploadWorkerRunTest` runs the real worker with `TestListenableWorkerBuilder.setWorkerFactory`, `FakeCredentialRepository` and MockWebServer; The tests call `doWork()` directly (the work-testing scheduler would hide the `Result`); the internal constructor also takes the metered-network check. `RetryUploadReceiverTest` calls `handleRetry` with fake flows; `UploadEnqueuerTest` injects scope and dispatchers.
- **URI policy**: the share target (`parseSharedPhotos(intent, ownPackage)`) and `UploadWorker.openPhoto` only accept `content://` URIs whose authority is not the app's own (`isAllowedPhotoUri`); `file://` URIs are rejected (a rejected queue entry counts as a failed photo). Log lines contain exception class names only.
- **Staged entries**: shared photos are retried from their staged copy (`staged` is copied into the retry file; the worker keeps the staged files of the new retry file when it deletes the queue). Every retry writes its own history entry (photo count = retried photos).


## Videos (issues #15 / #34)

- **Permissions** (`ui/photogrid/MediaAccess.kt`, `PhotoGridScreen`): the manifest declares `READ_MEDIA_VIDEO`; the grid requests `READ_MEDIA_IMAGES`, `READ_MEDIA_VIDEO` and `READ_MEDIA_VISUAL_USER_SELECTED` in one `RequestMultiplePermissions` call. Access = any granted. "Video missing" (`MediaAccess.videoMissing`) = images granted and video not, which only happens for users upgrading from the images-only version: requested once automatically, guarded by the persisted `video_access_requested` flag (`MediaPermissionStore`, `app_preferences`, excluded from backup; the screen waits until the flag is read — `videoAccessRequested` is `null` before) plus a per-session `rememberSaveable` guard. Partial-access users are never asked automatically; they get the "Select more photos and videos" banner, which re-launches the request. The video banner's action re-launches the request, or opens `ACTION_APPLICATION_DETAILS_SETTINGS` after a permanent denial: `videoDenial()` classifies a denied result as `Permanent` only when `shouldShowRequestPermissionRationale(READ_MEDIA_VIDEO)` is false *and* a rationale was offered before (persisted `video_rationale_shown`, set after a denial with rationale or when the grid starts with a rationale pending); without an earlier rationale a false value means a dismissed dialog (`Dismissed`, the banner keeps asking). Every permission result that keeps access reloads the media, so a widened grant (images-only → + video, partial → full) shows the new items at once. Access is re-read on every resume (`LifecycleResumeEffect`). No access → the existing `PermissionDeniedContent`.
- **Query and ids** (`MediaRepository`): a second query on `MediaStore.Video.Media.EXTERNAL_CONTENT_URI` (`_ID, DISPLAY_NAME, DATE_TAKEN, SIZE, MIME_TYPE, DURATION`); a `SecurityException` from it yields only the images. Both lists are sorted by raw `DATE_TAKEN` descending (stable). Image and video `_ID`s overlap, so `mediaItemId(rawId, kind)` keeps image ids and sets `Photo.VIDEO_ID_FLAG` (`1L shl 62`) for videos; raw ids `< 0` or `>= 2^62` are skipped. The ids stay positive, so selection, `UploadedPhotosStore` (string set) and the queue JSON (`id >= 0` = markable) need no migration. `Photo.mediaKind` comes from the query, never from the mime type; a null / blank video `MIME_TYPE` uploads as `video/*`. Undated videos map to `Photo.UNKNOWN_DATE` like images (auto date folder `1970/01/01`; no `DATE_MODIFIED` fallback).
- **Thumbnails**: `coil-video` (same version as Coil) would register `VideoFrameDecoder` for every source through Coil 3's service loader; `KrhnlesApplication.newImageLoader` therefore calls `serviceLoaderEnabled(false)` (which also drops the service-loaded default OkHttp fetcher, `MediaDataSourceFetcher` is unused) and registers the authenticated `OkHttpNetworkFetcherFactory` and `LocalVideoFrameDecoderFactory` explicitly. The wrapper delegates to `VideoFrameDecoder.Factory()` only for sources with `ContentMetadata` of a `content://` URI (produced by Coil's `ContentUriFetcher`); network and disk-cache sources are refused, so a server answering a thumbnail request with `video/mp4` never reaches `MediaMetadataRetriever` (`VideoDecoderRegistrationTest`). Tiles keep `AsyncImage(photo.uri)`; frame extraction is slower than image decoding (scroll performance is a manual device check).
- **Upload** (`WebDavClient.uploadFile`): one `PUT` per file through `executeCancellable` (cancelling the worker cancels the transfer), on `uploadClient` = `noRedirectClient.newBuilder().readTimeout(5 min)` (shares pool, dispatcher and the origin-restricted auth interceptor; the server may finalise a large file long after the last byte); never a `callTimeout`. Uploads never follow redirects: OkHttp turns a 301 / 302 / 303 `PUT` into a body-less `GET`, whose 2xx would look like success, so every 3xx fails as `WebDavHttpException(code)`. This also closes OkHttp keeping `Authorization` on a same-host, same-port https → http redirect (the application interceptor runs only for the original request). `InputStreamRequestBody` is one-shot and reports `contentLength()` from the size the worker reads inside the stream's `use` block with `openAssetFileDescriptor(uri, "r").length` (closed again; `UNKNOWN_LENGTH` / any error → `-1` = chunked; staged share copies use only their own file size, never the entry URI). HTTP 413 / 507 map to `UploadFailure.TooLarge` / `StorageFull` (`Throwable.toUploadFailure()`, branches on `WebDavHttpException.code`) and their messages (`upload_failure_*`) are appended to the result notification. Nextcloud chunked upload v2 / resume is a follow-up.
- **Per-entry progress and foreground service limits**: after each successful entry the worker rewrites the queue file atomically (`rewriteQueueFile()`: `<name>.tmp` + rename; the entry gets `"uploaded": true`, `UploadQueue.toProgressJson()`) and marks that photo uploaded at once. A re-run (refused foreground service, process death, WorkManager stop) skips finished entries (`pendingIndices`); result counts, history and notification cover the whole batch including earlier runs. Files without markers (older versions, retry files) upload every entry. Every `setForeground` call goes through `setForegroundOrFalse()`; a refused foreground service (`ForegroundServiceStartNotAllowedException`, e.g. the `dataSync` time budget is used up) returns `Result.retry()` and keeps the queue file and its staged copies — except after the last entry (the batch is complete) and once `interruptions + 1 >= MAX_UPLOAD_RUN_ATTEMPTS` (5; `interruptions` is an optional top-level int of the queue file, absent = 0, rewritten by `UploadWorker.interrupted()` via `rewriteQueueFile()` before `Result.retry()`; retry files start at 0; Wi-Fi-only wake-ups and constraint stops never count, `runAttemptCount` is only a backstop for the cap (the run also gives up when `rewriteQueueFile()` fails and `runAttemptCount >= MAX_UPLOAD_RUN_ATTEMPTS`, and always at `MAX_UPLOAD_RUN_ATTEMPTS_BACKSTOP` = 10x the cap), the value is clamped to `0..MAX_UPLOAD_RUN_ATTEMPTS` when parsed (Int, Long, Double, negative), though WorkManager's back-off delay still grows with them up to 5 h): then the run stops with an "Upload failed" notification (`upload_failure_interrupted`) and a retry file for the entries not uploaded yet. Upload work requests come from `uploadWorkRequest()` (`worker/UploadConstraints.kt`, used by `UploadEnqueuer` and `handleRetry`) with an explicit exponential back-off (60 s initial). Only the entry interrupted mid-transfer is sent again (the PUT overwrites; Nextcloud may keep an extra file version).
- **Unchanged by design**: `UploadedPhotosStore` (the queue format only gains the optional `uploaded` marker), the share target (image-only), album screens and the duplicate / blur reviews (`AlbumsRepository.isImage` drops video entries, so uploaded videos do not appear in Albums).

## Share Target Flow

When another app (Gallery, Screenshot, etc.) shares images via the Android share sheet:

1. `MainActivity` is launched with `ACTION_SEND` or `ACTION_SEND_MULTIPLE` (`isShareIntent`); it never composes `KrhnlesApp` then. It gets `ShareViewModel` from the default factory (public `(Application)` constructor, `ViewModelFactoryRegressionTest`) and calls `start(intent)`, which only acts once per ViewModel, so rotation neither loses nor repeats anything. The UI is `ShareRoute` → stateless `ShareReceiverScreen(state, …)`.
2. `parseSharedPhotos(intent, ownPackage)` is a pure extraction of `EXTRA_STREAM` into `SharedItems(uris, truncated, rejected)`: hostile extras (any `RuntimeException` while reading them, e.g. `BadParcelableException` / `ClassCastException`, and wrong element types) are ignored (exception type logged only), then `isAllowedPhotoUri`, de-duplication and the 100-photo cap (`MAX_SHARED_PHOTOS`). Nothing usable → `ShareFinish(NoPhotos)`: Toast `share_no_photos` and `finish()`, the app is not launched.
3. The configuration is read once (`webDavConfig.first()` under a 3 s `withTimeoutOrNull`; timeout / failure counts as configured, the worker reports a missing server). Not configured → `NotConfigured` dialog; "Open app" starts `MainActivity` with `FLAG_ACTIVITY_NEW_TASK` (the share activity runs in the sender's task), nothing is copied.
4. `resolveSharedPhotos()` runs each item's `getType` + `query(…, CancellationSignal)` as an `abandonableCall` on the work dispatcher (never Main) with a 10 s per-item timeout; an item that times out is dropped. Types are allow-listed (`SharedImageType`: JPEG, PNG, GIF, WebP, HEIC, HEIF, AVIF, BMP, DNG; aliases such as `image/jpg` / `image/x-ms-bmp` normalized; SVG and every other type rejected). A concrete provider type decides alone; if the provider reports none, `application/octet-stream` or a wildcard, the `DISPLAY_NAME` extension decides via `MimeTypeMap` (a known non-image extension drops the item), and only without a known extension a concrete intent type is used (`image/*` never). Provider calls catch `SecurityException`, `IllegalArgumentException`, `IllegalStateException`, `OperationCanceledException`. The provider name is the remote file name only if it is one valid name (`isValidRemoteFileName`: valid path segment, ≤ 255 bytes, no Unicode Cf / bidi controls, line / paragraph separators or unpaired surrogates) and unique in the share (case-insensitive); a name not ending with one of the validated type's extensions gets it appended (`evil.svg` as PNG → `evil.svg.png`); else `shared_<millis>_<8 hex>.<ext>`. Shared photos have `id = -1` (never marked as uploaded) and today's date. The occasion dialog shows the count plus skipped / not-included notices (`ShareUiState.Ready`); auto date folders never apply. While the share is read, `Preparing` shows an indeterminate progress with Cancel.
5. On confirm (`ShareViewModel.confirm`, phase CAS latch) the photos are copied with `ShareStaging.stage()` into `noBackupFilesDir/share_staging/<uuid>` while the grant is still valid ("Preparing x of n" + Cancel; Back cancels too). Bounds: 100 MiB per file (provider `SIZE` pre-skip and counted bytes), 1 GiB per share (exceeding item skipped), staging folder ≤ 2 GiB incl. existing files and free space (`getAllocatableBytes`, else `usableSpace`) minus a 200 MiB margin (exceeding → share fails). Each item is opened with `openAssetFileDescriptor(uri, "r", CancellationSignal)` and copied inside one `abandonableCall` (per-item timeout 2 min → skipped as unreadable): the blocking open + copy run detached on IO, so cancellation or the timeout cancels the signal (aborting the provider's open, and closing the source stream so a blocked read returns) and returns at once even if the provider ignores the signal; an abandoned call deletes its own (also complete) file whenever it returns, and a returned `Staged` name is recorded by the ViewModel without a suspension point, so no staged file is ever orphaned. Skips carry a `SkipReason`: unreadable / too large (`ShareFinish.skipped`, `share_copy_skipped`) and over the per-share cap (`ShareFinish.overShareLimit`, `share_over_share_limit`); `shareFinishMessage()` builds the toast. A write / space failure stops the share with one `share_copy_failed`; if every item was skipped the share ends with `ShareError.NothingCopied` (`share_nothing_copied`), not the storage message. Cancel and Back publish `Cancelled` immediately (no join of a job blocked in a provider); Cancel, Back, a failure and `onCleared()` delete the batch's staged and partial files in the copy job's `finally`; nothing is enqueued.
6. After the copy the ViewModel enqueues one `UploadBatch.Occasion` (photos carry `stagedName`) through `UploadEnqueuer` (application scope) and emits the one-shot finish; an enqueue failure — any exception except cancellation, `UploadEnqueuer` never lets one escape the application scope — deletes the staged copies and shows `share_enqueue_failed`. The queue entry has `staged` and no id; the worker reads only the staged file (missing → failed photo, never the URI) and never touches `contentResolver` for it.
7. **Cleanup**: no deletion per successful photo (the staged copies stay until the queue is final; a re-run skips entries marked `uploaded`). `deleteQueueFile(context, queueFile, keep)` (also removes a leftover `<queue>.tmp`) is used at every queue deletion (malformed queue — staged names read leniently —, not configured, end of the run) and deletes the staged files except those referenced by the new retry file. `ShareStaging.sweep()` runs on IO when a share starts: staged files older than 7 days not referenced by an `upload_queue_*` file are deleted; one referenced by retry files is deleted together with those retry files only if every such retry file is itself older than 7 days (its own modification time — `handleRetry` refreshes it on every tap, so the window restarts) and has no unfinished retry work (`hasUnfinishedRetryWork`: `getWorkInfosForUniqueWork(retryWorkName)` bounded to 5 s; unknown keeps the files). It fails closed: an unreadable / malformed queue file or a changed queue-file list (listed twice) deletes nothing. A process death during a copy leaves only that share's partial files, removed by the sweep.
8. On dismiss → `finish()` returns without uploading or copying
   - **Security notes (accepted)**: *Confused deputy* — `MainActivity` is exported and reads every shared `content://` URI with the app's own identity, so a malicious sender could share a URI that only this app can read (e.g. a MediaStore image when the user granted the app media access). The only effect is that the photo goes to the user's own configured server, after the user saw the photo count and explicitly confirmed an occasion; the app's own authorities and `file://` are rejected (`isAllowedPhotoUri`), and nothing is sent anywhere else. *Per-process budget* — the share (1 GiB) and folder (2 GiB, counted from the files present when the share's copy starts) budgets are not shared between concurrent shares in separate `MainActivity` tasks, so two simultaneous shares can together exceed the folder cap by up to one share; the free-space margin still applies per share (accepted). *Overwrite* — a shared photo is uploaded with a plain `PUT`, so a file with the same name already in the occasion folder is overwritten (known behaviour, also for gallery uploads); names are only de-duplicated within one share. *Abandoned calls* — a provider that ignores its `CancellationSignal` keeps one IO thread until it returns; the share itself is never blocked.
   - **Tests**: `ShareIntentParserTest` / `ShareStagingTest` / `ShareViewModelTest` use `FakeShareProvider` (`Robolectric.setupContentProvider`; content is served through `openTypedAssetFile(…, CancellationSignal)`, which `openAssetFileDescriptor(uri, "r", signal)` reaches; `ProviderGate` blocks an open / query until released or — if it honours cancellation — until the signal is cancelled, or ignores the signal to model a stuck provider); stream-level cases (endless / blocking reads) inject a `SharedSourceOpener`. `ShareTestHarness` builds the ViewModel with fakes, a real IO work dispatcher and gated items for in-flight copies, and polls while idling the main looper (a `withTimeoutOrNull` on Main needs `idleFor`). `ShareReceiverScreenTest` covers the dialog, the single enqueue, Cancel and `ActivityScenario.recreate()` during a gated copy; `MainActivityShareTest` the no-photo Toast + `finish()`; `UploadWorkerRunTest` staged uploads, a stopped-and-rerun worker, retry from staging and invalid staged entries.
9. **History**: Upload outcomes are persisted via `UploadHistoryStore` and shown on the Upload History screen
10. **Uploaded Badge**: `PhotoGridViewModel` observes `UploadedPhotosStore.uploadedPhotoIds` and includes them in `PhotoGridUiState`; the grid shows a cloud badge on already-uploaded thumbnails (user can still select and re-upload them for a different album)
11. **Filter Toggle**: A funnel icon in the top bar (visible when any photos have been uploaded) lets the user hide already-uploaded photos; `PhotoGridViewModel.toggleShowOnlyNewPhotos()` recomputes `photosByDate` from the full unfiltered list

## Upload Path Construction

Given:
- WebDAV base URL: `https://nextcloud.example.com/remote.php/dav/files/user/`
- Base folder: `Photos/KrohnSync`
- Occasion: `Summer 2026`
- File: `photo.jpg`

Result: `https://nextcloud.example.com/remote.php/dav/files/user/Photos/KrohnSync/Summer 2026/photo.jpg`

### Auto date folders (issues #18 / #37)

When auto date folders are enabled (Settings switch, plain preference `auto_date_folders`, default off, reset by logout, not backed up), the photo grid skips the occasion dialog and shows a preview of the target paths (one per distinct day folder; the path list scrolls within a bounded height, the buttons stay visible). Confirming queues **one** upload for the whole selection (user decision, deliberately not one work per month or day as the issue text suggested):

- **Day folders:** each photo goes into `<base>/YYYY/MM/DD/` (`dayFolderName()`: `String.format(Locale.ROOT, "%04d/%02d/%02d", …)`, ASCII digits only, no month names, no default-locale dependency). The capture day is `Photo.dateTaken`, i.e. `DATE_TAKEN` converted once by `MediaRepository.dateTakenOf(millis, zone = ZoneId.systemDefault())` when the photo list loads, the same date as the grid's date header. Unknown dates (`Photo.UNKNOWN_DATE`) go into `1970/01/01`; pre-1970 dates keep their date.
- **Travel limitation (accepted):** the day is the device zone at load time, not the zone where the photo was taken (no EXIF offset); reloading after a zone change can move a not-yet-uploaded photo to another day.
- **One work per selection:** `resolveAutoDateUploadBatch(photos)` returns one `UploadBatch.PerPhoto(photos, folders, label)` (photos sorted by day, then id; `folders` same size / order, non-blank, enforced with `require`). Occasion mode and the share target use `UploadBatch.Occasion(folderName, photos)` unchanged; the share target never uses auto date mode. One work means one foreground / progress notification, one result notification (tag = queue file name), at most one retry action and one history entry.
- **History label:** the single day folder (`2026/05/14`) or `"<first> – <last>"` (`2026/04/30 – 2026/05/01`), stored in `UploadHistoryEntry.occasionName` (no model change), capped at 200 characters when recorded, never used as a path.
- **Queue format (backward compatible, no version field):** occasion / old queues are written and read exactly as before (`{"folderName": "Trip", "photos": [...]}`). Per-photo queues have `label`, a `folderName` on every entry and **no** top-level `folderName`. A file is per-photo if it has a `label` (any type) or any entry has a `folderName` key; then every entry needs a non-blank string folder and a top-level `folderName` makes it malformed (as do mixed files, missing entry folders and non-string folders: work fails, file deleted, nothing uploaded). A non-string `label` is dropped (history label `""`). History label = `label` ?: top-level `folderName` ?: `""`. Queue and retry files persisted before this change (single `folderName`, including old `YYYY/MM-Mon` folders) behave as before. Downgrade is not supported: older versions fail and delete per-photo queues.
- **Validation and folder creation:** every effective folder is validated before any request (top-level: blank = base folder, otherwise `isValidFolderPath`; entry folders: `isValidFolderPath`); any invalid folder fails the whole work with `FolderCreationError.InvalidFolderName`. Then `WebDavClient.createDirectories(paths)` MKCOLs every distinct folder level by level below the configured URL, each cumulative path at most once per run (405 = exists). Any MKCOL failure fails the whole work before the first PUT (failure notification, history all failed, no retry file). Each photo is then PUT into its own folder; progress counts all photos of the work.
- **Progress banner:** `PhotoGridViewModel.uploadProgress` still shows the first running work. With one work per selection it covers the whole selection; concurrently running works (two selections back to back, share target + grid) are not aggregated (unchanged).
- **Existing remote folders:** old `YYYY/MM-Mon` folders are neither migrated nor merged; they coexist with the new day folders. The Albums tab lists the base folder with `Depth: 1`, so year folders appear as albums (unchanged).

`WebDavClient.createDirectory()` walks each segment in order (MKCOL per segment, 405=already exists is OK), so nested paths are created safely regardless of what already exists on the server.
All path segments are validated (`.` / `..` rejected) and URL-encoded via `HttpUrl` segment builders to prevent path traversal and malformed path injection.

## Key Decisions

- **WorkManager** for uploads ensures they survive app closure
- **Share target** declared for `image/*` (`ACTION_SEND` + `ACTION_SEND_MULTIPLE`); `ShareReceiverScreen` shows the occasion dialog immediately so the user stays in context and the source app is returned to after confirm
- **Staged share copies (issues #16 / #35)** — a share grant is revoked when the receiving activity finishes and cannot be persisted, so shared photos are copied into backup-excluded app storage before `finish()` and uploaded from there. Rejected: keeping the activity alive until the upload ends (breaks background uploads), copying at receipt (wasted work on cancel), `takePersistableUriPermission` (not available for share grants), a `FileProvider`
- **Android Keystore** for secure credential encryption (replaced deprecated EncryptedSharedPreferences)
- **EncryptedSharedPreferences** — removed (deprecated in security-crypto 1.1.0)
- **Nextcloud Login Flow v2** for browser-based auth (no password handling in-app)
- **Nextcloud login polling timeout** so auth does not run forever if approval never happens
- **OkHttp** directly for WebDAV (no Retrofit needed for simple PUT/MKCOL/PROPFIND)
- **Coil 3** for efficient image loading in the grid
- **LazyVerticalGrid** with `GridItemSpan` for date headers spanning full width
- **AndroidViewModel** to access Application context for ContentResolver and DataStore
- **DataStore Preferences** (`uploaded_photos`) for persisting the set of already-uploaded photo IDs across restarts; stored as `Set<String>` (Long IDs converted to strings)
- **Settings connection test is one-shot** — `SettingsViewModel.testConnection()` reads the config once with `webDavConfig.first()` (never `collect` + `return@collect`, which leaks the collector; issue #22 / #41), drops calls while the previous test's `Job` is still active, and reports a typed `ConnectionTestResult` that `SettingsScreen` maps to localized `R.string.connection_test_*` messages (raw exception text is never shown). The server check is injected as `connectionTester` (default `WebDavClient.testConnection`) so tests run without a network. `NoCollectEarlyReturnRegressionTest` scans `app/src/main` for the early-return idiom (literal `return@collect` only — custom labels, `collectLatest` and multi-line forms are not detected)
- **Connection test guard is always released** — `WebDavClient.testConnection(timeoutMillis = 30 s)` sets a per-call OkHttp call timeout (the shared client used for uploads keeps no overall limit, so large uploads are not cut off) and runs via `enqueue` inside `suspendCancellableCoroutine`, so cancelling the coroutine cancels the HTTP call; cancellation is rethrown, never wrapped in the `Result`. Non-2xx statuses fail with the typed `WebDavHttpException(code)`. In the ViewModel every failure (including a DataStore `IOException` from `webDavConfig.first()` or a throwing tester) becomes a result, so `isTesting` is always cleared. `logout()` and any change of URL/username/password (observed in the `init` config collector) cancel the running test, null the `Job` and clear `testResult`; the job calls `ensureActive()` before publishing, so a cancelled test never writes a stale result into a new session
- **Connection-test error mapping** — `Throwable.toConnectionTestResult()`: `WebDavHttpException` 401/403 → `AuthFailed`, 404 → `NotFound`, other → `HttpError(code)`; any `SSLException` / `GeneralSecurityException` in the cause chain (`SSLHandshakeException`, `SSLPeerUnverifiedException`, `CertPathValidatorException`, `CertificateException`) → `CertificateError`; `UnknownHostException` → `UnknownHost`; `ConnectException` / `NoRouteToHostException` → `ServerUnreachable`; `InterruptedIOException` (socket or call timeout) → `Timeout`; `IllegalArgumentException` (bad URL) → `InvalidUrl`; everything else → `UnknownError`. Only the exception class name is logged
- **One photo-deletion path** — the three album deletion entry points (`DuplicatesViewModel.deletePhotos(toDelete, launcher)` for the duplicate review, `BlurViewModel.deleteBlurryPhotos(toDelete, launcher)` for the blur review, `AlbumDetailViewModel.deleteSelectedPhotos()` for selection mode) only supply their busy-state transitions (`DuplicatesState.Deleting`/`Idle`, `BlurState.Deleting`/`Idle`, `isDeletingPhotos`) to `AlbumDetailViewModel.launchPhotoDeletion()` (the `PhotoDeletionLauncher` interface; the review screens pass the detail ViewModel as launcher), which runs the deletion in the detail ViewModel's scope and calls the ViewModel-independent `AlbumsRepositoryContract.deletePhotosIndividually()` (`data/PhotoDeletionResult.kt`; sequential, one `DELETE` per photo, a failed `Result` or a thrown exception counts as one failure and does not stop the rest; cancellation is rethrown and `ensureActive()` stops the loop before the next photo). The launcher only deletes photos that are part of the currently loaded album (`detailState.photos`); others — e.g. review results that survived a server / account change — are not deleted and count as failed. `onFinish` runs exactly once, also when the job is cancelled before its body was dispatched (`invokeOnCompletion`), and the re-entry guard stays set until the job completed. Only hrefs that were actually deleted are removed from `AlbumDetailState` — photos whose deletion failed stay visible. Any other non-cancellation failure (e.g. repository creation with an invalid URL) is mapped via `runCatching` + rethrow `CancellationException` to `PhotoDeletionResult.allFailed()` instead of crashing. The busy state is reset in `finally` (review paths via `compareAndSet(Deleting, Idle)`, so a scan started meanwhile is never overwritten). New deletion entry points must reuse `deletePhotosIndividually()` / `PhotoDeletionLauncher.launchPhotoDeletion()` (issues #28 / #47, #29 / #48)
- **Photo-deletion outcome is state, not a callback** — the delete functions take no `onComplete`; they return `false` (and do nothing) while `photoDeletionJob` is still active (re-entry guard for all entry points; released when the job ends, every request bounded by the OkHttp connect/read timeouts). When a deletion finishes, `photoDeletionOutcome: StateFlow<PhotoDeletionOutcome?>` is set (after the busy state was cleared); `AlbumDetailScreen` collects it (`filterNotNull().collect` in `LaunchedEffect(viewModel)`, so consuming it does not cancel the snackbar), calls `consumePhotoDeletionOutcome()` first (shown once), clears the selection and shows `R.plurals.snackbar_delete_failures` via `photoDeletionFailureMessage()`. The duplicate / blur review remember (`rememberSaveable`) that they started a deletion and navigate back once their state leaves `Deleting`; `BackHandler` and the disabled top-bar back button keep the user on the review while deleting. The album detail screen does the same for selection-mode deletions (`BackHandler(enabled = isDeletingPhotos)`, back arrow, clear-selection X and delete action disabled), because the deletion runs in the detail entry's ViewModel and would be cancelled if that entry were popped. This replaced snackbars launched in the review's `rememberCoroutineScope`, which were cancelled by the immediate navigation, and callbacks that could fire into a screen the user had already left
- **Already-deleted photos** — `AlbumsRepository.deletePhoto()` treats `404` / `410` as success (deleted elsewhere); other non-2xx statuses fail with `WebDavHttpException(code)`. `deleteAlbum()` still fails on `404`
- **Server hrefs are validated** — `resolveWebDavHref(root, href)` (`data/WebDavHref.kt`) checks the *raw* href first (percent-decoded pieces must not be `.` / `..` or contain `/`, `\` or control characters; no `?`, `#`, `\`), because `HttpUrl.resolve()` silently normalizes dot segments away; then resolves it with `root.resolve(href)` and requires the same scheme/host/port and a path strictly below `root`. `AlbumsRepository` uses `baseFolderUrl` (config URL + base folder) as root for album/photo hrefs (`deletePhoto`, `deleteAlbum`, `renameAlbum`, `listPhotos(albumHref)`, direct image URLs) and the album URL for the photos of a listing. Listings skip unsafe entries (only the count is logged); requests for an unsafe href fail with `UnsafeHrefException` without being sent; image URLs fall back to `""`. `downloadBitmapForHash(url)` (scan thumbnails) only requests a URL strictly below `baseFolderUrl` or the Memories preview `<nextcloudBase>/index.php/apps/memories/api/image/preview/<alphanumeric id>` on the configured origin; anything else fails with `UnsafeHrefException` before a request. PROPFIND and thumbnail failures carry `WebDavHttpException(code)`. The href itself is never logged. `PropfindEntryReader` only keeps an `oc:fileid` matching `[A-Za-z0-9]+` (it ends up in the Memories preview URL; anything else is dropped, so the photo falls back to its WebDAV URL), and `checkMemories()` logs the exception type only. Absolute, percent-encoded Nextcloud paths and absolute same-origin URLs are accepted
- **Streamed, bounded album listings (issues #27 / #46)** — PROPFIND responses are never buffered (`body.string()`) or DOM-parsed. `AlbumsRepository.executePropfind()` passes the decompressed `response.body.byteStream()`, wrapped in `LimitedInputStream` (`MAX_PROPFIND_RESPONSE_BYTES` = 32 MiB; the first read past the cap throws `PropfindResponseTooLargeException`), to `PropfindEntryReader` (`data/WebDavXmlParser.kt`, `android.util.Xml.newPullParser()`), which yields one `d:response` at a time. Per entry at most 256 elements, 16 nesting levels and 8 KiB per captured text value (`PropfindEntryLimits`); an oversized entry is skipped (only the count is logged, never the href). `listPhotos(albumHref, onProgress)` returns `Result<PhotoListing(photos, isTruncated)>`: it drops the collection entry, keeps images strictly below the album, drops duplicate hrefs (`HashSet`) and stops at `MAX_PHOTOS_PER_ALBUM` (20,000) or the byte cap — then the complete entries read so far are returned with `isTruncated = true` (no complete entry besides the album collection → `MalformedMultistatusException`; a truncated listing without photos shows `album_truncated_empty_notice` instead of the empty-album message). `LimitedInputStream.available()` never reports bytes beyond the cap, so the decoder's read-ahead stops at the cap. `onProgress` gets the running count every 100 photos plus once at the end (on the IO thread). `listAlbums()` uses the same reader with the byte cap only and fails with `AlbumsError.ListingTooLarge` instead of silently missing albums. The Memories check runs concurrently with the PROPFIND. `AlbumDetailViewModel` shows the count (`loadedCount`, "Loading photos… N", polite live region) while loading and publishes photos, thumbnail URLs (resolved on the injectable `backgroundDispatcher`, `Dispatchers.Default`, not Main; `listAlbums()` post-processes on IO), `isTruncated` and `isLoaded` once, after `ensureActive()` and a load-generation check — a failure is published only under the same two checks, so the failure of a cancelled read never overwrites `NotConfigured` / `ConfigurationChanged` or a newer load; deletion and review semantics are unchanged (they only see complete or truncated-complete listings); progress callbacks of a replaced / cancelled load are ignored via a load generation; `reload()` is ignored while a load runs, so Retry from a review never starts a second listing. A truncated album shows a notice on the album screen and on the duplicate / blur review (results may be incomplete). Rejected alternatives: Nextcloud `SEARCH` (DASL) paging (Nextcloud-only, still needs the PROPFIND fallback, server still enumerates) and progressive chunk publishing (needed a deletion gate, a Flow contract and growing-list handling for little benefit once memory is bounded). Accepted risk: a server trickling bytes just under the 60 s read timeout can keep a listing open; no `callTimeout` is added (it would break large uploads on the shared client) — the byte cap bounds the data and leaving the screen cancels the call.
- **Thumbnail URL resolution and decoding (issues #25 / #44)** — `thumbnailUrl()` sends at most one request per `AlbumsRepository` instance (the Memories `describe` check, none on non-Nextcloud URLs); `buildUrl()` is string work, so resolving N photos costs no per-photo round-trip (`ThumbnailUrlResolutionTest`, `runBlocking` with real time; timeouts are the internal constructor parameters `memoriesCheckTimeoutMs` / `memoriesRetryBackoffMs`). The check lives in `data/MemoriesAvailability.kt` (unit-tested with a fake check and fake clock in `MemoriesAvailabilityTest`): at most one request per repository instance once a definite answer is known (200 -> available, other status -> unavailable); an inconclusive check (timeout, I/O failure, HTTP 429 / 5xx, any non-cancellation failure) is not cached and is retried at most once per backoff period (30 s, doubling per consecutive failure, capped at 10 min). Only the first attempt is awaited by callers (`listPhotos` runs it concurrently with the PROPFIND); retries run fire-and-forget in the repository's own scope, bounded by the check timeout, so a hanging endpoint never delays a listing or `thumbnailUrl()` again. Cancellation is never cached. `MemoriesAvailability.close()` (via `AlbumsRepositoryContract.close()`, called by `AlbumsRepositoryProvider` whenever it replaces, invalidates or is closed from the ViewModel's `onCleared()`) cancels an in-flight retry and its HTTP call and blocks new ones, so a dropped repository never sends a request with outdated credentials. The lock is acquired with its own timeout (separate from the check timeout). `buildUrl()` uses the Memories preview only for ASCII-alphanumeric file ids (`FILE_ID_REGEX`) and `isMemoriesPreviewUrl` accepts ASCII alphanumerics only. `downloadBitmapForHash()` decodes with `inJustDecodeBounds` + a power-of-two `inSampleSize` (`decodeDownsampled`) so the longest side stays in 512..1023 px, the analysis size of dHash and `BlurDetector` (`MAX_ANALYSIS_SIZE` = 512); smaller images are not scaled and images announcing more than `MAX_THUMBNAIL_PIXELS` (100 MP) are rejected after the bounds pass with `ThumbnailTooLargeException` (the scan skips them). Intended behaviour change: on the WebDAV-fallback path blur scores are now computed from the subsampled original, so they differ from full-size decoding (a sharp textured image stays above the default threshold). Parallel scan downloads were considered and deferred (unmeasured; memory bound and ordering invariants unresolved) — reconsider only with a measurement.
- **Blocked reads are cancellable** — coroutine cancellation does not interrupt a blocking socket read, and `Job.invokeOnCompletion` does not fire while the body is still blocked. `executeCancellable(call)` (`data/CancellableCall.kt`, shared by `AlbumsRepository` and `WebDavClient.uploadFile`) runs `call.execute()` inside `withContext(Dispatchers.IO)` next to a sibling `launch(start = UNDISPATCHED) { try { awaitCancellation() } finally { call.cancel() } }`; on cancellation the read fails at once and any non-cancellation exception (the `IOException`, or a parser exception wrapping it) is turned back into the scope's `CancellationException` (`ensureActive()`), never an error. Used by the PROPFIND, the Memories check and `downloadBitmapForHash()` (whose body is capped at `MAX_THUMBNAIL_BYTES` = 32 MiB → `ThumbnailTooLargeException`); covered by MockWebServer tests stalled before the first body byte and mid-body with a hard limit of a few seconds, and by read-timeout tests (→ `AlbumsError.Timeout`).
- **XXE defense for a stream** — a stream cannot be pre-sanitized with a regex. `PropfindEntryReader` sets `FEATURE_PROCESS_DOCDECL` to false, reads the prolog with `nextToken()` up to the root `START_TAG` and fails with `MalformedMultistatusException` on any `DOCDECL` (also a benign DOCTYPE) or `ENTITY_REF`, requires the root `{DAV:}multistatus`, and then only uses `next()`: KXml rejects a DOCTYPE after the root start tag (tested also inside `d:response`), so no entity can ever be declared, and undeclared entity references are rejected by the parser. The parser is created lazily inside `next()`'s try because KXml already reads in `setInput()`: an `XmlPullParserException` wrapping a stream `IOException` (in `detail`) is unwrapped and rethrown unchanged (timeout → `AlbumsError.Timeout`, cancellation → `CancellationException`), anything else — including an unsupported declared encoding — becomes `MalformedMultistatusException`. Parser exception messages contain server content and are never logged (type only). Parser tests run under `RobolectricTestRunner` on the production parser (no `kxml2` test dependency).
- **Parse-cost bounds** — KXml grows `elementStack`, `attributes` and `nspStack` linearly, so deep nesting, many attributes or many namespace declarations in one tag would cost minutes to hours within the 32 MiB cap, and one 32 MiB text node about 260 MB of heap (an `OutOfMemoryError` crash). `PropfindEntryReader` therefore fails the whole response with `MalformedMultistatusException` on every start tag (prolog, responses and skipped elements) beyond an absolute depth of 32, 64 attributes or 64 namespace declarations (`PropfindEntryLimits` document bounds; per-entry limits still only skip), and reads through `XmlTokenSizeLimitingInputStream`, which fails once more than 64 KiB arrive between two markup starts (`<` outside CDATA, comments and processing instructions, because `next()` coalesces text across them). That bounds one tag with all its attributes and one text node before KXml buffers it; a maximal captured value (8 KiB characters, multi-byte UTF-8) still fits. Covered by time-bounded regression tests (200,000 nesting levels, attributes, namespace declarations; 1 MB text, CDATA and comment-split text).
- **Credentials only for the configured origin** — the `AlbumsRepository` and `WebDavClient` OkHttp interceptors and the Coil image-loader interceptor (`KrhnlesApplication`) only add `Authorization` when `request.url.hasSameOriginAs(config URL)` (scheme, host, port). OkHttp itself strips `Authorization` on cross-host / cross-port redirects (not on a same-host, same-port https → http downgrade), and application interceptors are not re-run for redirects; uploads and renames therefore never follow redirects
- **Uploaded-photo tracking reset on logout** — `SettingsViewModel.logout()` calls `UploadedPhotosStore.clear()` so the tracking starts fresh when a user disconnects (or switches servers)
- **UploadWorker records IDs after success** — each successfully uploaded photo's MediaStore ID is written to `UploadedPhotosStore`; failed uploads are not marked; re-uploads are always allowed (badge is visual only)
