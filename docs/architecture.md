# Architecture

## Overview

Kröhnle's Image Management follows **MVVM + Clean Architecture** using Kotlin and Jetpack Compose.

## Authentication

Two authentication methods are supported:

1. **Nextcloud Login Flow v2** (recommended): Opens the Nextcloud login page in the browser. The app polls for completion and receives an app-specific token. Follows the same pattern as the android-paper-reader reference project.
2. **Manual WebDAV config**: Direct URL, username, and password/app token entry for non-Nextcloud WebDAV servers.

Credentials are stored securely:
- URL and base folder in DataStore Preferences
- Username and password/app token encrypted via Android Keystore (AES-256-GCM) in standard SharedPreferences
- Crypto lives in `CredentialCipher` (format `Base64([ivLen][iv][ciphertext+tag])`), backed by an injectable `CredentialKeyProvider` (`AndroidKeystoreKeyProvider` in production, a software AES key in unit tests because the Keystore is unavailable under Robolectric)
- `CredentialCipher.decrypt()` maps missing values, format violations and every `GeneralSecurityException` / `ProviderException` / `IOException` to `DecryptResult.Missing`, `Success`, or `Failure(reason)` (other runtime exceptions are not caught) where the reason is `KEY_INVALIDATED` (`KeyPermanentlyInvalidatedException` / `UnrecoverableKeyException` / `UnrecoverableEntryException` anywhere in the cause chain) or `UNREADABLE` (malformed data, GCM tag mismatch, lost key, `UnexpectedKeyEntryException` when the alias holds a non-secret-key entry, other Keystore errors)
- Corrupted encrypted values fail closed (treated as not configured, never used for requests) and failures are logged via `Log.w` with field name and exception type only — never ciphertext or plaintext; a persisting failure is logged once per field until its outcome changes
- All credential-derived flows (`credentialState`, `isConfigured`, `webDavConfig`, `username`) derive from one private snapshot flow that decrypts both fields once per DataStore emission and runs `flowOn(ioDispatcher)` (internal constructor parameter, default `Dispatchers.IO`) to keep Keystore work off the main thread
- Because DataStore does not observe the secure SharedPreferences, `save()` and `clear()` bump a `credentials_version` key in the same DataStore edit, forcing an emission even when the server URL is unchanged
- `save()` is ordered for atomicity: encrypt both values → `commit()` them to the secure prefs → DataStore edit (`server_url` + version bump). A failed encryption leaves the previous credentials and URL untouched; failures surface as `CredentialSaveException`, which `SettingsViewModel` turns into `R.string.error_credentials_save_failed` instead of crashing
- Non-credential preferences share this DataStore: `wifiOnly`, `autoDateFoldersEnabled` and `blurSensitivity` (string key `blur_sensitivity`, value = `BlurSensitivity` enum name, plain `edit` without a `credentials_version` bump). `blurSensitivity` is read via `prefs.asMap()[KEY] as? String` so a wrong-typed value falls back to Medium instead of throwing; unknown / blank names also give Medium. Like the whole file it is excluded from backup and device transfer, so the setting is not restored on a new device (issue #20 / #39)
- `CredentialRepository.credentialState` exposes `CredentialState.Missing / Valid / Corrupted(reason)`; `SettingsViewModel` maps it to `SettingsUiState.credentialProblem` and the login screen shows a localized banner explaining why the user must log in again (issue #31 / #50)
- If obtaining the key or initialising the cipher during encryption fails with an error classified as `KEY_INVALIDATED` (same cause-chain predicate as decrypt), `CredentialCipher.encrypt()` deletes the key, regenerates it, and retries once, so re-login after a security-settings change succeeds; other errors propagate without deleting the key

## Navigation & Album State Scoping

`KrhnlesApp.kt` hosts a single `NavHost`. The album flow is split into one ViewModel per responsibility, each scoped to the back-stack entry of the route that owns it (issues #29 / #48):

| Route | ViewModel (scope) | Used by |
|---|---|---|
| `albums` | `AlbumsViewModel` (own entry) | album list, rename / delete album |
| `albums/detail?href={href}` | `AlbumDetailViewModel` (own entry) | detail screen; shared with viewer and reviews |
| `albums/viewer` | `VideoPlayerViewModel` (own entry, plain `viewModel()`) + detail entry's `AlbumDetailViewModel` | fullscreen viewer; the player ViewModel gets `detailVm.repositories` as an argument |
| `albums/duplicates` | `DuplicatesViewModel` (own entry) + detail's `AlbumDetailViewModel` | duplicate review |
| `albums/blur` | `BlurViewModel` (own entry) + detail's `AlbumDetailViewModel` | blur review |

Sub-routes of an album obtain the detail ViewModel via the private helper `sharedAlbumDetailViewModel()`; `getBackStackEntry()` matches the detail route *pattern* (`ROUTE_ALBUM_DETAIL_PATTERN`):

```kotlin
composable(route) { backStack ->
    val detailVm = sharedAlbumDetailViewModel(navController, backStack)
    // = viewModel(rememberParentEntry(navController, backStack, ROUTE_ALBUM_DETAIL_PATTERN))
}
```

The review ViewModels are created with plain `viewModel()` in their own destination, so leaving a review clears them and cancels a running scan. Reviews get the album's photos, thumbnail URLs and the detail ViewModel's repository as arguments (`findDuplicates(photos, thumbnailUrls, detailVm.repositories)` / `findBlurryPhotos(photos, thumbnailUrls, repositories, sensitivity)`) — ViewModels never hold references to each other, and one album flow uses one `AlbumsRepository` (one OkHttp client) whose lifetime is the detail entry, which always outlives the reviews opened from it.

**Scans** — both reviews run the shared `scanAlbumPhotos()` (`ui/albums/PhotoScan.kt`): repository from the source, then the analyzer (`PhotoAnalyzer`; the blur scorer is created inside the error handling and closed only if created), then per photo resolve URL → download → analyze → `recycle()` in `finally` → `ensureActive()` → progress. A failing photo is skipped; cancellation is rethrown (neither a skipped photo nor an error); any other failure is a `PhotoScanOutcome.Failed(AlbumsError)`. Before every photo the loop asks the source again (`repositories.get()`): if it fails or no longer returns the repository the scan started with (logout, server / account change) the scan stops with `AlbumsError.ConfigurationChanged` / the typed failure, so no further request goes to the old server. Analysis (`PhotoAnalyzer.analyze`) runs on an injectable dispatcher (`analysisDispatcher`, default `Dispatchers.Default`), never on Main. Robolectric Compose UI tests inject `Dispatchers.Unconfined`: `waitUntil {}` does not drain the paused main looper, so a result resumed from a real background pool after the last `waitForIdle()` would hang the scan, timing-dependently (`RobolectricAnalysisDispatcherRegressionTest`). Each review ViewModel tracks its `scanJob`: `cancelScan()` (album became unavailable), `reset…State()` and a new scan cancel it, so two scans never publish concurrently; results are published only after `ensureActive()`. A scan starts only from `Idle` (`findDuplicates` / `findBlurryPhotos`), and Retry calls `retryFindDuplicates` / `retryFindBlurryPhotos`, which only run from `Error` and ignore an empty photo list (never turns an error into "none found"). So recreating the screen (rotation) never restarts a scan, never discards `Found` and never overwrites `Deleting`. `rememberReviewSelection()` pre-fills the selection once per result and keeps the user's choices across recreation (`ReviewSelectionTest`).

**Review ↔ album lifecycle** — the review screens take the album href and use `rememberReviewAlbumReady()` (`ReviewSelection.kt`): it calls `AlbumDetailViewModel.loadAlbum(href)` (no-op if loaded, so a review restored after process death loads its album), starts the scan only once the album `isLoaded` (never reports "none found" for an unloaded / loading / failed album), and on `NotConfigured` / `ConfigurationChanged` calls `cancelScan()` (state back to `Idle`, results dropped; not while `Deleting`, re-evaluated when it ends). `ReviewAlbumGate` shows the album error (Retry → `reload()`) or a progress indicator instead of the scan states.

**Blur sensitivity** — `findBlurryPhotos` / `retryFindBlurryPhotos` take the level as a `Flow<BlurSensitivity>` argument (the `albums/blur` destination passes `CredentialStore.blurSensitivity` to `BlurReviewScreen`; never a collected State value, so `BlurViewModel` stays a plain ViewModel). The scan job reads it once with `first()` after `Scanning` is published, bounded by `withTimeoutOrNull(3 s)` inside `runCatching` (cancellation rethrown); timeout or failure gives Medium. The level is fixed for that scan; a change in Settings applies to the next scan / Retry (no re-filter, no rescan). Photos with `score < threshold` are blurry; the thresholds are unvalidated heuristics (Memories previews and downsampled originals score differently) and are retuned only in `BlurSensitivity`. The Settings slider (`SettingsScreen`, logged-in content) derives its position from the hoisted level, persists in `onValueChange` whenever the rounded level changes (optimistic UI update in `SettingsViewModel.setBlurSensitivity`; the stored-value collector is ignored while a save is pending so a fast drag does not flicker, and a failed save restores the persisted level and shows `error_blur_sensitivity_save_failed`). Logout (`CredentialStore.clear()`) resets the level to Medium like the other preferences. `CredentialStore.snapshot` de-duplicates its DataStore inputs (server URL, base folder, `credentials_version`) before decrypting, so these preference writes never re-emit the credential flows; `credentialDataStore` is `@VisibleForTesting` and only used inside `CredentialStore.kt` (`NoCredentialDataStoreAccessRegressionTest`) and is a single accessibility node (content description = title, state description = level label; the visible texts are hidden from semantics).

**Repositories** — `AlbumsViewModel` and `AlbumDetailViewModel` own an `AlbumsRepositoryProvider` (`data/`, implements `AlbumsRepositorySource`). `get()` returns a `Result` and never throws (except cancellation): no complete credentials → `AlbumsRepositoryUnavailableException(NOT_CONFIGURED)`, a factory `IllegalArgumentException` (invalid URL) → `INVALID_CONFIGURATION`, lock not acquired / config not read within 10 s → `TIMEOUT`. Every `get()` re-reads the config and rebuilds when it differs from the cached one; calls are serialized by a `Mutex` (`withTimeoutOrNull`, CLAUDE.md lock rule) so concurrent callers share one instance; `invalidate()` bumps a generation so a build overlapping it is returned but never cached. `get()` itself picks up configuration changes, so `AlbumsViewModel.loadAlbums()` needs no explicit `invalidate()`. `AlbumDetailViewModel.loadAlbum(href)` is a no-op when the same album is already loaded or loading without error (a recreated screen never reloads, which could resurrect photos during a deletion); `reload()` is the explicit Retry. `AlbumDetailViewModel` additionally observes `webDavConfig` (`distinctUntilChanged().drop(1)`): on logout / server or account change it cancels a running load and deletion, invalidates and clears the album with `AlbumsError.NotConfigured` / `ConfigurationChanged`.

**Errors** — album list, detail and review states hold a typed `AlbumsError` (never exception text). `Throwable.toAlbumsError()` maps provider failures and reuses the connection-test classification (`toConnectionTestResult()`: TLS, DNS, unreachable, timeout, 401/403, 404, other HTTP); `albumsErrorMessage(resources, error)` resolves `R.string.albums_error_*`. The detail screen offers Retry except for `NotConfigured` / `ConfigurationChanged`. Only exception class names are logged.

Album ViewModels keep an `(Application)` constructor for the default factory (`ViewModelFactoryRegressionTest`): `AlbumsViewModel` / `AlbumDetailViewModel` via `@JvmOverloads (Application, credentialRepo, repoFactory)`, while `BlurViewModel` (`@JvmOverloads (blurScorerFactory, analysisDispatcher)`; the sensitivity source is a per-call argument) and `DuplicatesViewModel` (`@JvmOverloads (analysisDispatcher)`) are plain `ViewModel`s with a no-arg constructor (`PlainViewModelFactoryRegressionTest`).

**Album search & sort** — the `albums` entry keeps the search query (`rememberSaveable`, outside the state `when`) and the grid state in `AlbumsScreen`; `AlbumsViewModel` owns only the sort (`albumSort`: stored `album_sort` preference overridden by the session choice until the store confirms it or a logout clears it) and keeps `AlbumsState.albums` in server order. `AlbumsViewModel.sortedAlbums` builds the index and sorts off the main thread (injectable `computeDispatcher`, default `Dispatchers.Default`; `albumNameKey()` bounds names to 255 chars) and the screen only filters it with the pure `AlbumListOrdering.kt` functions; `d:getlastmodified` comes from `listAlbums()` only (`ALBUMS_PROPFIND_BODY`).

After process death a restored review entry gets a fresh detail ViewModel; the review loads the album itself (`loadAlbum(albumHref)`) and scans once it is loaded.

`rememberParentEntry()` (`ui/navigation/BackStackEntries.kt`) remembers `navController.getBackStackEntry(parentRoute)` keyed on the destination's own `NavBackStackEntry`: the lookup is cached across recompositions and re-resolved whenever the current entry changes, which is the form the navigation-compose `UnrememberedGetBackStackEntry` lint check accepts. Keying on a constant such as the route string is forbidden, and the check must never be silenced (issues #24 / #43).

`NoLintSuppressionRegressionTest` (backed by `LintSuppressionScanner` in the test source set) enforces this in `./gradlew test`: it scans every source set under `app/src` (`.kt`, `.kts`, `.java`) for `@Suppress`/`@SuppressLint`/`@SuppressWarnings` (any use-site target such as `@file:`, qualified or not, single- or multi-line) and `noinspection` comments naming the issue, and fails if `app/build.gradle.kts`, `app/lint*.xml`, any `app/*baseline*.xml` or the root `lint.xml` mention the issue id at all. The module and root directories are passed to unit tests as the system properties `krhnles.moduleDir` / `krhnles.projectDir` (`testOptions.unitTests.all` in `app/build.gradle.kts`); the test falls back to the working directory and fails loudly if `src/main` is not found. The test spells the issue id as a concatenation so the scan of its own source set does not flag its fixtures.

## New photos reminder (`new-photos-reminder`, issue #75)

An opt-in, local-only periodic check (Settings > "Remind me about new photos", off by default, interval Weekly / Every 2 weeks / Monthly = 7 / 14 / 30 days) that posts one notification when photos or videos were added to the device after the last upload and are not marked uploaded. Nothing in it uses the network, the credentials or the upload / download work.

- **Storage**: four plain keys in the credentials DataStore (`new_photos_reminder_enabled` / `_interval` / `_since` / `_last_shown`) through `CredentialStore` (`NewPhotosReminderRepository`, which `CredentialRepository` extends so the worker can be given only the reminder part). Plain `edit`s, no `credentials_version` bump; turning it on from off writes `since = now` and removes `last_shown` in one edit; `clear()` (logout) resets everything; the file is excluded from backup and device transfer. The interval is read type-safely (`asMap()[KEY] as? String`, fallback Weekly).
- **Scheduling** (`NewPhotosReminderScheduler`, interface `NewPhotosReminderScheduling`): one unique periodic work `new_photos_reminder` (period = interval, initial delay = one interval, `requiresBatteryNotLow`, no network constraint) enqueued only with `ExistingPeriodicWorkPolicy.UPDATE` (keeps the id, the enqueue time and a running instance; `CANCEL_AND_REENQUEUE` / `REPLACE` are never used). `cancel()` removes the notification, then the single `cancelUniqueWork(NEW_PHOTOS_REMINDER_WORK_NAME)` of the code base for this work (guarded: `NoUploadWorkCancelOutsideCancelPathRegressionTest` allows exactly that call in that file, which never references upload work). Every call is bounded and failures are logged by type. `SettingsViewModel.reminder` (`ReminderSettingsController.change()`) persists first, then schedules / cancels, serialized by a `Mutex` acquired with a timeout; logout adds a `clearLogged("reminder")` cancel step. `MainActivity.onCreate` (non-share path, fresh start only) calls `KrhnlesApplication.reconcileInBackground()` (3 s bounded read; unreadable setting = no change): enabled -> `UPDATE`, disabled -> `cancel()`. After a force-stop no reminder appears until the app is opened again.
- **Worker** (`NewPhotosReminderWorker`): always `Result.success()`. Disabled setting -> `scheduler.cancel()` as the last step. Otherwise: `ReminderNotifier.canPost()` (permission, app notifications, channel not blocked) -> `queryableKinds(MediaAccess.of(context))` -> bounded reads of history and markers (unreadable markers = post nothing) -> `NewMediaQuery` -> pure `countNewMedia()` -> re-read of the setting (still enabled, same `since`) -> post -> `markNewPhotosReminderShown(now)`. Baseline = later of `since` and the newest history entry with `photoCount > failedCount` (a cancelled run counts). Items are counted by `DATE_ADDED` (seconds) after the baseline, not marked uploaded (`mediaItemId` tells video and image ids apart); nothing is posted unless an item is newer than the previous reminder.
- **Query** (`NewMediaQuery`): per kind one `contentResolver.query(collection, [_id, date_added], Bundle, CancellationSignal)` with `reminderSelection()` (`date_added > ? ## Data Flow

1. **Photo Loading**: `MediaRepository` queries `MediaStore.Images` and `MediaStore.Video` → merged, grouped by date in `PhotoGridViewModel` (see [Videos](#videos-issues-15--34))
2. **Selection**: User taps photos or date headers → selection state in ViewModel
3. **Upload Trigger**: FAB → occasion dialog *or* auto date preview dialog (the occasion dialog suggests recent occasions and existing server folders, see [Occasion folder suggestions](#occasion-folder-suggestions-issue-72)) → exactly one `UploadBatch` per selection → `UploadEnqueuer` → one `WorkManager.enqueue(UploadWorker)` call
4. **Upload Execution**: `UploadWorker` reads config from `CredentialStore`, creates the remote folder(s) via `WebDavClient.createDirectories()`, uploads each file via `WebDavClient.uploadFile()` (streamed request body, no full in-memory byte copy), records each successfully uploaded photo ID right after its upload via `UploadedPhotosStore.markAsUploaded()` and persists the entry's `uploaded` marker in the queue file
5. **Progress**: Worker emits progress via `setProgress()` and shows system notifications
6. **History**: Upload outcomes are persisted via `UploadHistoryStore` and shown on the Upload History screen
7. **Album Management**: The Albums flow lists remote directories and can rename an album in place via `WebDavClient.renameDirectory()` using WebDAV `MOVE`, updating UI state without re-fetching the full album list. The MOVE is hardened: `renameDirectory()` awaits the call cancellably (`awaitStatus()`, no `callTimeout`) on a non-redirecting client derived from the shared one, sends the source as collection URL (trailing slash) with `Overwrite: F`, accepts only 201 / 204 and otherwise throws `WebDavHttpException(code)`. `renameDirectory(oldSegments, newSegments)` takes decoded segment lists (never joined strings) and rejects blank segments, `\\` and ISO control characters instead of filtering them. `AlbumsRepository.renameAlbum()` trims and re-validates the name with `isValidOccasionName` (`InvalidAlbumNameException`) and `exceedsAlbumNameLimit` (255 UTF-8 bytes, `AlbumNameTooLongException`), requires the source exactly one level below the base folder without empty / blank segments (`UnsafeHrefException`), and runs in `resultOf {}` (no request on rejection). A 2xx other than 201 / 204 maps to `AlbumsError.RenamePartial` and, like a timeout, reloads the list. The success branch drops another entry with the new href (duplicate grid keys). `AlbumsScreen` consumes the rename outcome only after its snackbar was shown, so a rotation does not lose it. `WebDavClient`'s interceptor adds `Authorization` only for the configured origin (`hasSameOriginAs`). `AlbumsViewModel.renameAlbum()` is a guarded one-shot (`renameJob`, `withTimeoutOrNull(30 s)`, failures become a `RenameOutcome` exposed as one-shot `renameOutcome` / `consumeRenameOutcome()`, busy flag reset in `finally`); a timeout reports `AlbumsError.RenameTimedOut` and reloads the list, and Refresh is ignored while a rename runs. `Throwable.toRenameAlbumError()` maps 412 -> `AlreadyExists`, 404 / 409 -> `AlbumGone`, 400 / 403 -> `RenameRejected`, everything else via `toAlbumsError()`. Pending uploads / retry queues keep the old folder name (known limitation)

### Retry of failed photos (issues #19 / #38)
- **Queue file as failure record**: after a partial upload `UploadWorker` writes `noBackupFilesDir/retry_queue_<uuid>.json` (same format as the input queue, failed photos only: a top-level `folderName`, or for auto date uploads a `folderName` on every entry plus the top-level `label`; each failed photo keeps its own folder, folders are never re-derived) and the completion notification gets a "Retry Failed (N)" action to `RetryUploadReceiver`. Only names `retry_queue_[0-9a-f-]+.json` / `upload_queue_<millis>_<uuid>.json` directly in `noBackupFilesDir` (new files; excluded from cloud backup and device transfer automatically because they contain per-photo capture days; `UploadEnqueuer` writes there too) or in the legacy `filesDir` (files and retry notifications of older versions) are accepted, no other parent (receiver and worker, `isRetryQueueFile` / `isWorkerQueueFile` in `worker/QueueFiles.kt`, canonical-parent check, so subdirectories and traversal are rejected). A missing or malformed queue file in the worker ends with `Result.failure()`; a malformed file is deleted. The format is decided from the content (`parseUploadQueue`, `worker/UploadQueue.kt`), never from a version field; `folderName` / `label` are read strictly with `opt(key)` + `is String` (Android `org.json` `getString` / `optString` would coerce `5` or `null` to strings). See *Upload Path Construction* for the rules.
- **Per-photo read failures**: a narrow try around `openInputStream` (`SecurityException`, `FileNotFoundException`, `IllegalArgumentException`; class name logged only) counts the photo as failed and keeps it in the retry file; progress / foreground updates run for failed photos too. `CancellationException` is never caught.
- **Wi-Fi-only** (`worker/UploadConstraints.kt`): `uploadConstraints(wifiOnly)` builds the constraint for the original upload and the retry; `readWifiOnly(flow)` reads `first()` bounded by `withTimeoutOrNull(3 s)`, timeout / failure -> unmetered. Enqueueing lives in the process-scoped `UploadEnqueuer` (`upload/UploadEnqueuer.kt`, owned by `KrhnlesApplication.uploadEnqueuer`, scope `KrhnlesApplication.appScope`): non-suspend `enqueue(batches)` launches in the application scope, reads the setting with `readWifiOnly`, writes the queue files, awaits `workManager.enqueue(...)` and then shows the toast on Main, so an upload is never lost when the activity is destroyed (rotation, dismissed share dialog). The share path calls it (with an `onFailure` callback that deletes the staged copies) only after copying, then `finish()`es; `ShareViewModel` ignores every confirm after the first. A queue file whose WorkManager enqueue fails is deleted. A setting switched on after enqueue is honoured by `UploadWorker.doWork()`: Wi-Fi-only on and `isActiveNetworkMetered` -> `Result.retry()` (WorkManager backoff, queue file kept). Settings shows the toggle as a single `toggleable(role = Role.Switch)` row (`wifiOnlyRow`, label and hint merged, inner `Switch` non-interactive, 48 dp minimum height). The setting is off by default, reset by `CredentialStore.clear()` (logout) and, living in the credentials DataStore, not restored from backup. `UNMETERED` means unmetered, not Wi-Fi: a metered hotspot waits, an unmetered cellular plan uploads. Work enqueued with the setting on stays constrained after it is switched off until an unmetered network is available or the user retries.
- **Receiver**: `onReceive` uses `goAsync()` with a fresh `CoroutineScope(SupervisorJob() + Dispatchers.IO)` per broadcast, delegates to `internal suspend fun handleRetry(context, intent, wifiOnly: Flow<Boolean>, timeout)` and calls `finish()` in `finally`. `handleRetry` cancels the notification from the extras (tag + id) first, then validates the file, then `enqueueUniqueWork(retryFileName, ExistingWorkPolicy.KEEP, ...).await()` (tag `photo_upload`), so the request is persisted before `finish()`. At most one retry runs per retry file at a time; a later tap after it finished finds no file and does nothing (old retry files are not pruned).
- **Notification ids**: the foreground / progress notification keeps id 1001; every result notification (success, partial, failure, folder-creation failure) uses `UploadWorker.RESULT_NOTIFICATION_ID` (1002) with the input queue file name as notification tag (`notify(tag, id, ...)`; no hash, no collisions); the notification builders are top-level `Context` extensions in `worker/UploadNotifications.kt`. The retry `PendingIntent` has a unique data URI `retry://<retryFileName>` because `PendingIntent` identity ignores extras. The receiver cancels exactly the tag + id carried in the extras.
- **Folder-creation failure**: `WebDavClient.createDirectory` / `createDirectories` return a `Result` whose failure is a `WebDavHttpException(code)`; the worker first validates the folder path (`isValidFolderPath`: no `.` / `..` / empty segment / backslash) and maps failures with `FolderCreationError` (`worker/FolderCreationError.kt`: `InvalidFolderName`, `FolderNotAvailable` for 403 / 404 / 409, `NotConfigured`, `Connection(AlbumsError)`, `Generic`) into `notification_create_folder_failed` with `upload_error_*` reasons (never raw exception text, never album wording). `OccasionDialog` (`ui/share`, used by the photo grid and the share target) rejects `.` / `..` / `/` / `\` names inline (`isValidOccasionName`).
- **Test seam**: `UploadWorker` has an internal constructor `(context, params, CredentialRepository, (WebDavConfig) -> WebDavClient)`; WorkManager uses the public `(context, params)` constructor (`CredentialStore`, `::WebDavClient`). `UploadWorkerRunTest` runs the real worker with `TestListenableWorkerBuilder.setWorkerFactory`, `FakeCredentialRepository` and MockWebServer; The tests call `doWork()` directly (the work-testing scheduler would hide the `Result`); the internal constructor also takes the metered-network check. `RetryUploadReceiverTest` calls `handleRetry` with fake flows; `UploadEnqueuerTest` injects scope and dispatchers.
- **URI policy**: the share target (`parseSharedPhotos(intent, ownPackage)`) and `UploadWorker.openPhoto` only accept `content://` URIs whose authority is not the app's own (`isAllowedPhotoUri`); `file://` URIs are rejected (a rejected queue entry counts as a failed photo). Log lines contain exception class names only.
- **Staged entries**: shared photos are retried from their staged copy (`staged` is copied into the retry file; the worker keeps the staged files of the new retry file when it deletes the queue; a cancelled upload deletes the staged copies of the uploaded items at once and keeps the others, see *Cancelling a running upload*). Every retry writes its own history entry (photo count = retried photos).


### Cancelling a running upload (`cancel-running-upload`, issue #70)
- **Entry points**: the progress notification (`buildProgressNotification()`, also `getForegroundInfo()`) has a "Cancel" action: an explicit, `FLAG_IMMUTABLE` broadcast `PendingIntent` (request code 2002, unique data URI `cancel-upload://<workId>`) to `CancelUploadReceiver` (`android:exported="false"`, `goAsync()` + fresh IO scope + `finish()` in `finally`, delegating to `internal suspend fun handleCancel(intent, workManager)`). The Photos tab banner (`UploadProgress.workId` = the id of the running `WorkInfo`) calls `PhotoGridViewModel.cancelUpload(workId)`, a guarded one-shot (`cancelUploadJob` re-entry guard, failures logged by type only). Both call the shared `cancelRunningUpload(workManager, workId)` (`worker/UploadCancellation.kt`): bounded (5 s) read of the work info, cancel only if it exists, has the tag `photo_upload` and is `RUNNING`, then `cancelWorkById().await()` (bounded) so the cancel is persisted before the receiver finishes. Malformed / missing ids, unknown, enqueued, finished or non-upload work are ignored. The receiver touches no file. This function is the only code that cancels work (`NoUploadWorkCancelOutsideCancelPathRegressionTest`: WorkManager cancel APIs only in `worker/UploadCancellation.kt`, no `ExistingWorkPolicy.REPLACE` / `APPEND_OR_REPLACE`, which would also stop with `STOP_REASON_CANCELLED_BY_APP`).
- **User cancel vs. system stop**: `UploadWorker.doWork()` wraps everything after the queue parse in `try { … } catch (CancellationException)`. It is a user cancel only if `isStopped && stopReason == WorkInfo.STOP_REASON_CANCELLED_BY_APP` (`userCancelled()`; the internal-constructor seam `userCancelled: (() -> Boolean)?` replaces the rule in tests). WorkManager sets the stop reason *before* the coroutine is cancelled (pinned end-to-end by `UploadWorkerCancelWorkManagerTest`, which uses the real rule with a real test `WorkManager`). Every other reason (constraints, `STOP_REASON_FOREGROUND_SERVICE_TIMEOUT`, preemption, quota, unknown) rethrows unchanged: queue file and progress stay, WorkManager re-runs, nothing is reported, no interruption is counted. A `CANCELLED_BY_APP` stop is terminal in WorkManager, so the queue is finalized by the worker; `interrupted()` never counts a user cancel (it throws a `CancellationException` first).
- **Transfer and bookkeeping**: coroutine cancellation aborts the running request (`executeCancellable` -> `Call.cancel()`; since this change also the folder `MKCOL`, which used a blocking `execute()`). A finished `PUT` is always booked: `bookOutcome()` (queue rewrite with `"uploaded": true`, `markUploaded`, `recordOutcome` / verified record) runs in `withContext(NonCancellable)` with each DataStore write bounded (`BOOKKEEPING_TIMEOUT_MS` = 5 s), so a cancel that arrives as the response returns still counts the item as uploaded; the cancel surfaces at the next suspension point. A cancel during a verification download leaves the item pending (it is re-sent; its target records were dropped before the `PUT`). Terminal reporting (`finish()`, folder-creation failure, not configured) runs through `terminalReport {}` (`NonCancellable`, sets `terminal`); a cancel after the last item therefore yields the normal completion, never a second history entry, and `finalizeOnCancel()` is skipped when `terminal` is set.
- **Finalization = claim by rename** (`finalizeCancelledQueue(context, queueFile, queue, failures, history)`): the queue file is renamed (atomic) to a new `noBackupFilesDir/retry_queue_<uuid>.json`; only the caller whose rename succeeds continues (`CancelFinalization.NotClaimed` otherwise), so a worker and the recovery finalize exactly once, and the claimed file is already a valid retry file if the process dies. Nothing pending -> `deleteQueueFile()` and the usual completion; otherwise the file is rewritten with `UploadQueue.toRetryJson(pending)` (only the entries not uploaded, each with its folder, no `uploaded` markers, no `interruptions`: a user cancel never uses the interruption budget), its mtime is refreshed (the 7-day staging window starts at the cancel), and the staged copies of uploaded entries are deleted (only after the rewrite succeeded). Then one history entry (`cancelled = true`, `failedCount` = items not uploaded) and one result notification (`RESULT_NOTIFICATION_ID`, tag = the original queue file name) titled "Upload cancelled" with "N uploaded, M not uploaded." (reasons joined via `joinNotificationTexts()`), never the word "failed", and the existing "Retry Failed (M)" action (`FLAG_IMMUTABLE`, `retry://<retryFile>`). The whole function runs `NonCancellable`; its history write is bounded (`CANCEL_FINALIZE_TIMEOUT_MS` = 10 s). A cancelled retry run produces a new retry file (new unique work name). Guarded by `UploadWorkerCancelTest`, `UploadCancellationTest`, `UploadNotificationsTest`.
- **Start-up recovery** (`recoverCancelledUploads()`, launched once per process from `KrhnlesApplication.onCreate` in `appScope`): covers a cancel that reached work between two runs (cancelled while `ENQUEUED` after a `Result.retry()`) or a process that died before the worker finalized. `uploadWorkRequest()` adds the per-queue tag `upload_queue_file:<queueFileName>` (`queueFileTag()`, next to `photo_upload`). The recovery takes one snapshot of the upload / retry queue files accepted by `QueueFiles.kt` (both parents) and, per file, the tagged work infos (bounded 5 s). A file is a candidate only if it has work and **all** of it is `CANCELLED`; unknown state, timeout, no work (legacy work without the tag, or pruned by WorkManager) or any other state leaves it untouched (fail-closed). After `CANCEL_RECOVERY_GRACE_MS` (30 s, longer than a worker's bounded bookkeeping and finalization) each candidate that still exists is parsed (unparsable stays untouched) and finalized through `finalizeCancelledQueue()`. A pruned orphan keeps its staged copies until the age sweep.
- **History**: `UploadHistoryEntry.cancelled` (default false) is written as `"cancelled": true` only when set and read strictly (`opt == true`); the history screen shows `upload_history_counts_cancelled` ("Cancelled · X uploaded · Y not uploaded").
- **Chunked transfers (`nextcloud-chunked-upload`, issue #69)**: on a *user* cancel `UploadWorker.finalizeOnCancel()` first runs `finalizeCancelledQueue()` (claim, retry file without `chunked` progress, history, "Upload cancelled" notification — never delayed by the network), **then** aborts every open chunked transfer: each `chunked` state of the worker's live queue whose binding matches the run's server / account / destination (the in-flight transfer is saved there before its `MKCOL`; a cancel that comes before the run read its configuration — Wi-Fi-only or config read — reads it itself via `cancelAborter()`, bounded and `NonCancellable`), each `DELETE` `NonCancellable` and bounded by `CHUNKED_CANCEL_ABORT_TIMEOUT_MS` (10 s), failures logged by type / code only. A `MOVE` answered 2xx clears its state at once (no longer open) and is booked by `bookOutcome()`, so a cancel right after it never sends a `DELETE`. A system stop keeps the transfers for the next run; a cancel finalized by `recoverCancelledUploads()` after process death sends nothing (the server's 24 h cleanup removes the folder). There is no second cancel predicate: only `userCancelled()` decides. Tested in `UploadWorkerChunkedTest`.
- **Tests**: `UploadCancelHarness` (MockWebServer that holds a request until the cancel aborts it, queue files over the fake MediaStore, real worker with fakes), `UploadWorkerCancelTest`, `UploadWorkerCancelWorkManagerTest` (real test `WorkManager`, no seam, system stop via `Processor.stopForegroundWork`), `CancelUploadReceiverTest` (also asserts the manifest entry is not exported), `UploadCancellationTest`, `PhotoGridViewModelCancelTest`, `PhotoGridCancelUploadTest`. Workers that wait inside tests use `holdUntilCancelled()` (a timer-backed loop): a coroutine parked in `awaitCancellation()` can have its `CallbackToFutureAdapter` completer garbage collected, which fails the work.

## Videos (issues #15 / #34)

- **Permissions** (`ui/photogrid/MediaAccess.kt`, `PhotoGridScreen`): the manifest declares `READ_MEDIA_VIDEO`; the grid requests `READ_MEDIA_IMAGES`, `READ_MEDIA_VIDEO` and `READ_MEDIA_VISUAL_USER_SELECTED` in one `RequestMultiplePermissions` call. Access = any granted. "Video missing" (`MediaAccess.videoMissing`) = images granted and video not, which only happens for users upgrading from the images-only version: requested once automatically, guarded by the persisted `video_access_requested` flag (`MediaPermissionStore`, `app_preferences`, excluded from backup; the screen waits until the flag is read — `videoAccessRequested` is `null` before) plus a per-session `rememberSaveable` guard. Partial-access users are never asked automatically; they get the "Select more photos and videos" banner, which re-launches the request. The video banner's action re-launches the request, or opens `ACTION_APPLICATION_DETAILS_SETTINGS` after a permanent denial: `videoDenial()` classifies a denied result as `Permanent` only when `shouldShowRequestPermissionRationale(READ_MEDIA_VIDEO)` is false *and* a rationale was offered before (persisted `video_rationale_shown`, set after a denial with rationale or when the grid starts with a rationale pending); without an earlier rationale a false value means a dismissed dialog (`Dismissed`, the banner keeps asking). Every permission result that keeps access reloads the media, so a widened grant (images-only → + video, partial → full) shows the new items at once. Access is re-read on every resume (`LifecycleResumeEffect`). No access → the existing `PermissionDeniedContent`.
- **Query and ids** (`MediaRepository`): a second query on `MediaStore.Video.Media.EXTERNAL_CONTENT_URI` (`_ID, DISPLAY_NAME, DATE_TAKEN, SIZE, MIME_TYPE, DURATION`); a `SecurityException` from it yields only the images. Both lists are sorted by raw `DATE_TAKEN` descending (stable). Image and video `_ID`s overlap, so `mediaItemId(rawId, kind)` keeps image ids and sets `Photo.VIDEO_ID_FLAG` (`1L shl 62`) for videos; raw ids `< 0` or `>= 2^62` are skipped. The ids stay positive, so selection, `UploadedPhotosStore` (string set) and the queue JSON (`id >= 0` = markable) need no migration. `Photo.mediaKind` comes from the query, never from the mime type; a null / blank video `MIME_TYPE` uploads as `video/*`. Undated videos map to `Photo.UNKNOWN_DATE` like images (auto date folder `1970/01/01`; no `DATE_MODIFIED` fallback).
- **Thumbnails**: `coil-video` (same version as Coil) would register `VideoFrameDecoder` for every source through Coil 3's service loader; `KrhnlesApplication.newImageLoader` therefore calls `serviceLoaderEnabled(false)` (which also drops the service-loaded default OkHttp fetcher, `MediaDataSourceFetcher` is unused) and registers the authenticated `OkHttpNetworkFetcherFactory` and `LocalVideoFrameDecoderFactory` explicitly. The wrapper delegates to `VideoFrameDecoder.Factory()` only for sources with `ContentMetadata` of a `content://` URI (produced by Coil's `ContentUriFetcher`); network and disk-cache sources are refused, so a server answering a thumbnail request with `video/mp4` never reaches `MediaMetadataRetriever` (`VideoDecoderRegistrationTest`). Tiles keep `AsyncImage(photo.uri)`; frame extraction is slower than image decoding (scroll performance is a manual device check).
- **Upload** (`WebDavClient.uploadFile`): one `PUT` per file through `executeCancellable` (cancelling the worker cancels the transfer), on `uploadClient` = `noRedirectClient.newBuilder().readTimeout(5 min)` (shares pool, dispatcher and the origin-restricted auth interceptor; the server may finalise a large file long after the last byte); never a `callTimeout`. Uploads never follow redirects: OkHttp turns a 301 / 302 / 303 `PUT` into a body-less `GET`, whose 2xx would look like success, so every 3xx fails as `WebDavHttpException(code)`. This also closes OkHttp keeping `Authorization` on a same-host, same-port https → http redirect (the application interceptor runs only for the original request). `InputStreamRequestBody` is one-shot and reports `contentLength()` from the size the worker reads inside the stream's `use` block with `openAssetFileDescriptor(uri, "r").length` (closed again; `UNKNOWN_LENGTH` / any error → `-1` = chunked; staged share copies use only their own file size, never the entry URI). HTTP 413 / 507 map to `UploadFailure.TooLarge` / `StorageFull` (`Throwable.toUploadFailure()`, branches on `WebDavHttpException.code`) and their messages (`upload_failure_*`) are appended to the result notification. Large files on Nextcloud use chunked upload instead (next section).
- **Per-entry progress and foreground service limits**: after each successful entry the worker rewrites the queue file atomically (`rewriteQueueFile()`: `<name>.tmp` + rename; the entry gets `"uploaded": true`, `UploadQueue.toProgressJson()`) and marks that photo uploaded at once. A re-run (refused foreground service, process death, WorkManager stop) skips finished entries (`pendingIndices`); result counts, history and notification cover the whole batch including earlier runs. Files without markers (older versions, retry files) upload every entry. Every `setForeground` call goes through `setForegroundOrFalse()`; a refused foreground service (`ForegroundServiceStartNotAllowedException`, e.g. the `dataSync` time budget is used up) returns `Result.retry()` and keeps the queue file and its staged copies — except after the last entry (the batch is complete) and once `interruptions + 1 >= MAX_UPLOAD_RUN_ATTEMPTS` (5; `interruptions` is an optional top-level int of the queue file, absent = 0, rewritten by `UploadWorker.interrupted()` via `rewriteQueueFile()` before `Result.retry()`; retry files start at 0; Wi-Fi-only wake-ups and constraint stops never count, `runAttemptCount` is only a backstop for the cap (the run also gives up when `rewriteQueueFile()` fails and `runAttemptCount >= MAX_UPLOAD_RUN_ATTEMPTS`, and always at `MAX_UPLOAD_RUN_ATTEMPTS_BACKSTOP` = 10x the cap), the value is clamped to `0..MAX_UPLOAD_RUN_ATTEMPTS` when parsed (Int, Long, Double, negative), though WorkManager's back-off delay still grows with them up to 5 h): then the run stops with an "Upload failed" notification (`upload_failure_interrupted`) and a retry file for the entries not uploaded yet. Upload work requests come from `uploadWorkRequest()` (`worker/UploadConstraints.kt`, used by `UploadEnqueuer` and `handleRetry`) with an explicit exponential back-off (60 s initial). Only the entry interrupted mid-transfer is sent again (the PUT overwrites; Nextcloud may keep an extra file version).
- **Unchanged by design**: `UploadedPhotosStore` (the queue format only gains the optional `uploaded` marker), the share target (image-only). Album screens list and play videos since issue #74, the duplicate / blur reviews stay photo-only (see "Videos in albums").

### Chunked upload (issue #69)

Spec: `openspec/specs/chunked-upload` and `openspec/specs/upload-verification` (change archived as `openspec/changes/archive/2026-11-03-nextcloud-chunked-upload`).

- **Eligibility** (`data/NextcloudChunking.kt`): `nextcloudUploadsCollection(configUrl)` maps a files URL `<prefix>/remote.php/dav/files/<user>/…` to `<prefix>/remote.php/dav/uploads/<user>` (same scheme / host / port, sub-path installs kept; the user segment is checked by the shared `validatePathSegment()`); any other shape (`/remote.php/webdav/`, plain WebDAV, unsafe user segment) is `null`. `UploadWorker.uploadPhoto()` uploads in chunks iff that collection exists, the run-wide `chunkingUnavailable` flag is unset and `uploadLengthOf()` reports a known length of at least `ChunkedUploadPolicy.thresholdBytes` (`DEFAULT_THRESHOLD_BYTES` = 50 MiB); everything else stays one `PUT`. Staged (shared) entries can be chunked too and stay unverified.
- **Protocol** (`WebDavClient`): `createChunkedUpload` = `MKCOL <collection>/<transferId>` with `Destination` (absolute target URL from validated segments) and `OC-Total-Length` → `ChunkedUploadCreation.Created` (201) / `AlreadyExists` (405); `uploadChunk` = `PUT <transferId>/<chunkName(n)>` (`00001` … `10000`, `MAX_CHUNK_NUMBER`) with `Destination`, `OC-Total-Length` and `Content-Length` = the chunk, body `BoundedInputStreamRequestBody` (one-shot, copies exactly the chunk from the shared stream, never closes it, `IOException` on early EOF), any 2xx, never `X-Hash`; `finishChunkedUpload` = `MOVE <transferId>/.file` with `Destination`, `OC-Total-Length` (load-bearing: a lost v2 session falls through to the classic assembly of an empty folder and is rejected with 400) and `X-Hash: sha256` only when requested, only 201 / 204, `X-Hash-SHA256` kept only as 64 hex; `abortChunkedUpload` = `DELETE <transferId>` (2xx / 404 = success). All run through `executeCancellable`, rethrow `CancellationException`, report other statuses as `WebDavHttpException(code)` and never follow redirects. `MKCOL` / chunk `PUT` / `DELETE` use `uploadClient`; the `MOVE` uses `assemblyClient` = `uploadClient.newBuilder().readTimeout(CHUNK_ASSEMBLY_READ_TIMEOUT_MINUTES)` (30 min: the server assembles the whole file before answering; same pool, interceptor and no-redirect rule, never a `callTimeout`). Transfer ids are `krhnles-` + 32 lower-case hex (`newTransferId()` / `isValidTransferId()`, checked before any request).
- **Persisted state** (`worker/ChunkedTransfer.kt`): `UploadQueueEntry.chunked: ChunkedTransferState?`, the optional entry object `"chunked"` with `transferId`, `chunkBytes`, `totalBytes`, `confirmedChunks`, `prefixSha256` (SHA-256 of the confirmed prefix, `EMPTY_SHA256` for none), `original` (source was `UploadSource.Original`) and `binding` (`chunkedBinding(collectionUrl, destinationUrl)`, SHA-256 hex, so no URL or user name is stored). Parsing is strict per field but **lenient per object** (the chunk count is compared as a `Long` with `MAX_CHUNK_NUMBER` before any conversion to `Int`, so a crafted count cannot wrap into range; `chunkBytes` must be in `1..totalBytes`; `confirmedBytes` never multiplies past the total): an invalid `chunked` value is dropped and the entry uploads from the start (unlike a wrong folder, progress never changes the destination). `withChunked(i, state)` + `rewriteQueueFile()` save it, `withUploaded(i)` and `toRetryJson()` clear it (retry files never carry progress), `toProgressJson()` keeps it. The chunk size is `ChunkedUploadPolicy.chunkBytesFor(total)` = `DEFAULT_CHUNK_BYTES` (10 MiB) or, above 10,000 chunks, the smallest whole MiB that keeps the count ≤ `MAX_CHUNK_NUMBER`; fixed per transfer.
- **One attempt** (`worker/ChunkedUploader.kt`, design D5): read `before` and open the source exactly like a `PUT` (`openVerifiable` → `openEntry` / `openForUpload`); inside the stream's `use`, `uploadLengthOf()` first, then `DigestCountingInputStream`. The saved state is kept only with the same binding, `totalBytes`, `original` and the chunk size the policy chooses for the length (`chunkBytesFor`); same binding but a different length / source kind / chunk size → `DELETE` of the old id, another binding → no request for it (`discard()` sends a `DELETE` only for the uploader's own binding, also when the file can no longer be opened). An `IOException` inside an attempt (a local read) is transient; any other non-cancellation exception (e.g. a provider `SecurityException` during the prefix re-read) fails the file instead of escaping the worker. `applyUploadLogged(target)` runs before the first request of every attempt. A new transfer is saved (`confirmedChunks = 0`) **before** its `MKCOL`, which must be `Created`; a saved one sends `MKCOL` again: `AlreadyExists` continues, `Created` (server dropped the folder) restarts at chunk 1 with the same id. The confirmed prefix is read again on the device through the digest stream (nothing sent) and must equal `prefixSha256`, else `DELETE` + restart. After every 2xx chunk the state (`confirmedChunks + 1`, new `prefixSha256` from the clone-based `sha256Hex()`) is saved and, except after the last chunk, the notification shows the file percentage through `setForegroundOrFalse()` (a refusal = `Interrupted`, see below). After the last chunk the stream must be at EOF (a grown file restarts). The `MOVE` requests the server hash iff the source is an original and the verifier asks for it (`requestsServerHash`); on 2xx the state is cleared at once and the response + digest stream go to the unchanged `verifyUpload()`, so a record still only comes from an `UploadSource.Original` and the digest covers the whole file read once in this attempt.
- **Attempts and failures** (design D6 / D10): at most `MAX_CHUNKED_ATTEMPTS_PER_RUN` (3) attempts per file and run, each resuming from the saved state. Transient (`isTransientChunkFailure()`): non-cancellation `IOException`, 408, 423, 429, 5xx except 501 and 507; waits `CHUNKED_RETRY_DELAYS_MS` (2 s, 8 s, cancellable). 404 / 409 / 412 on a chunk `PUT` or the `MOVE` = the server lost the upload (v2 session evicted, 24 h cleanup): `DELETE` + restart with a new id; lost at the `MOVE` (every chunk confirmed) this happens at most `MAX_MOVE_LOST_RESTARTS_PER_RUN` (1) time per file and run, a second such answer fails the file (a server cannot make the app send a file again and again). When the **last** attempt failed transiently (e.g. a network outage longer than the 2 s + 8 s waits) the progress is **kept** and the run ends as an interruption (`ChunkedResult.Interrupted`, see below) instead of discarding the confirmed chunks. Anything else fails the file through `toUploadFailure()` (413 → too large, 507 → storage full, else Other), with a `DELETE`. A `MKCOL` answered with a non-transient status other than 413 / 507 (404, 405, 403, 400, 501, 3xx, or 405 for a fresh id) means no usable uploads endpoint: the state is cleared (a saved transfer is also aborted), `chunkingUnavailable` is set and this and every later file of the run use one `PUT` (not persisted; the next run tries again). A file whose saved transfer is not continued (now single `PUT`, e.g. it shrank below the threshold) has that transfer aborted first.
- **Interruptions and cleanup** (design D7 / D8): a refused foreground service between chunks, and a file whose last attempt of the run failed transiently, end the run like a refusal between files (`UploadRun(interrupted = true)`, progress kept, `Result.retry()` with WorkManager's exponential back-off, same `interruptions` budget — no `NetworkType.CONNECTED` constraint is added); at the cap (`finish(gaveUp = true)`), after a folder-creation failure (before it is reported) and at the end of a normal run every remaining binding-matched transfer of the queue is aborted (`abortOpenTransfers`). A WorkManager stop or process death sends nothing: the next run resumes. Aborts are `abortQuietly()`: `NonCancellable`, bounded by `CHUNKED_ABORT_TIMEOUT_MS` (30 s) inside a run and `CHUNKED_CANCEL_ABORT_TIMEOUT_MS` (10 s) on the user-cancel path, never throwing, logged by type / HTTP code only, never changing the result or the notification. The server's 24 h `UploadCleanup` removes what the app can no longer reach (malformed queue, other account, older app version, recovery after process death, a `MOVE` or `MKCOL` whose answer was lost). Known limit: a stop or cancel during the verification download after a `MOVE` leaves the file unbooked, so it is uploaded again on the next run / retry (as for a single `PUT`).
- **Progress**: `buildProgressNotification(current, total, workId, filePercent)` shows `notification_uploading_file_progress` ("%1$d / %2$d · %3$d %%") while a file is chunked (the bar stays per batch, the Cancel action stays).
- **Test seam**: `UploadWorker.chunking: ChunkedUploadSettings` (`@VisibleForTesting internal var`, not a constructor parameter) bundles the policy, the wait between attempts and both abort bounds; user cancels use the existing `userCancelled` seam. Tests: `NextcloudChunkingTest`, `WebDavClientChunkedTest`, `WebDavClientTest` (assembly client), `ChunkedTransferTest`, `ChunkedUploaderTest` (the uploader alone: no request for a foreign binding, a `SecurityException` fails the file), `UploadQueueProgressTest`, `UploadNotificationsTest`, `UploadWorkerChunkedTest`, `UploadWorkerChunkedRecoveryTest` (review cases: outage keeps progress, one restart after a lost `MOVE`, aborts on an early cancel / folder failure, chunk-size check) and the chunked cases of `UploadWorkerVerificationTest`, both over `ChunkedUploadHarness` (MockWebServer behaving like Nextcloud's upload folders, `FakeMediaStoreProvider.files` with a real length, threshold 20 bytes / chunks of 10). A hanging `DELETE` is tested with a small real-time bound, not virtual time.

## Videos in albums (issue #74)

- **Classification** (`AlbumsRepository.classifyRemoteMedia(entry): MediaKind?`): directory -> not listed; `isImage()` (unchanged) -> `Image`; an allow-listed content type (`VIDEO_CONTENT_TYPES`: mp4, x-m4v, quicktime, 3gpp, 3gpp2, webm, x-matroska; parameters stripped, case-insensitive) -> `Video`; for a blank / `application/octet-stream` type an allow-listed extension (`VIDEO_EXTENSIONS`: mp4, m4v, mov, 3gp, 3g2, webm, mkv) -> `Video`; everything else is not listed (a specific non-video type wins over a video extension; AVI, WMV, FLV, MPEG-TS are not listed because the restricted extractor set cannot play them). `RemotePhoto.mediaKind` (default `Image`) is set by the listing, never derived from the content type later. `MAX_PHOTOS_PER_ALBUM` counts photos and videos together.

For a video: the Memories preview when available, else on Nextcloud the core preview `<base>/index.php/core/preview?fileId=<id>&x=&y=&a=1&mimeFallback=false` (used blind, no extra availability request; a failure ends in the placeholder), else `null` (plain WebDAV, unsafe or missing file id). The WebDAV URL of a video is handed out only by `videoStreamUrl()` and only the player requests it, after a tap. `AlbumDetailViewModel.thumbnailUrls` has no entry for a preview-less video; the tile then shows the movie placeholder (the spinner is only for images without URL). `LocalVideoFrameDecoderFactory` still refuses network bytes.

Both guard exceptions extend `IOException`: `OkHttpDataSource` uses `Call.enqueue()`, which rethrows any other interceptor exception on its dispatcher thread (crash). `AlbumsRepository.close()` closes the client with the repository, so a pin / config change (`AlbumsRepositoryProvider` replaces the repository) ends the stream.
- **Player** (`ui/viewer/`): `Media3VideoPlayerFactory` is the only Media3 construction site, `ExoPlayer.Builder(application, ProgressiveMediaSource.Factory(OkHttpDataSource.Factory(videoCallFactory()), extractors).setLoadErrorHandlingPolicy(...))` with `Mp4Extractor` / `FragmentedMp4Extractor` / `MatroskaExtractor` (each with `DefaultSubtitleParserFactory()`) and a policy that never retries an HTTP status or a guard refusal (a 401 would otherwise trigger Nextcloud brute-force throttling), under the user-approved single `@OptIn(UnstableApi::class)`. `NoTrustAllRegressionTest` forbids `DefaultDataSource`, `DefaultMediaSourceFactory`, `SimpleCache`, `CacheDataSource` and the one-argument `ExoPlayer.Builder(x)` (they use `DefaultHttpDataSource`, keep every extractor or leave copies on disk). `VideoPlayerViewModel` (`AndroidViewModel`, scoped to the viewer entry, never references the album ViewModel) runs a guarded one-shot `play(photo, repositories)` (job + generation), `pause()`, `resume()` (re-asks the source and continues only with the same repository, else rebuilds), `stop()`, `retry()`; the UI sees `VideoPlayback` / `VideoPlayerFactory` (no Media3 types), so tests use `FakeVideoPlayerFactory`. Errors: `PlaybackException.toVideoPlaybackError()` (guard exceptions -> generic, bad status by code -> `Redirected` / album errors, decoder / container -> `UnsupportedFormat`, network / TLS via `toAlbumsError()`); only the error code is logged.
- **Viewer lifecycle**: stop on page change, when the album reports `NotConfigured` / `ConfigurationChanged` or the video left the album; pause on `ON_STOP` unless `LocalActivity.current.isChangingConfigurations` (rotation keeps playing, the ViewModel survives); controls auto-hide only while a video plays, with `calculateRecommendedTimeoutMillis`. - **Tests**: data-source level with the real `OkHttpDataSource` and the real factory against `MockWebServer` (`Media3VideoPlayerFactoryTest`; Robolectric needs `ShadowLooper.idleFor` because the playback thread's delayed messages only run when the paused clock advances); UI tests use a fake player. ## Saving album photos (`download-album-photos`, issue #73)

Spec: `openspec/changes/download-album-photos` (`album-photo-download`, deltas for `webdav-href-validation`, `uploaded-photo-markers`, `remove-uploaded-photos`).

- **Entry points**: "Save to device" in the fullscreen viewer (top-end `IconButton`, photos only, a `rememberSaveable` set of saved hrefs disables it per photo) and in the album selection top bar (disabled while a deletion runs). Both call `AlbumDetailViewModel.saveToDevice(photos)`, which keeps only hrefs of the loaded listing and passes `(albumHref, hrefs)` to the injected `DownloadRequester` (default `KrhnlesApplication.downloadEnqueuer`). Videos are passed on; the worker reports them as `Unsupported`.
- **Queue file** (`worker/DownloadQueue.kt`): `noBackupFilesDir/download_queue_<millis>_<uuid>.json` with `serverUrl`, `albumHref`, `entries[{href, downloaded}]`, optional `account` (SHA-256 of URL and user name, no credential; absent = URL-bound), `pendingItem` (uri of the item being written) and `interruptions`. No username, password or token; the work input `Data` is only `queue_file`. Strict parse (`opt` + `is String`), `isDownloadQueueFile()` accepts only that pattern directly in `noBackupFilesDir`, progress is written with `rewriteQueueFile()`.
- **Chain semantics** (`download/DownloadEnqueuer.kt`): under a `Mutex` (only the wait for it is bounded, 30 s; the sweep has its own 60 s bound), the enqueuer sweeps queue files older than 30 s whose `download_queue:<name>` work is finished or unknown (bounded lookup, fail-closed, recorded `pendingItem` discarded first), writes the file and awaits `enqueueUniqueWork("photo_download", APPEND_OR_REPLACE, downloadWorkRequest())` (CONNECTED only; the Wi-Fi-only upload setting is ignored on purpose; exponential back-off; never the `photo_upload` tag). One batch runs at a time, so a single foreground id suffices. `APPEND_OR_REPLACE` (not `APPEND`) keeps the chain usable after a user cancel: the cancelled prerequisite is replaced, the new batch is not cancelled with it. A Cancel cascades to the batches queued after the cancelled one; their queue files are swept at the next request. The worker never returns `Result.failure()` (it would cancel the dependents): `success()` for every finished batch, `retry()` only for an interruption. `NoUploadWorkCancelOutsideCancelPathRegressionTest` allows `APPEND_OR_REPLACE` only in this file and `createCancelPendingIntent` only in `DownloadNotifications.kt` (user-approved narrowing; `REPLACE` stays forbidden, download work never carries the upload tag).
- **Transfer** (`WebDavClient.download`): see CLAUDE.md "Photo downloads" - pin-aware `noRedirectClient`, `Accept-Encoding: identity`, same-origin check, 200 MiB cap announced and streamed, fail-closed content checks (`Content-Type` parse and allow-list, `Content-Encoding: identity`, chunked-or-known length on HTTP/1.x; the first bytes are checked per type in the worker), `executeCancellable`, never buffered.
- **Output** (`data/LocalMediaWriter.kt`): an app may insert into and write, update and delete its *own* `MediaStore.Images` items without any storage permission. `insertPending` (`Pictures/KroehnSync/<album>/`, `IS_PENDING = 1`; MediaProvider appends ` (1)`, ` (2)` to a taken name, nothing is overwritten) -> `write {}` (destination failures become `StorageFullException` / `LocalMediaWriteException`, source failures keep their type) -> `publish()` only after the whole body; `discard()` (`NonCancellable`) on every other outcome. A killed run leaves a `pendingItem` that the next run (or the sweep) removes via `discardLeftover()`, which accepts only a `media` `<volume>/images/media/<id>` uri that is still pending and owned by this package. `DownloadOwnItemsOnlyRegressionTest` pins that this is the only delete.
- **Worker** (`worker/DownloadWorker.kt`): per entry: bounded config re-check (valid, same `serverUrl`), pin re-read (client rebuilt on change), `resolveDownloadTarget`, name and type (`DownloadNames.kt`), `setForegroundOrFalse` (refusal -> interruption, `MAX_DOWNLOAD_RUN_ATTEMPTS` 5, backstop on `runAttemptCount`), free-space check, download into the pending item, publish, `downloaded` marker. Stop rules: AccessDenied / Certificate (only certificate / handshake / unverified-peer failures; a plain `SSLException` is `Connection`) / StorageFull / ConfigurationChanged and 5 consecutive Connection / ServerError fail the rest of the batch with that reason. The first 32 bytes must match the type's signature before the item is inserted; free space is re-checked every 4 MiB while streaming; a failed pending-item record discards the item (`WriteFailed`). A `Connection` failure without a validated network pauses the batch (`Result.retry()`, queue kept, no interruption counted); a changed account fingerprint is `ConfigurationChanged`.
- **User cancel vs. system stop**: only `isStopped && stopReason == STOP_REASON_CANCELLED_BY_APP` (the notification's WorkManager cancel intent) is the user's: pending item discarded, queue deleted, "Saving cancelled" with "N of M photos saved before cancelling". Every other stop keeps the queue and its markers and re-runs only the remaining entries; a network error while `isStopped` is a stop, not a failure.
- **Notifications**: channel `download_channel` (Downloads, low importance), glyph `ic_notification_download`, progress id 1004 (determinate, Cancel action), result id 1005 tagged with the queue file name (counts as plurals plus one typed sentence per distinct reason joined via `joinNotificationTexts()`, gated on `POST_NOTIFICATIONS`); upload ids 1001 / 1002 are untouched, so an upload and a download never replace each other.
- **Uploads and removal are unaffected**: the download worker does not take `UploadedPhotosStore` or `VerifiedUploadsStore`. Saved photos are new local items without a cloud badge, visible under "show only new photos", uploadable like any photo, and never removal candidates (a record needs the MediaStore id, `SIZE` and `DATE_MODIFIED` of a verified upload).
- **Tests**: `DownloadTargetTest`, `DownloadNamesTest`, `DownloadFailureTest`, `WebDavClientDownloadTest`, `NoBufferedDownloadRegressionTest`, `LocalMediaWriterTest`, `DownloadOwnItemsOnlyRegressionTest`, `DownloadQueueTest`, `DownloadWorkerRunTest`, `DownloadWorkerCancelTest`, `DownloadWorkerCancelWorkManagerTest`, `ImageSignatureTest`, `DownloadWorkerNotificationTest` (also covers the string resources), `DownloadEnqueuerTest`, `AlbumDetailViewModelSaveTest`, `AlbumDetailSaveTest`, `FullscreenViewerSaveTest`, `RemovalCandidateCheckerTest`. Shared set-up: `DownloadHarness`, `FakeMediaStoreProvider` (insert / update / delete / `openFile` with failure injection), `FakeDownloadRequester`.

## Upload verification and removal of uploaded photos

Spec: `openspec/changes/delete-after-verified-upload` (`upload-verification`, `remove-uploaded-photos`).

**Spike result (API 35 emulator).** A background worker cannot move other apps' photos to the system trash, not even with `MANAGE_MEDIA`: `MediaStore.createTrashRequest()` returns a `PendingIntent` whose MediaProvider activity (`PermissionActivity`) starts (it is allowlisted, so this is not a background-launch block) but finishes at once with "Missing calling package", because the calling package only exists for `startIntentSenderForResult` from an Activity; a direct `update(IS_TRASHED = 1)` throws `RecoverableSecurityException`. Removal therefore is a manual action in a visible Activity, decided per photo, with no `MANAGE_MEDIA` (without it the system shows its own confirmation, once per request).

**Verification (`data/UploadVerifier.kt`, `UploadWorker`).**
- **Originals only (review finding).** Without `ACCESS_MEDIA_LOCATION` the MediaProvider redacts the location of another app's photo (EXIF GPS, ISO-BMFF location boxes: zeroed bytes, same size), so a redacted copy verifies byte for byte. The worker validates the uri (`isAllowedPhotoUri`) before any MediaStore query, then opens a verifiable entry through `Context.openForUpload(uri, wantOriginal)` (`worker/UploadSource.kt`): with the permission (`hasMediaLocationAccess()`, read once per run) it opens `MediaStore.setRequireOriginal(uri)` and gets `UploadSource.Original`; without it, or when that open throws `UnsupportedOperationException` / `SecurityException` / `FileNotFoundException` / `IllegalArgumentException`, it opens the plain uri as `UploadSource.Plain` (upload still happens, no `X-Hash`, never verified). Only `verifyUpload(…, original: UploadSource.Original, …)` builds a `VerifiedUpload` (guarded by `VerifiedRecordOnlyFromOriginalRegressionTest`).
- `UploadWorker.uploadPhoto()` wraps an original's stream in `DigestCountingInputStream` (`util/`, SHA-256 + byte count of exactly the sent bytes, applied *after* `uploadLengthOf()` so the staged length is still read from the file) and reads `SIZE` / `DATE_MODIFIED` through `ContentResolver.mediaFileStateOf()` just before opening it. Staged (shared) and `id = -1` entries are never wrapped, hashed, verified or recorded.
- `verifierFor(config, downloadEnabled, client)`: a URL containing `/remote.php/` -> `NextcloudHashVerifier` (the `PUT` carries `X-Hash: sha256`, `WebDavClient.uploadFile(requestServerHash = true)` returns `UploadResponse.serverSha256` only if it is 64 hex chars; compared case-insensitively; a missing / malformed header delegates to the `DownloadVerifier` fallback when "Verify by downloading again" is on, else `Unavailable`); any other server -> `DownloadVerifier` when the setting is on, else `NoVerifier`. The setting (`CredentialStore.verifyByDownload`, plain edit without a `credentials_version` bump) is read once per run with `readVerifyByDownload()` (3 s timeout, fallback off).
- `DownloadVerifier` uses `WebDavClient.downloadSha256(folder, file, maxBytes = sent bytes)`: `GET` on `uploadClient` (no redirects, `Accept-Encoding: identity`, no call timeout), body through `LimitedInputStream`; a larger `Content-Length` or body is `RemoteFileTooLargeException` (-> `Mismatch`, never confused with an `IOException`, which is `Inconclusive`).
- Outcomes (`verifyUpload()`): `Verified` -> uploaded + `VerifiedUploadsStore.recordVerified`; `Unavailable` (no strategy, MediaStore metadata missing, or `SIZE` != sent bytes: the copy on the server is good but the local file is not provably the same, so no download is spent) -> uploaded, older record forgotten; `Mismatch` / `Inconclusive` -> failed with `UploadFailure.Verification` (reason `upload_failure_verification` in the result notification), not marked uploaded, retried like any failure, older record forgotten. The record is written after `markUploaded`; a failed write only means "not removable".
- **Path and account binding.** Records are bound to `UploadTarget(serverUrl, folder, fileName)` (`isAt()`, folder and name case-insensitive). Every `PUT` attempt (also staged and failed ones) calls `VerifiedUploadsRepositoryContract.applyUpload(target, …)` twice: before the `PUT` (drops every record at the target, so a run that dies mid-`PUT` leaves none) and after it in one edit with the photo's own update (drops records of other ids at the target, stores the verified record or forgets the id). Before recording, the worker re-reads the config (`isStillConfiguredAs`, 3 s) and records nothing if the URL or username changed or the config is invalid. `SettingsViewModel` clears the store before saving credentials with another URL or username (or when the previous config is unreadable) and, on logout, clears it first; each clear runs in its own `runCatching` (rethrowing `CancellationException`). The store's `records` are parsed with `flowOn(parseDispatcher)` (default `Dispatchers.Default`).
- `VerifiedUploadsStore`: string set `records` in DataStore `verified_uploads` (`VERIFIED_UPLOADS_DATASTORE_NAME`), one JSON object per photo (`id`, `uri`, `size`, `dateModified`, `serverUrl`, `folder` = the exact remote folder string of the `PUT`, `fileName`, `verifiedAt`; no credentials), strict parse (malformed elements skipped), newest `verifiedAt` per id wins, at most 20,000 records (oldest dropped), `verifiedUploadsCorruptionHandler` -> empty, excluded from backup / device transfer, `clear()` on logout.

**Removal (`UploadedRemovalViewModel`, `ui/photogrid/UploadedRemovalUi.kt`).** States `Idle` -> `Checking(done, total)` -> `Confirm(count)` / `NothingToRemove` / `NotConfigured` / `ServerUnreachable` -> `Trashing` -> one-shot `RemovalOutcome` (`Trashed(n)` / `Cancelled` / `Failed`). Every job (`start`, `confirm`) takes a new generation (`AtomicInteger`, also bumped by `cancel()`); state writes, progress callbacks and cancellation handlers of an older generation are ignored, so cancel followed at once by start keeps the new check's state.
- `DefaultRemovalCandidateChecker.check()` returns `RemovalCheck(candidates, serverUnreachable)` (parallelism 4, each `remoteFileSize()` `HEAD` under 30 s, every failure keeps the photo, cancellation propagates): same `serverUrl`, `validatedMediaUri()` (authority `media`, `<volume>/images|video/media/<rawId>`, raw id = record id with `Photo.VIDEO_ID_FLAG` set exactly for `video`), `mediaFileStateOf()` with equal `SIZE` + `DATE_MODIFIED`, server `Content-Length` = recorded size. An item-uri query returns trashed and pending rows whatever the query args say, so `mediaFileStateOf()` projects `IS_TRASHED` / `IS_PENDING` and treats 1 (or null, or any non-cancellation query failure) as missing. `REMOVAL_MAX_CONSECUTIVE_SERVER_FAILURES` (5) timeouts / I/O failures / `5xx` / `408` / `429` in a row abort the check (the remaining calls are cancelled, `serverUnreachable`, every photo kept, localized `removal_server_unreachable_*` dialog); other answers (404, other size, 3xx) reset the count.
- `confirm()` re-reads the records and the config (bounded) and keeps only candidates whose record is still stored unchanged and whose `serverUrl` is the configured one; a confirmation older than `REMOVAL_CONFIRM_MAX_AGE_MS` (10 min, monotonic `clock`) re-runs the full check (shown as `Checking`, cancellable), else only the local half (`recheckLocal`, failures -> `Failed`). It then snapshots which candidates are already in the trash (`trashedAmong`), requests only the others and subtracts the snapshot from the final count, so neither the count nor the forgotten ids include items this request did not trash, and `RESULT_CANCELED` with nothing newly trashed is `Cancelled`. It splits into requests of at most `MAX_TRASH_REQUEST_URIS` (2000) and exposes one `IntentSenderRequest` at a time (`pendingRequest`); the screen launches it with `StartIntentSenderForResult`, clears it (`onRequestLaunched`) and reports `onTrashResult(resultCode)`. `RESULT_OK` -> next chunk; anything else stops. The count is confirmed by re-querying the requested uris with `QUERY_ARG_MATCH_TRASHED` (`LocalMediaTrasher.trashedAmong`, `IS_TRASHED = 1`, one query per uri, a failing uri is "not confirmed"); only those records are forgotten (matched through a `Set<String>` on the injectable `computeDispatcher`, records read bounded); the screen reloads the grid and shows the snackbar. A process death while the system dialog is open loses the state, which is safe: trashed items fail the MediaStore check next time.
- Photos are moved to the system trash only; naming uses "remove" / "trash", never "delete", to stay apart from `album-photo-deletion`.

## TLS trust & certificate pinning (`pin-self-signed-certificate`, issue #71)

Decision record (details in the OpenSpec change `pin-self-signed-certificate`, design D1-D11):

- **D1 Trust model.** A connection is accepted if the platform trust manager (system CAs and the network security configuration) accepts the chain, or if the leaf is the one pinned certificate (SHA-256 of its DER encoding, the value `openssl x509 -fingerprint -sha256` prints) for exactly the pinned `https` origin (host + effective port, normalized through `HttpUrl`) and is currently valid. OkHttp's `CertificatePinner` cannot be used (it runs after chain validation) and is banned.
- **D2 `PinAwareTrustManager`** (`data/tls/`) is the only custom `X509ExtendedTrustManager`: it calls the same overload of the platform delegate first, consults the pin only after a `CertificateException` (peer host / port from the handshake session) and throws `CertificateChangedException` when a pin exists for the peer but the leaf differs. The non-extended overload, a missing session, a null chain or a non-extended delegate fail closed. Lint's `CustomX509TrustManager` is suppressed on this one class with the user's explicit approval (no non-custom alternative meets the requirements: a KeyStore-based trust anchor would trust the certificate for every host); `TrustAllX509TrustManager` / `BadHostnameVerifier` are never suppressed.
- **D3 `PinAwareHostnameVerifier`** accepts OkHttp's standard verification, or the pinned leaf on the pinned host and port even without a matching SAN (self-signed certificates usually have none), re-checking validity because a resumed TLS session skips the trust manager.
- **D4 One factory.** `serverHttpClientBuilder(ServerTrust)` builds every server client with a new `SSLContext` per call, so TLS sessions and pooled connections are never shared across pins. `WebDavClient(config, pin)` and `AlbumsRepository(config, pin)` take the pin without default. The Coil image loader gets a `PinnedClientHolder` (rebuilds the client and evicts the old pool when the pin changes; config and pin come from one combined state). `NoTrustAllRegressionTest` (comment-stripped, whitespace-collapsed source scan) allows trust managers, hostname verifiers, `SSLContext.getInstance`, `OkHttpClient` construction, `.sslSocketFactory(` and `.hostnameVerifier(` only in `data/tls/`, and bans trust-all patterns, `CertificatePinner`, `HttpURLConnection`, `DefaultHttpDataSource` (and the Media3 `DefaultDataSource`, `DefaultMediaSourceFactory`, `SimpleCache`, `CacheDataSource` and the one-argument `ExoPlayer.Builder`; the video stream client is a `newBuilder()` derivation, see "Videos in albums"), a Coil `OkHttpNetworkFetcherFactory()` without `callFactory`, and Network Security Configs with `src="user"` / `overridePins`; `ServerClientsPinningTest` proves every client kind accepts the pinned origin and rejects another one.
- **D5 Pin snapshots are explicit.** `TrustedCertificateRepository.pinFor(url)` returns the stored pin only for the configured origin and reads it bounded (3 s, fallback `null` = system trust only). `AlbumsRepositoryProvider.get()` re-reads config and pin and rebuilds on a change; `UploadWorker` reads the pin at run start, in `cancelAborter()` and before every queue entry (a removed pin applies from the next photo; a chunked transfer in progress finishes with its snapshot; the transfer aborters (cancel, give-up, end of run) always use the client of the pin in effect, `abortTransfers` is replaced with the client; a `CertificateException` / `SSLHandshakeException` / `SSLPeerUnverifiedException` is a final chunk failure, never retried); `DefaultRemovalCandidateChecker` reads it once per check; `SettingsViewModel` per connection test.
- **D6 Storage.** `TrustedCertificateStore` keeps one strict-JSON record in DataStore `trusted_certificates` (`TRUSTED_CERTIFICATES_DATASTORE_NAME`; origin, sha256, subject, issuer, validity, trustedAt); invalid records and I/O read errors mean no pin, `trustedCertificatesCorruptionHandler` replaces a corrupt file with an empty one (pinned by `TrustedCertificatesCorruptionHandlerRegressionTest`), the file is excluded from backup and both data-extraction sections (`BackupRulesTest`). Logout clears it (own `runCatching`), saving credentials for another origin clears it before `credentialStore.save()`.
- **D7 Capture without trusting.** `WebDavClient.testConnection()` derives a per-call client with a `CertificateCapture` for the configured origin; after a TLS failure it throws `CertificateReviewException(certificate, changed, previousSha256)`. The handshake still fails, so no request or credentials are sent; certificates of other hosts (redirects) are not captured. Subject / issuer are sanitized (control, format and bidi characters removed, 256 characters) and never logged.
- **D8 Typed results.** `ConnectionTestResult.UntrustedCertificate(certificate)` / `CertificateChanged(certificate?, previousSha256)`; classification order in `toConnectionTestResult()`: HTTP status, `CertificateReviewException`, `CertificateChangedException` in the cause chain, generic TLS, rest. `AlbumsError.CertificateChanged`, `FolderCreationError.Connection(CertificateChanged)` and `UploadFailure.CertificateChanged` (notification text via `joinNotificationTexts()`).
- **D9 Settings UX.** `CertificateReview` card (fingerprint, previous fingerprint for a changed certificate, subject, issuer, validity, origin, warning) -> confirmation dialog -> guarded one-shot `confirmTrust()` (config re-read 3 s, origin and review-currency check, write under a 5 s timeout, `ensureActive()`, re-test); a config change or logout cancels it and clears the review. "Stop trusting" is a guarded one-shot too. Review fixes: `confirm(review)` takes the review the user saw and stores only while it is still the current one (a new test clears the review at once; the dialog state is keyed on the fingerprint); keys that are not RSA >= 2048 / EC >= 256 (`ServerCertificate.hasStrongKey`, key shown on the card) cannot be trusted; the dialog of a changed certificate lists the previous and the new fingerprint; a pin that cannot be cleared at logout / server change is reported (`error_trusted_certificate_clear_failed`) and removed by the next sign-in. The album / upload certificate messages are neutral (no call to trust; the review lives in Settings > Test connection). Known limit: a slow pin read in `AlbumsRepositoryProvider` falls back to no pin and is treated as a configuration change. Follow-up: remember system-trusted origins (an origin that used to present a CA certificate is shown as a normal first review).
- **D11 Login library.** `libs/login-flow-nextcloud` keeps its own client and the system trust store; the Nextcloud login never uses or stores a pin and offers no review (self-signed servers: manual configuration + Test Connection). An injectable client in the library (design task groups 1 and 7) is a possible follow-up once the library changes.

## Share Target Flow

When another app (Gallery, Screenshot, etc.) shares images via the Android share sheet:

1. `MainActivity` is launched with `ACTION_SEND` or `ACTION_SEND_MULTIPLE` (`isShareIntent`); it never composes `KrhnlesApp` then. It gets `ShareViewModel` from the default factory (public `(Application)` constructor, `ViewModelFactoryRegressionTest`) and calls `start(intent)`, which only acts once per ViewModel, so rotation neither loses nor repeats anything. The UI is `ShareRoute` → stateless `ShareReceiverScreen(state, …)`.
2. `parseSharedPhotos(intent, ownPackage)` is a pure extraction of `EXTRA_STREAM` into `SharedItems(uris, truncated, rejected)`: hostile extras (any `RuntimeException` while reading them, e.g. `BadParcelableException` / `ClassCastException`, and wrong element types) are ignored (exception type logged only), then `isAllowedPhotoUri`, de-duplication and the 100-photo cap (`MAX_SHARED_PHOTOS`). Nothing usable → `ShareFinish(NoPhotos)`: Toast `share_no_photos` and `finish()`, the app is not launched.
3. The configuration is read once (`webDavConfig.first()` under a 3 s `withTimeoutOrNull`; timeout / failure counts as configured, the worker reports a missing server). Not configured → `NotConfigured` dialog; "Open app" starts `MainActivity` with `FLAG_ACTIVITY_NEW_TASK` (the share activity runs in the sender's task), nothing is copied.
4. `resolveSharedPhotos()` runs each item's `getType` + `query(…, CancellationSignal)` as an `abandonableCall` on the work dispatcher (never Main) with a 10 s per-item timeout; an item that times out is dropped. Types are allow-listed (`SharedImageType`: JPEG, PNG, GIF, WebP, HEIC, HEIF, AVIF, BMP, DNG; aliases such as `image/jpg` / `image/x-ms-bmp` normalized; SVG and every other type rejected). A concrete provider type decides alone; if the provider reports none, `application/octet-stream` or a wildcard, the `DISPLAY_NAME` extension decides via `MimeTypeMap` (a known non-image extension drops the item), and only without a known extension a concrete intent type is used (`image/*` never). Provider calls catch `SecurityException`, `IllegalArgumentException`, `IllegalStateException`, `OperationCanceledException`. The provider name is the remote file name only if it is one valid name (`isValidRemoteFileName`: valid path segment, ≤ 255 bytes, no Unicode Cf / bidi controls, line / paragraph separators or unpaired surrogates) and unique in the share (case-insensitive); a name not ending with one of the validated type's extensions gets it appended (`evil.svg` as PNG → `evil.svg.png`); else `shared_<millis>_<8 hex>.<ext>`. Shared photos have `id = -1` (never marked as uploaded) and today's date. The occasion dialog shows the count plus skipped / not-included notices (`ShareUiState.Ready`) and occasion suggestions (loaded when `Ready` appears); auto date folders never apply. While the share is read, `Preparing` shows an indeterminate progress with Cancel.
5. On confirm (`ShareViewModel.confirm`, phase CAS latch) the photos are copied with `ShareStaging.stage()` into `noBackupFilesDir/share_staging/<uuid>` while the grant is still valid ("Preparing x of n" + Cancel; Back cancels too). Bounds: 100 MiB per file (provider `SIZE` pre-skip and counted bytes), 1 GiB per share (exceeding item skipped), staging folder ≤ 2 GiB incl. existing files and free space (`getAllocatableBytes`, else `usableSpace`) minus a 200 MiB margin (exceeding → share fails). Each item is opened with `openAssetFileDescriptor(uri, "r", CancellationSignal)` and copied inside one `abandonableCall` (per-item timeout 2 min → skipped as unreadable): the blocking open + copy run detached on IO, so cancellation or the timeout cancels the signal (aborting the provider's open, and closing the source stream so a blocked read returns) and returns at once even if the provider ignores the signal; an abandoned call deletes its own (also complete) file whenever it returns, and a returned `Staged` name is recorded by the ViewModel without a suspension point, so no staged file is ever orphaned. Skips carry a `SkipReason`: unreadable / too large (`ShareFinish.skipped`, `share_copy_skipped`) and over the per-share cap (`ShareFinish.overShareLimit`, `share_over_share_limit`); `shareFinishMessage()` builds the toast. A write / space failure stops the share with one `share_copy_failed`; if every item was skipped the share ends with `ShareError.NothingCopied` (`share_nothing_copied`), not the storage message. Cancel and Back publish `Cancelled` immediately (no join of a job blocked in a provider); Cancel, Back, a failure and `onCleared()` delete the batch's staged and partial files in the copy job's `finally`; nothing is enqueued.
6. After the copy the ViewModel enqueues one `UploadBatch.Occasion` (photos carry `stagedName`) through `UploadEnqueuer` (application scope) and emits the one-shot finish; an enqueue failure — any exception except cancellation, `UploadEnqueuer` never lets one escape the application scope — deletes the staged copies and shows `share_enqueue_failed`. The queue entry has `staged` and no id; the worker reads only the staged file (missing → failed photo, never the URI) and never touches `contentResolver` for it.
7. **Cleanup**: no deletion per successful photo (the staged copies stay until the queue is final; a re-run skips entries marked `uploaded`). `deleteQueueFile(context, queueFile, keep)` (also removes a leftover `<queue>.tmp`) is used at every queue deletion (malformed queue — staged names read leniently —, not configured, end of the run) and deletes the staged files except those referenced by the new retry file. `ShareStaging.sweep()` runs on IO when a share starts: staged files older than 7 days not referenced by an `upload_queue_*` file are deleted; one referenced by retry files is deleted together with those retry files only if every such retry file is itself older than 7 days (its own modification time — `handleRetry` refreshes it on every tap, so the window restarts) and has no unfinished retry work (`hasUnfinishedRetryWork`: `getWorkInfosForUniqueWork(retryWorkName)` bounded to 5 s; unknown keeps the files). It fails closed: an unreadable / malformed queue file or a changed queue-file list (listed twice) deletes nothing. A process death during a copy leaves only that share's partial files, removed by the sweep.
8. On dismiss → `finish()` returns without uploading or copying
   - **Security notes (accepted)**: *Confused deputy* — `MainActivity` is exported and reads every shared `content://` URI with the app's own identity, so a malicious sender could share a URI that only this app can read (e.g. a MediaStore image when the user granted the app media access). The only effect is that the photo goes to the user's own configured server, after the user saw the photo count and explicitly confirmed an occasion; the app's own authorities and `file://` are rejected (`isAllowedPhotoUri`), and nothing is sent anywhere else. *Per-process budget* — the share (1 GiB) and folder (2 GiB, counted from the files present when the share's copy starts) budgets are not shared between concurrent shares in separate `MainActivity` tasks, so two simultaneous shares can together exceed the folder cap by up to one share; the free-space margin still applies per share (accepted). *Overwrite* — a shared photo is uploaded with a plain `PUT`, so a file with the same name already in the occasion folder is overwritten (known behaviour, also for gallery uploads); names are only de-duplicated within one share. *Abandoned calls* — a provider that ignores its `CancellationSignal` keeps one IO thread until it returns; the share itself is never blocked.
   - **Tests**: `ShareIntentParserTest` / `ShareStagingTest` / `ShareViewModelTest` use `FakeShareProvider` (`Robolectric.setupContentProvider`; content is served through `openTypedAssetFile(…, CancellationSignal)`, which `openAssetFileDescriptor(uri, "r", signal)` reaches; `ProviderGate` blocks an open / query until released or — if it honours cancellation — until the signal is cancelled, or ignores the signal to model a stuck provider); stream-level cases (endless / blocking reads) inject a `SharedSourceOpener`. `ShareTestHarness` builds the ViewModel with fakes, a real IO work dispatcher and gated items for in-flight copies, and polls while idling the main looper (a `withTimeoutOrNull` on Main needs `idleFor`). `ShareReceiverScreenTest` covers the dialog, the single enqueue, Cancel and `ActivityScenario.recreate()` during a gated copy; `MainActivityShareTest` the no-photo Toast + `finish()`; `UploadWorkerRunTest` staged uploads, a stopped-and-rerun worker, retry from staging and invalid staged entries.
9. **History**: Upload outcomes are persisted via `UploadHistoryStore` and shown on the Upload History screen
10. **Uploaded Badge**: `PhotoGridViewModel` observes `UploadedPhotosStore.uploadedPhotoIds` and includes them in `PhotoGridUiState`; the grid shows a cloud badge on already-uploaded thumbnails (user can still select and re-upload them for a different album)
11. **Filter Toggle**: A funnel icon in the top bar (visible when any photos have been uploaded) lets the user hide already-uploaded photos; `PhotoGridViewModel.toggleShowOnlyNewPhotos()` recomputes `photosByDate` from the full unfiltered list. Opening the app from the new-photos reminder calls `showOnlyNewPhotos()` instead: it only ever turns the filter on (idempotent) and deselects the items it hides

## Upload Path Construction

Given:
- WebDAV base URL: `https://nextcloud.example.com/remote.php/dav/files/user/`
- Base folder: `Photos/KrohnSync`
- Occasion: `Summer 2026`
- File: `photo.jpg`

Result: `https://nextcloud.example.com/remote.php/dav/files/user/Photos/KrohnSync/Summer 2026/photo.jpg`

### Auto date folders (issues #18 / #37)

When auto date folders are enabled (Settings switch, plain preference `auto_date_folders`, default off, reset by logout, not backed up), the photo grid skips the occasion dialog and shows a preview of the target paths (one per distinct day folder; the path list scrolls within a bounded height, the buttons stay visible). Confirming queues **one** upload for the whole selection (user decision, deliberately not one work per month or day as the issue text suggested):

- **Day folders:** each photo goes into `<base>/YYYY/MM/DD/` (`dayFolderName()`: `String.format(Locale.ROOT, "%04d/%02d/%02d", …)`, ASCII digits only, no month names, no default-locale dependency). The capture day is `Photo.dateTaken`, i.e. `DATE_TAKEN` converted once by `MediaRepository.dateTakenOf(millis, zone = ZoneId.systemDefault())` when the photo list loads, the same date as the grid's date header. Unknown dates (`Photo.UNKNOWN_DATE`) go into `1970/01/01`; pre-1970 dates keep their date.
- **Travel limitation (accepted):** the day is the device zone at load time, not the zone where the photo was taken (no EXIF offset); reloading after a zone change can move a not-yet-uploaded photo to another day.
- **One work per selection:** `resolveAutoDateUploadBatch(photos)` returns one `UploadBatch.PerPhoto(photos, folders, label)` (photos sorted by day, then id; `folders` same size / order, non-blank, enforced with `require`). Occasion mode and the share target use `UploadBatch.Occasion(folderName, photos)` unchanged; the share target never uses auto date mode. One work means one foreground / progress notification, one result notification (tag = queue file name), at most one retry action and one history entry.
- **History label:** the single day folder (`2026/05/14`) or `"<first> – <last>"` (`2026/04/30 – 2026/05/01`), stored in `UploadHistoryEntry.occasionName` (no model change), capped at 200 characters when recorded, never used as a path.
- **Queue format (backward compatible, no version field):** occasion / old queues are written and read exactly as before (`{"folderName": "Trip", "photos": [...]}`). Per-photo queues have `label`, a `folderName` on every entry and **no** top-level `folderName`. A file is per-photo if it has a `label` (any type) or any entry has a `folderName` key; then every entry needs a non-blank string folder and a top-level `folderName` makes it malformed (as do mixed files, missing entry folders and non-string folders: work fails, file deleted, nothing uploaded). A non-string `label` is dropped (history label `""`). History label = `label` ?: top-level `folderName` ?: `""`. Queue and retry files persisted before this change (single `folderName`, including old `YYYY/MM-Mon` folders) behave as before. Downgrade is not supported: older versions fail and delete per-photo queues.
- **Validation and folder creation:** every effective folder is validated before any request (top-level: blank = base folder, otherwise `isValidFolderPath`; entry folders: `isValidFolderPath`); any invalid folder fails the whole work with `FolderCreationError.InvalidFolderName`. Then `WebDavClient.createDirectories(paths)` MKCOLs every distinct folder level by level below the configured URL, each cumulative path at most once per run (405 = exists). Any MKCOL failure fails the whole work before the first PUT (failure notification, history all failed, no retry file). Each photo is then PUT into its own folder; progress counts all photos of the work.
- **Progress banner:** `PhotoGridViewModel.uploadProgress` still shows the first running work. With one work per selection it covers the whole selection; concurrently running works (two selections back to back, share target + grid) are not aggregated (unchanged).
- **Existing remote folders:** old `YYYY/MM-Mon` folders are neither migrated nor merged; they coexist with the new day folders. The Albums tab lists the base folder with `Depth: 1`, so year folders appear as albums (unchanged).

`WebDavClient.createDirectory()` walks each segment in order (MKCOL per segment, 405=already exists is OK), so nested paths are created safely regardless of what already exists on the server.
All path segments are validated (`.` / `..` rejected) and URL-encoded via `HttpUrl` segment builders to prevent path traversal and malformed path injection.

## Key Decisions

- **Album video playback: Media3 over the album client (issue #74)** — options evaluated: (a) in-app Media3 ExoPlayer over `OkHttpDataSource`, (b) no playback (save to device / open in Nextcloud), (c) platform `MediaPlayer` / `VideoView` with a header map. (c) was rejected (the platform HTTP stack follows redirects with the headers, cannot be origin-restricted and ignores the app's pinned trust); (b) copies the whole file into shared storage or needs the Nextcloud app and a public link and does nothing for plain WebDAV; (a) is the only option that keeps the app's network rules (origin-restricted credentials, no redirects, pinned trust, no copy on disk) and costs two Media3 artifacts (`media3-exoplayer`, `media3-datasource-okhttp`, one version ref). The sibling change `download-album-photos` complements it with "save to device". Reviews stay photo-only; remote durations / sizes are not shown (no extra PROPFIND properties).
- **Album search & sort (issue #77)** — folding is lowercase → uppercase → lowercase (`Locale.ROOT`) → NFD → strip `\p{Mn}` (so `ß` / `ẞ` match `ss`, accents are ignored; letters like `ł` / `ø` are not folded, a documented limit); ordering is total and deterministic (key → exact name → href), undated albums are a partition so they sort last in both directions. Names longer than 255 chars are folded by their first 255 chars only (NFD of long combining-mark runs is quadratic-ish and the names are server-supplied); `listAlbums()` drops repeated hrefs. The album-folder PROPFIND has its own body with `d:getlastmodified` so the bounded photo listing is unchanged. The sort is a plain credentials-DataStore preference (reset on logout like the other plain preferences). Nested folder navigation (`2026 → 05 → 14` for auto date users) is deliberately deferred to a follow-up: it needs a detail listing that returns sub-collections, a rename / delete policy deeper than one level (`albumRelativeSegments()` requires exactly one), several `albums/detail` entries sharing the route pattern that `sharedAlbumDetailViewModel()` resolves, and review semantics for folders; it also overlaps the photo-listing changes of other work.
- **WorkManager** for uploads ensures they survive app closure
- **Share target** declared for `image/*` (`ACTION_SEND` + `ACTION_SEND_MULTIPLE`); `ShareReceiverScreen` shows the occasion dialog immediately so the user stays in context and the source app is returned to after confirm
- **Staged share copies (issues #16 / #35)** — a share grant is revoked when the receiving activity finishes and cannot be persisted, so shared photos are copied into backup-excluded app storage before `finish()` and uploaded from there. Rejected: keeping the activity alive until the upload ends (breaks background uploads), copying at receipt (wasted work on cancel), `takePersistableUriPermission` (not available for share grants), a `FileProvider`
- **Android Keystore** for secure credential encryption (replaced deprecated EncryptedSharedPreferences)
- **EncryptedSharedPreferences** — removed (deprecated in security-crypto 1.1.0)
- **Nextcloud Login Flow v2** for browser-based auth (no password handling in-app)
- **Nextcloud login polling timeout** so auth does not run forever if approval never happens
- **OkHttp** directly for WebDAV (no Retrofit needed for simple PUT/MKCOL/PROPFIND)
- **Coil 3** for efficient image loading in the grid
- **LazyVerticalGrid** with `GridItemSpan` for date headers spanning full width
- **DataStore Preferences** (`trusted_certificates`) for the single pinned server certificate (see "TLS trust & certificate pinning"); excluded from backup and device transfer (`BackupRulesTest` via `TRUSTED_CERTIFICATES_DATASTORE_NAME`), corrupt file -> no pin (`trustedCertificatesCorruptionHandler`).
- **AndroidViewModel** to access Application context for ContentResolver and DataStore
- **DataStore Preferences** (`uploaded_photos`) for persisting the set of already-uploaded photo IDs across restarts; stored as `Set<String>` (Long IDs converted to strings). The file `datastore/uploaded_photos.preferences_pb` is excluded from cloud backup and device transfer (`backup_rules.xml`, `data_extraction_rules.xml`, guarded by `BackupRulesTest` via `UPLOADED_PHOTOS_DATASTORE_NAME`) because MediaStore ids are only meaningful on the device that produced them; a restored set would badge the wrong photos. A corrupted file is replaced by an empty set (`ReplaceFileCorruptionHandler`). `UploadedPhotosStore` has an internal `DataStore` constructor for `UploadedPhotosStoreTest`
- **DataStore Preferences** (`upload_history`) for the local upload log (JSON array under `upload_history_entries`). The file `datastore/upload_history.preferences_pb` is excluded from cloud backup and device transfer (`backup_rules.xml`, `data_extraction_rules.xml`, guarded by `BackupRulesTest` via `UPLOAD_HISTORY_DATASTORE_NAME`) because folder names are user-written and may be sensitive. A corrupt file is replaced by an empty history (`uploadHistoryCorruptionHandler`, pinned by `UploadHistoryCorruptionHandlerRegressionTest`). Retention: at most 500 newest entries, applied in `addEntry` inside the same `edit` (an oversized stored history is trimmed on the next add). Ids: `addEntry` makes a colliding id unique (`maxOf(entry.id, maxExisting + 1)`; the worker passes `now`), and `decodeEntries` keeps the newest entry per id (sort by timestamp desc, then `distinctBy`; only the dropped count is logged, the duplicate disappears on the next write) so persisted duplicates neither crash `LazyColumn` nor make `removeEntry` remove two. The history is a user-facing local log and is deliberately not cleared on logout (the user has Clear all). Because it survives logout, on a shared or handed-over device folder names stay visible until "Clear all". Labels are bounded: per-photo labels to 200 characters, the single-folder fallback to 1000 (`MAX_HISTORY_LABEL_LENGTH` / `MAX_FOLDER_HISTORY_LABEL_LENGTH`). `UploadHistoryStore` has an internal `DataStore` constructor for `UploadHistoryStoreTest`; the delegate is private.
- **Settings connection test is one-shot** — `SettingsViewModel.testConnection()` reads the config once with `webDavConfig.first()` (never `collect` + `return@collect`, which leaks the collector; issue #22 / #41), drops calls while the previous test's `Job` is still active, and reports a typed `ConnectionTestResult` that `SettingsScreen` maps to localized `R.string.connection_test_*` messages (raw exception text is never shown). The server check is injected as `connectionTester` (default `WebDavClient.testConnection`) so tests run without a network. `NoCollectEarlyReturnRegressionTest` scans `app/src/main` for the early-return idiom (literal `return@collect` only — custom labels, `collectLatest` and multi-line forms are not detected)
- **Connection test guard is always released** — `WebDavClient.testConnection(timeoutMillis = 30 s)` sets a per-call OkHttp call timeout (the shared client used for uploads keeps no overall limit, so large uploads are not cut off) and runs via `enqueue` inside `suspendCancellableCoroutine`, so cancelling the coroutine cancels the HTTP call; cancellation is rethrown, never wrapped in the `Result`. Non-2xx statuses fail with the typed `WebDavHttpException(code)`. In the ViewModel every failure (including a DataStore `IOException` from `webDavConfig.first()` or a throwing tester) becomes a result, so `isTesting` is always cleared. `logout()` and any change of URL/username/password (observed in the `init` config collector) cancel the running test, null the `Job` and clear `testResult`; the job calls `ensureActive()` before publishing, so a cancelled test never writes a stale result into a new session
- **Connection-test error mapping** — `Throwable.toConnectionTestResult()`: `WebDavHttpException` 401/403 → `AuthFailed`, 404 → `NotFound`, other → `HttpError(code)`; any `SSLException` / `GeneralSecurityException` in the cause chain (`SSLHandshakeException`, `SSLPeerUnverifiedException`, `CertPathValidatorException`, `CertificateException`) → `CertificateError` (before it: a `CertificateReviewException` → `UntrustedCertificate` / `CertificateChanged` with the captured certificate, a bare `CertificateChangedException` → `CertificateChanged(null)`); `UnknownHostException` → `UnknownHost`; `ConnectException` / `NoRouteToHostException` → `ServerUnreachable`; `InterruptedIOException` (socket or call timeout) → `Timeout`; `IllegalArgumentException` (bad URL) → `InvalidUrl`; everything else → `UnknownError`. Only the exception class name is logged
- **One photo-deletion path** — the three album deletion entry points (`DuplicatesViewModel.deletePhotos(toDelete, launcher)` for the duplicate review, `BlurViewModel.deleteBlurryPhotos(toDelete, launcher)` for the blur review, `AlbumDetailViewModel.deleteSelectedPhotos()` for selection mode) only supply their busy-state transitions (`DuplicatesState.Deleting`/`Idle`, `BlurState.Deleting`/`Idle`, `isDeletingPhotos`) to `AlbumDetailViewModel.launchPhotoDeletion()` (the `PhotoDeletionLauncher` interface; the review screens pass the detail ViewModel as launcher), which runs the deletion in the detail ViewModel's scope and calls the ViewModel-independent `AlbumsRepositoryContract.deletePhotosIndividually()` (`data/PhotoDeletionResult.kt`; sequential, one `DELETE` per photo, a failed `Result` or a thrown exception counts as one failure and does not stop the rest; cancellation is rethrown and `ensureActive()` stops the loop before the next photo). The launcher only deletes photos that are part of the currently loaded album (`detailState.photos`); others — e.g. review results that survived a server / account change — are not deleted and count as failed. `onFinish` runs exactly once, also when the job is cancelled before its body was dispatched (`invokeOnCompletion`), and the re-entry guard stays set until the job completed. Only hrefs that were actually deleted are removed from `AlbumDetailState` — photos whose deletion failed stay visible. Any other non-cancellation failure (e.g. repository creation with an invalid URL) is mapped via `runCatching` + rethrow `CancellationException` to `PhotoDeletionResult.allFailed()` instead of crashing. The busy state is reset in `finally` (review paths via `compareAndSet(Deleting, Idle)`, so a scan started meanwhile is never overwritten). New deletion entry points must reuse `deletePhotosIndividually()` / `PhotoDeletionLauncher.launchPhotoDeletion()` (issues #28 / #47, #29 / #48)
- **Photo-deletion outcome is state, not a callback** — the delete functions take no `onComplete`; they return `false` (and do nothing) while `photoDeletionJob` is still active (re-entry guard for all entry points; released when the job ends, every request bounded by the OkHttp connect/read timeouts). When a deletion finishes, `photoDeletionOutcome: StateFlow<PhotoDeletionOutcome?>` is set (after the busy state was cleared); `AlbumDetailScreen` collects it (`filterNotNull().collect` in `LaunchedEffect(viewModel)`, so consuming it does not cancel the snackbar), calls `consumePhotoDeletionOutcome()` first (shown once), clears the selection and shows `R.plurals.snackbar_delete_failures` via `photoDeletionFailureMessage()`. The duplicate / blur review remember (`rememberSaveable`) that they started a deletion and navigate back once their state leaves `Deleting`; `BackHandler` and the disabled top-bar back button keep the user on the review while deleting. The album detail screen does the same for selection-mode deletions (`BackHandler(enabled = isDeletingPhotos)`, back arrow, clear-selection X and delete action disabled), because the deletion runs in the detail entry's ViewModel and would be cancelled if that entry were popped. This replaced snackbars launched in the review's `rememberCoroutineScope`, which were cancelled by the immediate navigation, and callbacks that could fire into a screen the user had already left
- **Already-deleted photos** — `AlbumsRepository.deletePhoto()` treats `404` / `410` as success (deleted elsewhere); other non-2xx statuses fail with `WebDavHttpException(code)`. `deleteAlbum()` still fails on `404`
- **Server hrefs are validated** — `resolveWebDavHref(root, href)` (`data/WebDavHref.kt`) checks the *raw* href first (percent-decoded pieces must not be `.` / `..` or contain `/`, `\` or control characters; no `?`, `#`, `\`), because `HttpUrl.resolve()` silently normalizes dot segments away; then resolves it with `root.resolve(href)` and requires the same scheme/host/port and a path strictly below `root`. `AlbumsRepository` uses `baseFolderUrl` (config URL + base folder) as root for album/photo hrefs (`deletePhoto`, `deleteAlbum`, `renameAlbum`, `listPhotos(albumHref)`, direct image URLs) and the album URL for the photos of a listing. Listings skip unsafe entries (only the count is logged); requests for an unsafe href fail with `UnsafeHrefException` without being sent; image URLs fall back to `""`. `downloadBitmapForHash(url)` (scan thumbnails) only requests a URL strictly below `baseFolderUrl` or the Memories preview `<nextcloudBase>/index.php/apps/memories/api/image/preview/<alphanumeric id>` on the configured origin; anything else fails with `UnsafeHrefException` before a request. PROPFIND and thumbnail failures carry `WebDavHttpException(code)`. The href itself is never logged. `PropfindEntryReader` only keeps an `oc:fileid` matching `[A-Za-z0-9]+` (it ends up in the Memories preview URL; anything else is dropped, so the photo falls back to its WebDAV URL), and `checkMemories()` logs the exception type only. Absolute, percent-encoded Nextcloud paths and absolute same-origin URLs are accepted
- **Streamed, bounded album listings (issues #27 / #46)** — PROPFIND responses are never buffered (`body.string()`) or DOM-parsed. `AlbumsRepository.executePropfind()` passes the decompressed `response.body.byteStream()`, wrapped in `LimitedInputStream` (`MAX_PROPFIND_RESPONSE_BYTES` = 32 MiB; the first read past the cap throws `PropfindResponseTooLargeException`), to `PropfindEntryReader` (`data/WebDavXmlParser.kt`, `android.util.Xml.newPullParser()`), which yields one `d:response` at a time. Per entry at most 256 elements, 16 nesting levels and 8 KiB per captured text value (`PropfindEntryLimits`); an oversized entry is skipped (only the count is logged, never the href). `listPhotos(albumHref, onProgress)` returns `Result<PhotoListing(photos, isTruncated)>`: it drops the collection entry, keeps photos and videos (`classifyRemoteMedia()`) strictly below the album, drops duplicate hrefs (`HashSet`) and stops at `MAX_PHOTOS_PER_ALBUM` (20,000 items, photos and videos together) or the byte cap — then the complete entries read so far are returned with `isTruncated = true` (no complete entry besides the album collection → `MalformedMultistatusException`; a truncated listing without photos or videos shows `album_truncated_empty_notice` instead of the empty-album message). `LimitedInputStream.available()` never reports bytes beyond the cap, so the decoder's read-ahead stops at the cap. `onProgress` gets the running count every 100 photos plus once at the end (on the IO thread). `listAlbums()` uses the same reader with the byte cap only and fails with `AlbumsError.ListingTooLarge` instead of silently missing albums. The Memories check runs concurrently with the PROPFIND. `AlbumDetailViewModel` shows the count (`loadedCount`, "Loading photos… N", polite live region) while loading and publishes photos, thumbnail URLs (resolved on the injectable `backgroundDispatcher`, `Dispatchers.Default`, not Main; `listAlbums()` post-processes on IO), `isTruncated` and `isLoaded` once, after `ensureActive()` and a load-generation check — a failure is published only under the same two checks, so the failure of a cancelled read never overwrites `NotConfigured` / `ConfigurationChanged` or a newer load; deletion and review semantics are unchanged (they only see complete or truncated-complete listings); progress callbacks of a replaced / cancelled load are ignored via a load generation; `reload()` is ignored while a load runs, so Retry from a review never starts a second listing. A truncated album shows a notice on the album screen and on the duplicate / blur review (results may be incomplete). Rejected alternatives: Nextcloud `SEARCH` (DASL) paging (Nextcloud-only, still needs the PROPFIND fallback, server still enumerates) and progressive chunk publishing (needed a deletion gate, a Flow contract and growing-list handling for little benefit once memory is bounded). Accepted risk: a server trickling bytes just under the 60 s read timeout can keep a listing open; no `callTimeout` is added (it would break large uploads on the shared client) — the byte cap bounds the data and leaving the screen cancels the call.
- **Thumbnail URL resolution and decoding (issues #25 / #44)** — `thumbnailUrl()` sends at most one request per `AlbumsRepository` instance (the Memories `describe` check, none on non-Nextcloud URLs); `buildUrl()` is string work, so resolving N photos costs no per-photo round-trip (`ThumbnailUrlResolutionTest`, `runBlocking` with real time; timeouts are the internal constructor parameters `memoriesCheckTimeoutMs` / `memoriesRetryBackoffMs`). The check lives in `data/MemoriesAvailability.kt` (unit-tested with a fake check and fake clock in `MemoriesAvailabilityTest`): at most one request per repository instance once a definite answer is known (200 -> available, other status -> unavailable); an inconclusive check (timeout, I/O failure, HTTP 429 / 5xx, any non-cancellation failure) is not cached and is retried at most once per backoff period (30 s, doubling per consecutive failure, capped at 10 min). Only the first attempt is awaited by callers (`listPhotos` runs it concurrently with the PROPFIND); retries run fire-and-forget in the repository's own scope, bounded by the check timeout, so a hanging endpoint never delays a listing or `thumbnailUrl()` again. Cancellation is never cached. `MemoriesAvailability.close()` (via `AlbumsRepositoryContract.close()`, called by `AlbumsRepositoryProvider` whenever it replaces, invalidates or is closed from the ViewModel's `onCleared()`) cancels an in-flight retry and its HTTP call and blocks new ones, so a dropped repository never sends a request with outdated credentials. The lock is acquired with its own timeout (separate from the check timeout). `buildUrl()` uses the Memories preview only for ASCII-alphanumeric file ids (`FILE_ID_REGEX`) and `isMemoriesPreviewUrl` accepts ASCII alphanumerics only. `downloadBitmapForHash()` decodes with `inJustDecodeBounds` + a power-of-two `inSampleSize` (`decodeDownsampled`) so the longest side stays in 512..1023 px, the analysis size of dHash and `BlurDetector` (`MAX_ANALYSIS_SIZE` = 512); smaller images are not scaled and images announcing more than `MAX_THUMBNAIL_PIXELS` (100 MP) are rejected after the bounds pass with `ThumbnailTooLargeException` (the scan skips them). Intended behaviour change: on the WebDAV-fallback path blur scores are now computed from the subsampled original, so they differ from full-size decoding (a sharp textured image stays above the default threshold). Parallel scan downloads were considered and deferred (unmeasured; memory bound and ordering invariants unresolved) — reconsider only with a measurement.
- **Blocked reads are cancellable** — coroutine cancellation does not interrupt a blocking socket read, and `Job.invokeOnCompletion` does not fire while the body is still blocked. `executeCancellable(call)` (`data/CancellableCall.kt`, shared by `AlbumsRepository` and `WebDavClient.uploadFile`) runs `call.execute()` inside `withContext(Dispatchers.IO)` next to a sibling `launch(start = UNDISPATCHED) { try { awaitCancellation() } finally { call.cancel() } }`; on cancellation the read fails at once and any non-cancellation exception (the `IOException`, or a parser exception wrapping it) is turned back into the scope's `CancellationException` (`ensureActive()`), never an error. Used by the PROPFIND, the Memories check and `downloadBitmapForHash()` (whose body is capped at `MAX_THUMBNAIL_BYTES` = 32 MiB → `ThumbnailTooLargeException`); covered by MockWebServer tests stalled before the first body byte and mid-body with a hard limit of a few seconds, and by read-timeout tests (→ `AlbumsError.Timeout`).
- **XXE defense for a stream** — a stream cannot be pre-sanitized with a regex. `PropfindEntryReader` sets `FEATURE_PROCESS_DOCDECL` to false, reads the prolog with `nextToken()` up to the root `START_TAG` and fails with `MalformedMultistatusException` on any `DOCDECL` (also a benign DOCTYPE) or `ENTITY_REF`, requires the root `{DAV:}multistatus`, and then only uses `next()`: KXml rejects a DOCTYPE after the root start tag (tested also inside `d:response`), so no entity can ever be declared, and undeclared entity references are rejected by the parser. The parser is created lazily inside `next()`'s try because KXml already reads in `setInput()`: an `XmlPullParserException` wrapping a stream `IOException` (in `detail`) is unwrapped and rethrown unchanged (timeout → `AlbumsError.Timeout`, cancellation → `CancellationException`), anything else — including an unsupported declared encoding — becomes `MalformedMultistatusException`. Parser exception messages contain server content and are never logged (type only). Parser tests run under `RobolectricTestRunner` on the production parser (no `kxml2` test dependency).
- **Parse-cost bounds** — KXml grows `elementStack`, `attributes` and `nspStack` linearly, so deep nesting, many attributes or many namespace declarations in one tag would cost minutes to hours within the 32 MiB cap, and one 32 MiB text node about 260 MB of heap (an `OutOfMemoryError` crash). `PropfindEntryReader` therefore fails the whole response with `MalformedMultistatusException` on every start tag (prolog, responses and skipped elements) beyond an absolute depth of 32, 64 attributes or 64 namespace declarations (`PropfindEntryLimits` document bounds; per-entry limits still only skip), and reads through `XmlTokenSizeLimitingInputStream`, which fails once more than 64 KiB arrive between two markup starts (`<` outside CDATA, comments and processing instructions, because `next()` coalesces text across them). That bounds one tag with all its attributes and one text node before KXml buffers it; a maximal captured value (8 KiB characters, multi-byte UTF-8) still fits. Covered by time-bounded regression tests (200,000 nesting levels, attributes, namespace declarations; 1 MB text, CDATA and comment-split text).
- **Credentials only for the configured origin** — the `AlbumsRepository` and `WebDavClient` OkHttp interceptors and the Coil image-loader interceptor (`KrhnlesApplication`) only add `Authorization` when `request.url.hasSameOriginAs(config URL)` (scheme, host, port). OkHttp itself strips `Authorization` on cross-host / cross-port redirects (not on a same-host, same-port https → http downgrade), and application interceptors are not re-run for redirects; uploads and renames therefore never follow redirects
- **Uploaded-photo tracking reset on logout** — `SettingsViewModel.logout()` calls `UploadedPhotosStore.clear()` so the tracking starts fresh when a user disconnects (or switches servers)
- **UploadWorker records IDs after success** — each successfully uploaded photo's MediaStore ID is written to `UploadedPhotosStore`; failed uploads are not marked; re-uploads are always allowed (badge is visual only)
- **Chunked upload progress (issue #69)** — the `chunked` queue-entry object is parsed leniently (an invalid object is dropped, the entry uploads from the start), because progress is only an optimization while a malformed queue would delete the user's upload; retry files never carry progress (a manual retry may come days later, after the server's 24 h cleanup, and would complicate the retry-file contract); the digest of the confirmed prefix is re-computed by reading it again on the device instead of persisting `MessageDigest` state (not serializable; the re-read also detects a changed local file).
